# ACTRA Project — Agent Rules & Notes

## Запуск локального dev-сервера

Используй скрипт `start-dev.ps1` из корня проекта:

```powershell
.\start-dev.ps1
```

Или вручную:

```powershell
# 1. Поднять Docker-сервисы
docker compose -f docker-compose.hosted.yml -f docker-compose.localhost.yml up -d postgres minio

# 2. Запустить Flask-сервер
$env:TRAINER_HTTP_PORT         = "8000"
$env:ACTRA_RUNTIME_MODE        = "hosted_web"
$env:ACTRA_POSTGRES_DSN        = "postgresql://actra:8xQn4WmR3zKp7YtL2sVd9HcB6fJq1NwE@127.0.0.1:5433/actra" # gitleaks:allow
$env:ACTRA_S3_ENDPOINT         = "http://127.0.0.1:9000"
$env:ACTRA_S3_BUCKET           = "actra"
$env:ACTRA_S3_ACCESS_KEY       = "23N({doog?)" # gitleaks:allow
$env:ACTRA_S3_SECRET_KEY       = '8W$gx{Q&wEv' # gitleaks:allow
$env:ACTRA_SECRET_KEY          = 'actra_dev_secret_key' # gitleaks:allow
.venv\Scripts\python desktop-app/server.py
```

> ⚠️ **PostgreSQL пробрасывается на порт 5433, а не 5432!**
> Причина: Windows удерживает порт 5432 в состоянии TCP `TIME_WAIT` после каждого
> перезапуска Python-сервера (~60–120 сек), из-за чего Docker не может пробросить
> порт и PostgreSQL стартует без биндинга на хост. Порт 5433 свободен от этой
> проблемы. Конфигурация зафиксирована в `docker-compose.localhost.yml`.

## Частые проблемы

### Кнопка «Войти» зависает / ничего не делает
PostgreSQL недоступен. Симптом: в логах сервера все треды висят на `psycopg.connect()`.
Решение:
1. Убедись что Docker-контейнер запущен: `docker ps --filter "name=postgres"`
2. Убедись что порт слушается: `netstat -an | findstr "5433.*LISTEN"`
3. Если контейнер есть но порт не слушается — перезапусти: `docker compose -f docker-compose.hosted.yml -f docker-compose.localhost.yml restart postgres`

### Сервер не запускается (порт 8000 занят)
```powershell
Stop-Process -Name python -Force -ErrorAction SilentlyContinue
```

## Обязательный протокол: LLM-as-a-Verifier / Self-Verification

Агент **обязан всегда и непрерывно** применять методологию **LLM-as-a-Verifier** при решении задач в проекте ACTRA без необходимости напоминаний от пользователя.

### 1. Декомпозиция критериев верификации (Fine-Grained Criteria)
Любое решение, архитектурный план и код оцениваются по 5 ключевым критериям:
1. **Функциональная корректность (Correctness & Edge Cases):** Решает ли код поставленную задачу полностью? Обработаны ли крайние случаи, `None`/`null`, пустые данные, граничные значения?
2. **Архитектурная целостность и отсутствие регрессий (Regression & Architecture):** Совместимо ли решение с Flask, PostgreSQL (порт 5433), MinIO и существующей кодовой базой? Не ломает ли смежные модули?
3. **Безопасность и отказоустойчивость (Security & Resilience):** Есть ли корректная обработка ошибок (try/except, rollback транзакций, статус-коды HTTP, защита от SQL injection / XSS)?
4. **Производительность (Performance):** Нет ли N+1 запросов к БД, блокировок тредов Flask, утечек памяти, лишних рендеров в браузере?
5. **Качество кода и UI/UX (Clean Code & Design):** Чистота кода, отсутствие хардкода, соблюдение дизайн-системы ACTRA (Vanilla CSS, без запрещенных клише).

### 2. Best-of-N анализ сложных решений
Перед внедрением нетривиальных изменений (новые API, схема БД, сложные SQL-запросы, комплексные UI-контролы):
- Рассматривать 2–3 альтернативных варианта реализации.
- Выбирать наилучший вариант на основе декомпозированных критериев с обоснованием выбора.

### 3. Автоматический шлюз проверки (Verification Gate)
Перед завершением задачи агент **всегда**:
1. Проводит инспекцию написанного diff по критериям верификации.
2. Проверяет синтаксис / линтинг / запуск тестов (если применимо).
3. В финальном ответе кратко резюмирует статус прохождения верификации (Verification Verdict: PASS по всем критериям).

## Обязательный стандарт: ACTRA UI/UX Design & Visual Engineering (Google AI Studio Method)

Любая разработка, переработка или улучшение интерфейсов в проекте ACTRA **обязаны строго и неукоснительно** соблюдать 5 системных правил визуальной инженерии:

### 1. Правило «Анти-Матрёшка» (Strict De-nesting & Flat Surface Hierarchy)
- **Запрет на вложенность рамок глубже 1 уровня.** Внутри рабочей области (`surface-0`) допустима карточка/панель (`surface-1`). Вкладывать в неё ещё одну карточку с рамкой (`surface-2`) и ещё один блок с рамкой строго запрещено.
- Вместо нагромождения коробок в коробках разделение контента выполняется через воздух (*whitespace*), плоскую типографическую иерархию и тонкие субтильные границы (`border-subtle`).
- Запрещены искусственные «визарды» с сиротливыми стрелочками (`↓`), дробящие единый экран на псевдо-шаги.

### 2. Заповедь живого контента (Zero-Placeholder Mandate & High Data Density)
- Никакой компонент списка, витрины или карточки не имеет права рендерить слепые заглушки: «Задание 1», «Задание 2», «Элемент N».
- Компонент обязан извлекать и отображать ключевой предметный атрибут сущности: текст вопроса/промпта, эталонный ответ, значки вариантов теста `✓`/`•`, упорядоченную цепочку шагов `1 → 2 → 3` или найденные ошибки.
- Если текст длинный — использовать аккуратный `line-clamp` с многоточием, но показывать реальный контент.

### 3. Закон единственного фокуса (Single Primary CTA per Visible Zone)
- В видимой зоне экрана (или панели) может быть **ровно одно главное первичное действие** (`.btn--primary` / `.studio-btn--primary`).
- Категорически запрещено дублировать одну и ту же кнопку в шапке и подвале одной колонки одновременно.
- Кнопка действия над полем (например, «Вставить из буфера») обязана визуально и контекстно находиться в границах этого поля, а не в соседней панели или колонке.

### 4. Запрет на машинный мусор в UI (Clean Terminology & Human-Centric Copy)
- В интерфейсе категорически запрещены программные идентификаторы, SQL-поля и технические enum бэкенда (`SEQUENCE_ASSEMBLY`, `OPEN_ANSWER`, `text_errors`).
- Все типы, статусы и лейблы обязаны проходить через централизованный словарь локализации и иметь человекопонятное звучание («Последовательность», «Тест», «Открытый ответ»).

### 5. Геометрия без коллизий и утечек (Visual Geometry & No-Collision Gate)
- Полный запрет на взаимное перекрытие элементов: кнопки навигации не должны наезжать на табы, скролл-зоны обязаны быть изолированы (`min-w-0`, `overflow-x: auto`).
- Никаких выпадающих текстов за пределы футера и паразитных двойных скроллбаров.
- Перед закрытием задачи агент обязан проверить макет на реальном разрешении экрана.

### 6. Архитектурный протокол локализации Бэкенд ↔ Фронтенд (Decoupled i18n & Structured API Feedback)
- **Запрет на монолитную прозу из API в UI:** Сервисы бэкенда (Python: `TaskEvaluatorService`, валидаторы, менеджеры сложности) обязаны возвращать структурированный машинный контракт:
  `message_key` (или `code`) и `message_params` (числа, списки, пороги, флаги толерантности). Поле `message` на бэкенде сохраняется исключительно для обратной совместимости и логов.
- **Запрет на regex-парсинг бэкенд-текста на фронтенде:** Фронтенд обязан форматировать UI-сообщения через `wt(message_key, fallback, params)`, опираясь на `message_key` и `message_params`.
- **Запрет на слепую конкатенацию языков в контенте:** При генерации или модификации заданий на бэкенде (например, в `difficulty_manager`) запрещено жестко склеивать строки на русском языке к тексту на неизвестном/английском языке. Любые суффиксы или модификаторы обязаны учитывать язык исходного задания или накладываться через слои локализации интерфейса.

### 7. Системная защита от утечек локализации (4-Tier i18n Defense & Anti-Escape Gate)
- **Запрет на сырой текст в шаблонах и скриптах:** Любой пользовательский текст в HTML (`data-i18n`, `data-i18n-title`, `data-i18n-aria`, `data-i18n-placeholder`) и JS (`wt('key', 'Fallback')`) обязан быть локализован.
- **Запрет на обход через Unicode-эскейпы:** Категорически запрещено маскировать кириллицу под `\u04xx` в JS-строках (например, `'\u041f\u0430\u0443\u0437\u0430'`). Сканер утечек детектирует и блокирует такие строки.
- **Обязательный 100% паритет словарей:** Все новые ключи добавляются синхронно во все три файла: `ru.json`, `en.json`, `uk.json`.
- **4 уровня защиты от регрессий:**
  1. *CI Ratchet Gate* (`scripts/audit_i18n_leaks.py --ci`, `tests/i18n_hardcoded_leak_detector.test.mjs`): общее число унаследованных хардкод-строк может только уменьшаться (хранится в `tests/fixtures/i18n_hardcoded_baseline.json`), новые утечки не допускаются (+0 tolerance).
  2. *Нулевая толерантность для чистых экранов*: Главный экран (`Main.html` и `MainLogic.js`) зафиксирован на 0 утечек навсегда.
  3. *Runtime DOM Guardrail* (`frontend/assets/i18n.js`): `window.i18n.scanLeaks()` и строгий режим подсвечивают непереведённый контент в браузере оранжевым пунктиром (`[data-i18n-untranslated="true"]`).
  4. *Интеграционные тесты*: `tests/i18n_integrity.test.mjs` проверяет целостность ключей, паритет словарей и отсутствие битых плейсхолдеров.

### 8. Протокол проверки текстов и SMM: Anti-AI-Slop Gate
При написании любых публичных текстов, постов для соцсетей (Instagram, LinkedIn, X, Telegram), презентаций и маркетинговых материалов **обязательно** применять скилл `anti-ai-slop` (`.agents/skills/anti-ai-slop/`):
- **Запрет на AI-клише и шаблоны (Slop Lexicon & Patterns):**
  - Никаких заезженных вводных и пустого пафоса: *"In today's fast-paced world"*, *"At its core"*, *"game-changer"*, *"revolutionizing"*, *"streamline"*, *"empower"*, *"seamlessly"*, *"foster"*, *"Think about it:"*, *"In conclusion"*, *"Studies show"*.
  - Запрет на фальшивые инфобизнес-риторические связки: *"You don't have X, you have Y"*, *"Full stop"*, искусственный драматизм и дешевые интриги.
  - Никаких невидимых Unicode-символов (zero-width characters, bidi markers) — обязательна гигиена текста через `sanitize.py`.
- **Автоматический шлюз проверки (Slopcheck Linter):**
  - Любой подготовленный драфт проверяется детерминированным линтером: `python .agents/skills/anti-ai-slop/scripts/slopcheck.py <file>`.
  - Требование к тексту: результат $\ge 90/100$, отсутствие блокирующих нарушений (`major` / `blocker`).
- **Честный авторский голос ACTRA:**
  - Опираться на конкретные факты, код и клиническую практику.
  - Писать от первого лица или нейтрально-описательно, без воды и украшательств.

### 9. Протокол коммуникации и критики: Zero-Sycophancy & Objective Critique Gate
- **Полный запрет на подхалимаж и дежурные восторги (Zero Sycophancy):**
  Категорически запрещены шаблонные комплименты (*«Твоя редакция значительно сильнее!»*, *«Идея архитектурно безупречна!»*, *«Гениально!»*). Тон агента обязан быть сдержанным, профессиональным, партнёрским и ориентированным на факты.
- **Прямая критика слабых решений (Challenge by Default):**
  Если пользователь пишет нелогичную мысль, перегружает пост, путает термины, ломает драматургию или предлагает спорное UX/техническое решение — агент **обязан прямо сказать об этом**, без завуалированных смягчений разобрать слабые места и предложить альтернативы.
- **Вынесение спорных моментов на обсуждение:**
  Вместо слепого соглашательства агент обязан подсвечивать пограничные («на тоненького») вопросы, где решение несёт риски для конверсии, понимания аудиторией или архитектуры проекта.

### 10. Протокол отстранённого визуального аудита (Cold-Eye Visual Gate & UI Inspection Protocol)
Любая разработка, редизайн или аудит интерфейсов в проекте ACTRA **обязаны строго и безусловно** проходить через данный протокол. Агенту категорически запрещено одобрять работу или заявлять пользователю «все готово/исправлено», опираясь исключительно на код или зеленые тесты Vitest.

#### 1. Процедура при запросе на аудит («Cold-Eye Adversarial Audit»)
Когда пользователь просит провести аудит интерфейса, выявить огрехи или спроектировать улучшения:
1. **Инструментальный снимок (Dual-Height Viewport & Micro-Crop Matrix):**
   - Поднять локальный dev-сервер (`.\start-dev.ps1` / порт 8000, 5433).
   - Сгенерировать контрольные скриншоты в двух обязательных разрешениях: базовом **1280×800** и компактном **1280×720** (или 1280×680, моделирующем экран ноутбука с открытыми вкладками браузера и панелью задач ОС). Запрещено тестировать верстку исключительно на 1280×800.
   - **Micro-Crop Protocol (Зуммирование зон повышенного риска):** Помимо общего плана 1280×800/720 Playwright обязан автоматически нарезать и сохранять кропы критических зон высокого риска:
     - `crop_footer_boundary.png` — нижняя зона полей ввода и карточек (проверка среза выносных элементов шрифта и нижних рамок);
     - `crop_inter_section_rhythm.png` — зоны стыков между соседними карточками и селектами (проверка отсутствия 0px слипания);
     - `crop_focus_ring.png` — активные элементы в фокусе (проверка отсутствия коллизий AABB).
2. **Детерминированный шлюз автоматических проверок (Headless Assertions Gate):**
   Перед передачей рендера на визуальную оценку Playwright обязан программно валидировать 9 обязательных критериев:
   - **Zero-Truncation Assertion:** Для всех заголовков (`h1`, `h2`, `#task-title-display`), бейджей статуса, табов и кнопок выполняется проверка `element.scrollWidth <= element.offsetWidth + 1`. Любое непреднамеренное обрезание текста многоточием (`ellipsis`) является блокирующим дефектом.
   - **No-Overlap Collision Assertion (AABB):** Для интерактивных элементов в состояниях `:focus` и `:hover` проверяется отсутствие взаимного пересечения габаритов (`getBoundingClientRect()`). Фокус-контуры (`ring`, `outline`, `box-shadow`) не имеют права перекрывать или врезаться в соседние бейджи, иконки или кнопки (`badge.bottom < input.top - 2px`).
   - **Viewport Fold Assertion (1280×800 & 1280×720):** Первичный CTA, кнопка добавления элемента и первый экран данных обязаны укладываться в границу `rect.bottom <= window.innerHeight` без вынужденного вертикального скролла в базовом сценарии.
   - **Stacking Context Integrity Assertion (`elementFromPoint`):** Для любых раскрывающихся элементов («внахлёст», поповеры, оверлеи) выполняется проверка `document.elementFromPoint(x, y)` во всех 4 углах и в центре выступающей части оверлея. Если вызов возвращает соседний уровень или чужой контейнер вместо самого оверлея или его детей — это блокирующий дефект перекрытия контекста наложения.
   - **Dismiss Control Reachability Assertion (In-View & Unclipped):** Для любого раскрывающегося элемента проверяется, что контрол его закрытия (`[ ⌃ Свернуть ]`, крестик, отмена) физически находится в видимой области окна (`0 <= rect.top && rect.bottom <= window.innerHeight`). Если раскрытие опускает контрол ниже границы экрана без немедленного автоскролла — тест падает с блокирующей ошибкой.
   - **Underflow & Dead Whitespace Assertion (Anti-Void Gate):** Проверка на недозаполнение и пустые дыры. Программно замеряются коэффициенты полезного заполнения для модалок, панелей и карточек:
     - `densityRatio = innerContent.height / container.clientHeight >= 0.70` (полезный контент обязан занимать не менее 70% высоты контентного контейнера).
     - `bottomVoid = footer.top - innerContent.bottom <= 48px` (мертвая зона над футером не должна превышать 48px / стандартный паддинг `p-6`). Если контейнер растянут на 720px при высоте контента 200px, оставляя 300px белой дыры — тест падает с блокирующей ошибкой («Дыры и сироты»).
   - **Inter-Element Separation & Vertical Rhythm Assertion (Anti-Glue Gate):** Для любых последовательно расположенных функциональных блоков (карточки, секции полей, аккордеоны, списки) программно проверяется физический зазор:
     - `nextBlock.top - prevBlock.bottom >= 16px` (норматив: 20–24px / `gap: 1.25rem`–`1.5rem`).
     - Категорически запрещено нулевое расстояние (`gap < 12px` или касание), когда лейблы полей или границы нижнего блока прилипают к верхним элементам. Любое слипание блоков признается блокирующим браком.
   - **Phantom CSS & Precompiled Tailwind Verification Gate (Anti-Phantom-CSS Gate):** Категорически запрещено использовать в HTML/JS классы утилит Tailwind (например, `sm:grid-cols-3`, `space-y-3.5`, `grid-cols-6`), не проверив их физическое наличие в `frontend/assets/tailwind.css`. Любая критическая структурная сетка (Grid) и вертикальный ритм (Flex gap) обязаны явно фиксироваться в CSS-правилах `<style>` / компонента, исключая бесшумный сброс браузера в `grid-cols-1` или `gap: 0`.
   - **Silent-Clipping DOM Scanner (No-Hidden-Overflow-Clip Gate):**
     Автоматический программный обход всех контейнеров страницы с `overflow: hidden`, `overflow-y: hidden`, `overflow-x: hidden`. Для каждого контейнера проверяется:
     1. `container.scrollHeight <= container.clientHeight + 1` (контейнер не имеет скрытого переполнения).
     2. Для каждого прямого дочернего элемента: `childRect.bottom <= containerRect.bottom + 1` (дочерний элемент не вылезает за нижнюю кромку родителя).
     Категорически запрещено срезать нижние строки, сервисные плашки или кнопки границей контейнера. Поля ввода `<textarea>` обязаны иметь гибкий адаптивный `min-height` ($\le 90$px) и внутренний скролл, а сервисные плашки под ними (`#import-live-counter`) обязаны иметь `shrink-0` и оставаться на 100% видимыми при любой высоте экрана $\ge 650$px.
   - **Interactive Control-Sweep Gate & Zero-Blind-Spot Click Plan:**
     Категорический запрет на поверхностные аудиты, ограничивающиеся статическими снимками пассивного состояния! Любое модальное окно, мастер или экран обязаны иметь детерминированный сценарий **100% кликового покрытия всех интерактивных элементов**. Каждый интерактивный контрол (`button`, `select`, `input`, `checkbox`, `filter chip`, вторичные модалки `[Детали]`, переключатели исключения) обязан быть программно кликнут, активирован и сфотографирован в открытом/измененном виде.
   - **Top-Layer Stacking Context Integrity Gate (Dialog-in-Dialog Assertion):**
     Любые дочерние диалоги, карточки подробностей (`task-detail-overlay`), поповеры и тултипы, открываемые из нативного `<dialog>` (`dialog.showModal()`), обязаны монтироваться внутрь контейнера самого диалога (`.editor-import-modal-shell` / `#import-modal`), а **не** в `document.body` (где элементы DOM оказываются под Top Layer браузера, становятся невидимыми и блокируются свойством `inert`). Программно проверяется:
     1. `document.elementFromPoint(x, y)` в центре и по 4 углам вторичного оверлея возвращает сам оверлей или его дочерний элемент, а не родительскую модалку;
     2. Нажатие `Escape` обязано перехватываться (`e.stopPropagation()`, `e.preventDefault()`) и закрывать **только** вторичный оверлей, сохраняя родительский диалог открытым без потери данных.
   - **Anti-Duplicate Glyph Assertion:**
     Категорически запрещено дублировать графическую иконку одинаковым текстовым символом в теле одного бейджа или кнопки (например, иконка `<span class="material-symbols-outlined">check_circle</span>` в паре с текстом `✓ Готово` $\rightarrow$ визуальный дефект «две галочки подряд»). Все строковые лейблы обязаны содержать чистый текст без ручных Unicode-глифов (`"Готово"`, `"Ошибка"`, `"Требует внимания"`, `"Конфликт"`).
   - **Dropdown Chevron Clearance Assertion (Anti-Arrow-Overlap Gate):**
     Все выпадающие списки `<select>` обязаны оформляться по дизайн-системе ACTRA: `appearance-none`, кастомный шеврон `expand_more` с `pointer-events-none absolute right-2.5 top-1/2 -translate-y-1/2` и достаточный правый внутренний отступ `pr-8` ($\ge 32$px), полностью гарантирующий, что текст выбранного пункта любой длины не перекроет стрелку селекта.
3. **Обязательный матричный охват состояний (Dynamic States Matrix):**
   Запрещено инспектировать только пассивное состояние покоя (`idle`). Проверка обязана включать:
   - `idle` (чистое состояние покоя);
   - `focused / active` (активный ввод в самом длинном/нагруженном блоке данных с включённым фокус-кольцом);
   - `dirty / unsaved` (состояние несохранённых изменений с широкими предупреждающими бейджами);
   - **`heavy-stress-payload` («Стена текста» & Extreme Capacity):** Запрещено ограничиваться скромными 4 строками! Обязательна заливка реальной «Стены текста» $\ge 1500$–$2500$ символов (15–20 параграфов) и длинных неразрывных строк $\ge 80$ символов. Проверяется наличие адаптивного потолка высоты (`max-height: min(...)`), отсутствие растяжения на 2000px и плавный внутренний скролл.
   - **`worst-case-geometry` (Экстремальные пространственные координаты):** Тестирование интерактивных состояний на самых неблагоприятных пространственных позициях:
     - самый нижний элемент нижнего уровня у границы подвала страницы;
     - крайний правый элемент у сайдбара;
     - элемент непосредственно под sticky-шапкой.
4. **Прокурорская деконструкция по 9 смертным грехам верстки:** Агент обязан посмотреть на скриншот глазами стороннего придирчивого критика и выписать найденные дефекты по чек-листу ниже. Запрещены общие фразы вроде «интерфейс в целом выглядит хорошо».
5. **Adversarial Quota (Принцип «Адвоката дьявола»):**
   Промпты для субагентов-аудиторов обязаны требовать нахождения **не менее 3 конкретных дефектов верстки** (с селекторами, координатами и замерами). Отчёты с формулировками «всё выглядит отлично, дефектов не найдено» признаются поверхностными и автоматически бракуются.
6. **Best-of-N архитектурный выбор:** Предложить 2–3 альтернативных компоновочных решения, опираясь на скиллы (`universal-design-principles`, `anti-ui-slop`, `checklist-design`), аргументировать выбор сильнейшего.
7. **Контрольный снимок До / После:** Реализовать изменения, снять проверочный скриншот, просмотреть его через `view_file` и встроить в финальный отчет.

#### 2. Шлюз проверки: 9 смертных грехов верстки (Cold-Eye Checklist)
Перед завершением любой UI-задачи агент обязан проинспектировать реальный рендер по 9 критериям:
1. **«Дыры и сироты» (Void & Orphan Gate):** 
   - Запрещен неконтролируемый `flex-wrap` для разнородных бейджей, образующий рваный правый край и пустоту на последней строке.
   - Сетка обязана быть либо строгой табличной (`grid grid-cols-2`), либо центрированной, либо широкие элементы обязаны явно растягиваться на всю ширину (`col-span-2`).
2. **«Раздутые карточки и висячие кнопки» (Balloon Cards & Proximity Violation Gate):**
   - Запрещено использовать жесткое растяжение сетки (`items-stretch`) в сочетании с `justify-between`, если элементы в ряду содержат разное количество строк. Это приводит к раздуванию карточек с коротким текстом огромной белой пустотой (дырой) и отрыву кнопок навигации от текста на 50–100px.
   - **Закон близости Гештальта (Gestalt Proximity):** Элементы управления обязаны физически прилегать к контенту, которым они управляют. Контейнеры должны обнимать свой контент (`height: fit-content` / `items-start`), либо кнопки управления должны выноситься в шапку карточки, либо пустота должна поглощаться активным полем ввода, а не мёртвой зоной.
3. **«Слоёный пирог / Кладбище плашек» (Pill Pileup Gate):**
   - Запрещено нагромождать несколько слоев мелких плашек подряд (например, ряд кнопок над рядом бейджей над полем).
   - Более 1 ряда разнородных плашек подряд запрещено — переводить во вложенный/единый селектор, аккордеон или структурированную таблицу.
4. **«Асимметрия колонок» (Column Mismatch Gate):**
   - Запрещен разнобой, когда в одной колонке подряд идут блоки с разным делением ширины (например, сверху 3 колонки, под ним 2, под ним 4). Все блоки обязаны подчиняться единой визуальной сетке.
5. **«Серая каша и потеря аффорданса» (Muddy Surface & Ghost Controls):**
   - Интерактивные элементы обязаны иметь явный физический аффорданс (собственную светлую подложку `surface-1`, субтильную границу `border-border-subtle`, hover-состояние и тень).
   - Запрещено бросать голый текст кнопок на серый фон (`surface-2`), превращая интерфейс в некликабельную «серую кашу».
   - Запрещены вложенные серые коробки (`surface-2` внутри `surface-2`).
6. **«Обрезки и многоточия» (Zero Truncation Gate):**
   - Запрещены паразитные многоточия (`...`) в заголовках, табах, кнопках, счетчиках и статусах на десктопных разрешениях $\ge 1280$px.
   - Длинные слова (например, «Последовательность», «Открытый ответ») обязаны либо иметь достаточную фиксированную ширину, либо выноситься в контролы полной ширины.
   - Запрещено перегружать шапку статическими префиксами («Редактирование: ...»), ворующими полезную ширину у названия документа.
7. **«Конфликт шапки» (Header Collision Gate):**
   - Заголовок панели и вспомогательные контролы/бейджи не должны бороться за ширину в одной строке, вызывая сжатие текста. При риске коллизии контрол переносится на отдельную строку или компактно реорганизуется.
8. **«Иерархия весов» (Visual Hierarchy Gate):**
   - Основная рабочая зона пользователя (например, поле ввода редактора) обязана визуально доминировать по площади, контрасту и размеру первичного CTA над вспомогательными панелями и памятками.
9. **«Слепые оверлеи и срезанные контролы» (Blind Overlay & Occluded Dismiss Gate):**
   - **Запрет на перекрытие контекстом наложения:** Любой раскрывающийся оверлей обязан возвышать весь свой путь в дереве (`z-index: 40/45/50` на уровень, слот-враппер и саму карточку), чтобы нижележащие уровни и карточки никогда не срезали его своим непрозрачным фоном.
   - **Заповедь безусловной видимости выхода:** Кнопка сворачивания/закрытия обязана быть доступна моментально. Если элемент раскрывается вниз у границы экрана, обязателен плавный автоскролл в зону видимости, либо дублирующий контрол сворачивания в шапке элемента.
   - **Запрет на бесконечный вылет (Adaptive Capping):** Любой раскрывающийся блок обязан иметь потолок `max-height: min(16rem, 36vh)` с внутренним скроллом, чтобы карточка физически не могла перерасти треть экрана.

#### 3. Паритет статической разметки и гидратации (Zero Hydration Lag Gate)
- Текстовые строки в исходных HTML-файлах (шаблонах до запуска JavaScript) обязаны быть на 100% синхронизированы с текущими словарями `ru.json`, `en.json`, `uk.json`.
- Категорически запрещено оставлять в HTML устаревшие термины или заглушки, рассчитывая, что скрипт локализации перезапишет их в рантайме. При любых задержках сети или ошибках гидратации интерфейс обязан оставаться терминологически безупречным.

#### 4. Канон адаптивной геометрии модальных окон (Step-Aware Modal Geometry Canon)
- **Запрет на монолитный жесткий каркас модалки:** Категорически запрещено задавать единый фиксированный размер (`width: min(94vw, 76rem); height: min(90vh, 56rem);`) для всего модального окна без учета текущего шага и объема данных.
- **Двухрежимная адаптивность (Dialog vs. Studio):**
  - *Шаги выбора, онбординга и подтверждения (Диалоговый режим / Step 1 & Confirm):* Обязаны облегать свой контент (`width: min(92vw, 48rem); height: auto; max-height: min(88vh, 44rem);`), контентная зона `flex: 0 1 auto`. Окно аккуратно центрируется по вертикали, футер прилегает к контенту без пустот, вертикальный скроллбар строго запрещен (`hasVerticalScroll === False`).
  - *Шаги авторской работы, редактора и предпросмотра (Студийный режим / Step 2 & 3):* Расширяются в полноразмерную студию (`width: min(94vw, 76rem); height: min(90vh, 56rem);`), контентная зона `flex: 1 1 0%` со скроллом только внутри специализированных панелей (текст, шпаргалка, сетка карточек).
  - *Синхронизация через data-current-step:* Корневой элемент `<dialog>` или `.modal-shell` обязан поддерживать атрибут `data-current-step="${step}"`, управляющий размерами и плавным переходом `transition: width 0.25s, max-height 0.25s`.
- **Заповедь четкой гештальт-группировки секций:** Каждый обособленный функциональный блок внутри шага обязан иметь секционный заголовок (`text-xs font-bold uppercase tracking-wider text-text-secondary`) или явный визуальный разделитель. Запрещено бросать поля ввода без смыслового якоря (например, переход от выбора формата к выбору модуля без заголовка «ЦЕЛЕВОЙ РАЗДЕЛ»).

### 11. Протокол независимого мультиролевого аудита (Multi-Role Subagent Panel Protocol)
Для исключения когнитивных искажений разработчика («у меня всё работает», замыливание взгляда) и дежурного формализма любой аудит сложного интерфейса в ACTRA **обязан проводиться независимой панелью субагентов по 3 специализированным ролям** с жестким пятифазным регламентом.

#### 1. Триада ролей субагентов (The Audit Triad)
Каждый субагент запускается изолированно (`invoke_subagent`), наделяется уникальным мировоззрением и оценивает интерфейс через призму своего профиля:

1. **Роль 1: Преподаватель-новичок (First-Time UX & Onboarding Reviewer)**
   - **Профиль:** Преподаватель / автор курса, впервые открывший редактор. Не является разработчиком, не знает технического сленга программистов, не терпит сложных абстракций.
   - **Зона ответственности и фокус проверки:**
     - **Первое впечатление и чистое состояние (`01_default_blank`):** Ясно ли с первой секунды, что нужно делать? Соблюдается ли заповедь *Zero-Placeholder* (подсказки-плейсхолдеры объясняют механику без фиктивного мусора).
     - **Обучающий онбординг-тур (`02_tour_step_1`..`step_5`):** Логика шагов, доходчивость формулировок, 100% паритет подсказок с реальным положением элементов (отсутствие дезориентации).
     - **Терминология и доступность:** Человекопонятный язык вместо технических идентификаторов (SQL/бэкенд терминов).
     - **Защита от потери данных (Data Loss Prevention):** Наличие диалогов подтверждения (`confirmAction`) при деструктивных действиях («Очистить всё»), четкая индикация несохраненных изменений (`dirty / unsaved`).

2. **Роль 2: Опытный методист / Процедурный инженер (Didactics, Advanced Workflows & Ergonomics)**
   - **Профиль:** Специалист по педагогическому дизайну, регламентам, СОПам, технологическим картам и клиническим алгоритмам.
   - **Зона ответственности и фокус проверки:**
     - **Стресс-сценарии и большие объемы (Heavy Stress Payload):** Проверка на реальных длинных формулировках (дозировки, условия, предупреждения безопасности), процедурных матрицах на 8–12 шагов (`04_many_elements`) и вертикальных иерархиях на 4+ уровней (`05_many_levels`).
     - **Дидактическая строгость настроек:** Валидация логики оценивания (например, смысл режима «порядок уровней без порядка шагов» — исключение дидактически абсурдных состояний). Точность формулировок правил прохождения в информационной карточке.
     - **Эргономика и паттерны чтения:** Удобство перемещения шагов (Z-pattern: слева-направо, сверху-вниз), необходимость Drag-and-Drop против кнопочной навигации при длинных цепочках.
     - **Интерактивный Справочник (`/reference`):** Ценность живого превью и обучающей статьи для быстрого освоения механики.

3. **Роль 3: Строгий визуальный критик и хранитель дизайн-системы (Cold-Eye Visual & Design System Guardian)**
   - **Профиль:** Беспристрастный внешний прокурор интерфейсов. Запрет на похвалу; презумпция наличия скрытых дефектов верстки.
   - **Зона ответственности и фокус проверки:**
     - **9 смертных грехов верстки ACTRA:** «Дыры и сироты», «Раздутые карточки», «Слоёный пирог», «Асимметрия колонок», «Серая каша», «Обрезки», «Конфликт шапки», «Иерархия весов», «Слепые оверлеи».
     - **Контексты наложения и геометрия:** Проверка `elementFromPoint` для раскрывающихся оверлеев, адаптивный потолок высоты, гарантированная видимость контролов закрытия (`[ ⌃ Свернуть ]`).
     - **Темная тема («Ночь» / dark-a) и WCAG AA:** Контрастность границ, читаемость текста, отсутствие грязи и «слипания» плашек.
     - **Состояния фокуса и ввода:** Четкость `:focus-visible` колец без коллизий с соседними бейджами.

#### 2. Пятифазный регламент исполнения (Phased Audit Pipeline)
Аудит по ролям выполняется строго по 5 шагам:

- **Фаза 1: Подготовка полигона и инструментальная матрица снимков (Baseline & Stress Capture)**
  - Поднятие локального окружения (`.\start-dev.ps1` / порт 8000, 5433).
  - Генерация полного набора тестовых снимков в двух обязательных разрешениях: базовом **1280×800** и компактном **1280×720** (или 1280×680) через Playwright-скрипты (`scripts/visual_qa_capture.py` или сценарии `capture_*_qa.py`):
    - `01_default_blank` (чистое состояние);
    - `02_standard_populated` (стандартное наполнение);
    - `03_multiline_bug_reproduction` и `03b_multiline_focused` (многострочные карточки и фокус);
    - `04_many_elements` (нагруженная матрица шагов);
    - `05_many_levels` (многоуровневая структура);
    - `06_sidebar_settings` (состояния сайдбара и настроек);
    - `07_dark_theme` (темная тема «Ночь»);
    - снимки шагов онбординг-тура и Справочника (`/reference`).
  - **Автоматическая нарезка Micro-Crops (Зуммирование зон повышенного риска):** Скрипт обязан сохранять изолированные кропы критических зон в высоком разрешении:
    - `crop_footer_boundary.png` — нижняя зона полей ввода, карточек и статусов (инспекция срезов выносных элементов шрифта);
    - `crop_inter_section_rhythm.png` — зоны стыков между соседними карточками и селектами (инспекция расстояний $\ge 16$px);
    - `crop_focus_ring.png` — элементы в фокусе (инспекция AABB-коллизий).
  - **Детерминированный Silent-Clipping DOM Scanner:** Автоматическая валидация отсутствия срезанных детей во всех `overflow: hidden` контейнерах (`scrollHeight <= clientHeight + 1` и `child.bottom <= container.bottom + 1`).
- **Фаза 2: Изолированный запуск субагентов (Subagent Isolation & Adversarial Quota)**
  - Запуск субагентов через `invoke_subagent` с персональными системными инструкциями для каждой из 3 ролей.
  - **Обязательный аудит КАЖДОГО шага / состояния:** Субагенты обязаны проверять не только финальный нагруженный шаг, но **каждый шаг процесса по отдельности (Шаг 1, Шаг 2, Шаг 3, диалог закрытия)** на двух высотах (1280×800 и 1280×720). Запрещено игнорировать начальные экраны как «тривиальные».
  - **Обязательный 6-точечный Pixel-Level Checklist для каждого субагента:**
    Промпт субагента обязан требовать явной оценки по 6 микро-пунктам:
    1) *Выносные элементы шрифта (Letter Descenders Check):* Проверка нижней строки текста в карточках, полях ввода и подвалах (буквы «р», «д», «з», «у», «ц», «щ», «p», «q», «y», «g», «j»). Любой срез нижних пикселей или касание нижней границы — блокирующий дефект.
    2) *Целостность нижних рамок и скруглений (Border Radius & Frame Integrity):* Нижняя граница контейнера или карточки обязана быть видна целиком вместе со скругленными углами (`rounded-xl` / `border-b`). Контейнер не должен быть «утоплен» или обрезан снизу родителем с `overflow: hidden`.
    3) *Замер вертикального ритма и стыков (Inter-Section Separation):* Физический зазор между соседними функциональными блоками обязан составлять $\ge 16$px (`gap: 1.25rem`–`1.5rem`). Категорически запрещено нулевое расстояние или касание рамок.
    4) *Отсутствие паразитного диалогового скролла (Zero Dialog Scroll):* На компактных высотах (720px/680px) диалоговые шаги (Шаг 1, окна подтверждения) обязаны помещаться целиком без полос прокрутки.
    5) *Свободный доступ к контролам и видимость fold (Fold Clearance & Dismiss Reachability):* Кнопка закрытия, отмены и первичный CTA обязаны находиться строго в видимой области окна (`rect.bottom <= window.innerHeight`).
    6) *Замер пропорций контента и мертвых зон (Anti-Void Gate):* Высота мертвого белого пространства над футером не должна превышать 48px, а полезный контент обязан занимать $\ge 70\%$ высоты контентной зоны.
  - **Micro-Crop Inspection:** Субагентам передаются прямые пути к кропам высокого риска (`crop_footer_boundary.png`, `crop_inter_section_rhythm.png`) через `view_file` для детального осмотра пиксельных срезов, которые могут замыливаться на общем скриншоте.
  - **Adversarial Quota:** Каждый субагент обязан предоставить не менее 3 конкретных дефектов / точек трения с указанием селекторов, скриншотов и координат. Поверхностные отчеты с похвалой не принимаются.
  - Субагенты работают только с реальными артефактами через `view_file` и исходным кодом.
- **Фаза 3: Единый накопительный реестр замечаний (`audit_findings_registry.md`)**
  - Главный агент агрегирует выводы триады в единый артефакт в директории conversation: `audit_findings_registry.md`.
  - Структура записи:
    `| ID | Роль-источник | Компонент / Экран | Описание дефекта | Критичность (Blocker/High/Medium/Low) | Инженерное решение | Статус |`
- **Фаза 4: Пакетированная инженерная реализация (Batched Remediation)**
  - Дефекты разбиваются на логические пакеты (CSS-геометрия, JS-логика/безопасность, локализация и онбординг).
  - Правки внедряются последовательно с сохранением чистоты Git и обратной совместимости.
- **Фаза 5: Контрольный шлюз верификации До / После (Post-Fix Verification Gate)**
  - Повторный запуск инструментального снятия скриншотов на тех же состояниях в двух высотах (1280×800 и 1280×720) и генерация обновленных micro-crops.
  - Автоматическая валидация Headless Assertions Gate (включая Silent-Clipping DOM Scanner).
  - **Per-Iteration Subagent Review Gate (Обязательный аудит субагентов на каждую UI-итерацию):**
    - Агенту **категорически запрещено** объявлять задачу завершенной или отвечать пользователю «все готово/исправлено», опираясь лишь на код или тесты Vitest.
    - Перед финальным ответом агент **обязан** запустить независимых субагентов (`invoke_subagent`), которые смотрят реальный скриншот и micro-crops через `view_file` и проверяют каждый пункт 6-точечного Pixel-Level Checklist. Только после вердикта PASS от субагентов работа может быть представлена пользователю.
  - Сопоставление До / После через `view_file`.
  - Автоматические тесты: прогон Vitest (`npm test`), шлюз локализации (`scripts/audit_i18n_leaks.py --ci` с требованием +0 утечек).
  - Перевод всех пунктов реестра в статус `[FIXED / RESOLVED]`.
