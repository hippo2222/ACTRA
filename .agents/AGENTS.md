# ACTRA Project — Agent Rules & Notes

## Запуск локального dev-сервера

Используй скрипт `start-dev.ps1` из корня проекта:

```powershell
.\start-dev.ps1
```

Или вручную:

```powershell
# 1. Поднять Docker-сервисы
docker compose -f docker-compose.hosted.yml -f docker-compose.localhost.yml up -d postgres minio

# 2. Запустить Flask-сервер
$env:TRAINER_HTTP_PORT         = "8000"
$env:ACTRA_RUNTIME_MODE        = "hosted_web"
$env:ACTRA_POSTGRES_DSN        = "postgresql://actra:8xQn4WmR3zKp7YtL2sVd9HcB6fJq1NwE@127.0.0.1:5433/actra" # gitleaks:allow
$env:ACTRA_S3_ENDPOINT         = "http://127.0.0.1:9000"
$env:ACTRA_S3_BUCKET           = "actra"
$env:ACTRA_S3_ACCESS_KEY       = "23N({doog?)" # gitleaks:allow
$env:ACTRA_S3_SECRET_KEY       = '8W$gx{Q&wEv' # gitleaks:allow
$env:ACTRA_SECRET_KEY          = 'actra_dev_secret_key' # gitleaks:allow
.venv\Scripts\python desktop-app/server.py
```

> ⚠️ **PostgreSQL пробрасывается на порт 5433, а не 5432!**
> Причина: Windows удерживает порт 5432 в состоянии TCP `TIME_WAIT` после каждого
> перезапуска Python-сервера (~60–120 сек), из-за чего Docker не может пробросить
> порт и PostgreSQL стартует без биндинга на хост. Порт 5433 свободен от этой
> проблемы. Конфигурация зафиксирована в `docker-compose.localhost.yml`.

## Частые проблемы

### Кнопка «Войти» зависает / ничего не делает
PostgreSQL недоступен. Симптом: в логах сервера все треды висят на `psycopg.connect()`.
Решение:
1. Убедись что Docker-контейнер запущен: `docker ps --filter "name=postgres"`
2. Убедись что порт слушается: `netstat -an | findstr "5433.*LISTEN"`
3. Если контейнер есть но порт не слушается — перезапусти: `docker compose -f docker-compose.hosted.yml -f docker-compose.localhost.yml restart postgres`

### Сервер не запускается (порт 8000 занят)
```powershell
Stop-Process -Name python -Force -ErrorAction SilentlyContinue
```

## Обязательный протокол: LLM-as-a-Verifier / Self-Verification

Агент **обязан всегда и непрерывно** применять методологию **LLM-as-a-Verifier** при решении задач в проекте ACTRA без необходимости напоминаний от пользователя.

### 1. Декомпозиция критериев верификации (Fine-Grained Criteria)
Любое решение, архитектурный план и код оцениваются по 5 ключевым критериям:
1. **Функциональная корректность (Correctness & Edge Cases):** Решает ли код поставленную задачу полностью? Обработаны ли крайние случаи, `None`/`null`, пустые данные, граничные значения?
2. **Архитектурная целостность и отсутствие регрессий (Regression & Architecture):** Совместимо ли решение с Flask, PostgreSQL (порт 5433), MinIO и существующей кодовой базой? Не ломает ли смежные модули?
3. **Безопасность и отказоустойчивость (Security & Resilience):** Есть ли корректная обработка ошибок (try/except, rollback транзакций, статус-коды HTTP, защита от SQL injection / XSS)?
4. **Производительность (Performance):** Нет ли N+1 запросов к БД, блокировок тредов Flask, утечек памяти, лишних рендеров в браузере?
5. **Качество кода и UI/UX (Clean Code & Design):** Чистота кода, отсутствие хардкода, соблюдение дизайн-системы ACTRA (Vanilla CSS, без запрещенных клише).

### 2. Best-of-N анализ сложных решений
Перед внедрением нетривиальных изменений (новые API, схема БД, сложные SQL-запросы, комплексные UI-контролы):
- Рассматривать 2–3 альтернативных варианта реализации.
- Выбирать наилучший вариант на основе декомпозированных критериев с обоснованием выбора.

### 3. Автоматический шлюз проверки (Verification Gate)
Перед завершением задачи агент **всегда**:
1. Проводит инспекцию написанного diff по критериям верификации.
2. Проверяет синтаксис / линтинг / запуск тестов (если применимо).
3. В финальном ответе кратко резюмирует статус прохождения верификации (Verification Verdict: PASS по всем критериям).

## Обязательный стандарт: ACTRA UI/UX Design & Visual Engineering (Google AI Studio Method)

Любая разработка, переработка или улучшение интерфейсов в проекте ACTRA **обязаны строго и неукоснительно** соблюдать 5 системных правил визуальной инженерии:

### 1. Правило «Анти-Матрёшка» (Strict De-nesting & Flat Surface Hierarchy)
- **Запрет на вложенность рамок глубже 1 уровня.** Внутри рабочей области (`surface-0`) допустима карточка/панель (`surface-1`). Вкладывать в неё ещё одну карточку с рамкой (`surface-2`) и ещё один блок с рамкой строго запрещено.
- Вместо нагромождения коробок в коробках разделение контента выполняется через воздух (*whitespace*), плоскую типографическую иерархию и тонкие субтильные границы (`border-subtle`).
- Запрещены искусственные «визарды» с сиротливыми стрелочками (`↓`), дробящие единый экран на псевдо-шаги.

### 2. Заповедь живого контента (Zero-Placeholder Mandate & High Data Density)
- Никакой компонент списка, витрины или карточки не имеет права рендерить слепые заглушки: «Задание 1», «Задание 2», «Элемент N».
- Компонент обязан извлекать и отображать ключевой предметный атрибут сущности: текст вопроса/промпта, эталонный ответ, значки вариантов теста `✓`/`•`, упорядоченную цепочку шагов `1 → 2 → 3` или найденные ошибки.
- Если текст длинный — использовать аккуратный `line-clamp` с многоточием, но показывать реальный контент.

### 3. Закон единственного фокуса (Single Primary CTA per Visible Zone)
- В видимой зоне экрана (или панели) может быть **ровно одно главное первичное действие** (`.btn--primary` / `.studio-btn--primary`).
- Категорически запрещено дублировать одну и ту же кнопку в шапке и подвале одной колонки одновременно.
- Кнопка действия над полем (например, «Вставить из буфера») обязана визуально и контекстно находиться в границах этого поля, а не в соседней панели или колонке.

### 4. Запрет на машинный мусор в UI (Clean Terminology & Human-Centric Copy)
- В интерфейсе категорически запрещены программные идентификаторы, SQL-поля и технические enum бэкенда (`SEQUENCE_ASSEMBLY`, `OPEN_ANSWER`, `text_errors`).
- Все типы, статусы и лейблы обязаны проходить через централизованный словарь локализации и иметь человекопонятное звучание («Последовательность», «Тест», «Открытый ответ»).

### 5. Геометрия без коллизий и утечек (Visual Geometry & No-Collision Gate)
- Полный запрет на взаимное перекрытие элементов: кнопки навигации не должны наезжать на табы, скролл-зоны обязаны быть изолированы (`min-w-0`, `overflow-x: auto`).
- Никаких выпадающих текстов за пределы футера и паразитных двойных скроллбаров.
- Перед закрытием задачи агент обязан проверить макет на реальном разрешении экрана.

### 6. Архитектурный протокол локализации Бэкенд ↔ Фронтенд (Decoupled i18n & Structured API Feedback)
- **Запрет на монолитную прозу из API в UI:** Сервисы бэкенда (Python: `TaskEvaluatorService`, валидаторы, менеджеры сложности) обязаны возвращать структурированный машинный контракт:
  `message_key` (или `code`) и `message_params` (числа, списки, пороги, флаги толерантности). Поле `message` на бэкенде сохраняется исключительно для обратной совместимости и логов.
- **Запрет на regex-парсинг бэкенд-текста на фронтенде:** Фронтенд обязан форматировать UI-сообщения через `wt(message_key, fallback, params)`, опираясь на `message_key` и `message_params`.
- **Запрет на слепую конкатенацию языков в контенте:** При генерации или модификации заданий на бэкенде (например, в `difficulty_manager`) запрещено жестко склеивать строки на русском языке к тексту на неизвестном/английском языке. Любые суффиксы или модификаторы обязаны учитывать язык исходного задания или накладываться через слои локализации интерфейса.

### 7. Системная защита от утечек локализации (4-Tier i18n Defense & Anti-Escape Gate)
- **Запрет на сырой текст в шаблонах и скриптах:** Любой пользовательский текст в HTML (`data-i18n`, `data-i18n-title`, `data-i18n-aria`, `data-i18n-placeholder`) и JS (`wt('key', 'Fallback')`) обязан быть локализован.
- **Запрет на обход через Unicode-эскейпы:** Категорически запрещено маскировать кириллицу под `\u04xx` в JS-строках (например, `'\u041f\u0430\u0443\u0437\u0430'`). Сканер утечек детектирует и блокирует такие строки.
- **Обязательный 100% паритет словарей:** Все новые ключи добавляются синхронно во все три файла: `ru.json`, `en.json`, `uk.json`.
- **4 уровня защиты от регрессий:**
  1. *CI Ratchet Gate* (`scripts/audit_i18n_leaks.py --ci`, `tests/i18n_hardcoded_leak_detector.test.mjs`): общее число унаследованных хардкод-строк может только уменьшаться (хранится в `tests/fixtures/i18n_hardcoded_baseline.json`), новые утечки не допускаются (+0 tolerance).
  2. *Нулевая толерантность для чистых экранов*: Главный экран (`Main.html` и `MainLogic.js`) зафиксирован на 0 утечек навсегда.
  3. *Runtime DOM Guardrail* (`frontend/assets/i18n.js`): `window.i18n.scanLeaks()` и строгий режим подсвечивают непереведённый контент в браузере оранжевым пунктиром (`[data-i18n-untranslated="true"]`).
  4. *Интеграционные тесты*: `tests/i18n_integrity.test.mjs` проверяет целостность ключей, паритет словарей и отсутствие битых плейсхолдеров.

### 8. Протокол проверки текстов и SMM: Anti-AI-Slop Gate
При написании любых публичных текстов, постов для соцсетей (Instagram, LinkedIn, X, Telegram), презентаций и маркетинговых материалов **обязательно** применять скилл `anti-ai-slop` (`.agents/skills/anti-ai-slop/`):
- **Запрет на AI-клише и шаблоны (Slop Lexicon & Patterns):**
  - Никаких заезженных вводных и пустого пафоса: *"In today's fast-paced world"*, *"At its core"*, *"game-changer"*, *"revolutionizing"*, *"streamline"*, *"empower"*, *"seamlessly"*, *"foster"*, *"Think about it:"*, *"In conclusion"*, *"Studies show"*.
  - Запрет на фальшивые инфобизнес-риторические связки: *"You don't have X, you have Y"*, *"Full stop"*, искусственный драматизм и дешевые интриги.
  - Никаких невидимых Unicode-символов (zero-width characters, bidi markers) — обязательна гигиена текста через `sanitize.py`.
- **Автоматический шлюз проверки (Slopcheck Linter):**
  - Любой подготовленный драфт проверяется детерминированным линтером: `python .agents/skills/anti-ai-slop/scripts/slopcheck.py <file>`.
  - Требование к тексту: результат $\ge 90/100$, отсутствие блокирующих нарушений (`major` / `blocker`).
- **Честный авторский голос ACTRA:**
  - Опираться на конкретные факты, код и клиническую практику.
  - Писать от первого лица или нейтрально-описательно, без воды и украшательств.

### 9. Протокол коммуникации и критики: Zero-Sycophancy & Objective Critique Gate
- **Полный запрет на подхалимаж и дежурные восторги (Zero Sycophancy):**
  Категорически запрещены шаблонные комплименты (*«Твоя редакция значительно сильнее!»*, *«Идея архитектурно безупречна!»*, *«Гениально!»*). Тон агента обязан быть сдержанным, профессиональным, партнёрским и ориентированным на факты.
- **Прямая критика слабых решений (Challenge by Default):**
  Если пользователь пишет нелогичную мысль, перегружает пост, путает термины, ломает драматургию или предлагает спорное UX/техническое решение — агент **обязан прямо сказать об этом**, без завуалированных смягчений разобрать слабые места и предложить альтернативы.
- **Вынесение спорных моментов на обсуждение:**
  Вместо слепого соглашательства агент обязан подсвечивать пограничные («на тоненького») вопросы, где решение несёт риски для конверсии, понимания аудиторией или архитектуры проекта.

### 10. Протокол отстранённого визуального аудита (Cold-Eye Visual Gate & UI Inspection Protocol)
Любая разработка, редизайн или аудит интерфейсов в проекте ACTRA **обязаны строго и безусловно** проходить через данный протокол. Агенту категорически запрещено одобрять работу или заявлять пользователю «все готово/исправлено», опираясь исключительно на код или зеленые тесты Vitest.

#### 1. Процедура при запросе на аудит («Cold-Eye Adversarial Audit»)
Когда пользователь просит провести аудит интерфейса, выявить огрехи или спроектировать улучшения:
1. **Инструментальный снимок (Dual-Height Viewport & Micro-Crop Matrix):**
   - Поднять локальный dev-сервер (`.\start-dev.ps1` / порт 8000, 5433).
   - Сгенерировать контрольные скриншоты в двух обязательных разрешениях: базовом **1280×800** и компактном **1280×720** (или 1280×680, моделирующем экран ноутбука с открытыми вкладками браузера и панелью задач ОС). Запрещено тестировать верстку исключительно на 1280×800.
   - **Micro-Crop Protocol (Зуммирование зон повышенного риска):** Помимо общего плана 1280×800/720 Playwright обязан автоматически нарезать и сохранять кропы критических зон высокого риска:
     - `crop_footer_boundary.png` — нижняя зона полей ввода и карточек (проверка среза выносных элементов шрифта и нижних рамок);
     - `crop_inter_section_rhythm.png` — зоны стыков между соседними карточками и селектами (проверка отсутствия 0px слипания);
     - `crop_focus_ring.png` — активные элементы в фокусе (проверка отсутствия коллизий AABB).
2. **Детерминированный шлюз автоматических проверок (Headless Assertions Gate):**
   Перед передачей рендера на визуальную оценку Playwright обязан программно валидировать 9 обязательных критериев:
   - **Zero-Truncation Assertion:** Для всех заголовков (`h1`, `h2`, `#task-title-display`), бейджей статуса, табов и кнопок выполняется проверка `element.scrollWidth <= element.offsetWidth + 1`. Любое непреднамеренное обрезание текста многоточием (`ellipsis`) является блокирующим дефектом.
   - **No-Overlap Collision Assertion (AABB):** Для интерактивных элементов в состояниях `:focus` и `:hover` проверяется отсутствие взаимного пересечения габаритов (`getBoundingClientRect()`). Фокус-контуры (`ring`, `outline`, `box-shadow`) не имеют права перекрывать или врезаться в соседние бейджи, иконки или кнопки (`badge.bottom < input.top - 2px`).
   - **Viewport Fold Assertion (1280×800 & 1280×720):** Первичный CTA, кнопка добавления элемента и первый экран данных обязаны укладываться в границу `rect.bottom <= window.innerHeight` без вынужденного вертикального скролла в базовом сценарии.
   - **Stacking Context Integrity Assertion (`elementFromPoint`):** Для любых раскрывающихся элементов («внахлёст», поповеры, оверлеи) выполняется проверка `document.elementFromPoint(x, y)` во всех 4 углах и в центре выступающей части оверлея. Если вызов возвращает соседний уровень или чужой контейнер вместо самого оверлея или его детей — это блокирующий дефект перекрытия контекста наложения.
   - **Dismiss Control Reachability Assertion (In-View & Unclipped):** Для любого раскрывающегося элемента проверяется, что контрол его закрытия (`[ ⌃ Свернуть ]`, крестик, отмена) физически находится в видимой области окна (`0 <= rect.top && rect.bottom <= window.innerHeight`). Если раскрытие опускает контрол ниже границы экрана без немедленного автоскролла — тест падает с блокирующей ошибкой.
   - **Underflow & Dead Whitespace Assertion (Anti-Void Gate):** Проверка на недозаполнение и пустые дыры. Программно замеряются коэффициенты полезного заполнения для модалок, панелей и карточек:
     - `densityRatio = innerContent.height / container.clientHeight >= 0.70` (полезный контент обязан занимать не менее 70% высоты контентного контейнера).
     - `bottomVoid = footer.top - innerContent.bottom <= 48px` (мертвая зона над футером не должна превышать 48px / стандартный паддинг `p-6`). Если контейнер растянут на 720px при высоте контента 200px, оставляя 300px белой дыры — тест падает с блокирующей ошибкой («Дыры и сироты»).
   - **Inter-Element Separation & Vertical Rhythm Assertion (Anti-Glue Gate):** Для любых последовательно расположенных функциональных блоков (карточки, секции полей, аккордеоны, списки) программно проверяется физический зазор:
     - `nextBlock.top - prevBlock.bottom >= 16px` (норматив: 20–24px / `gap: 1.25rem`–`1.5rem`).
     - Категорически запрещено нулевое расстояние (`gap < 12px` или касание), когда лейблы полей или границы нижнего блока прилипают к верхним элементам. Любое слипание блоков признается блокирующим браком.
   - **Phantom CSS & Precompiled Tailwind Verification Gate (Anti-Phantom-CSS Gate):** Категорически запрещено использовать в HTML/JS классы утилит Tailwind (например, `sm:grid-cols-3`, `space-y-3.5`, `grid-cols-6`), не проверив их физическое наличие в `frontend/assets/tailwind.css`. Любая критическая структурная сетка (Grid) и вертикальный ритм (Flex gap) обязаны явно фиксироваться в CSS-правилах `<style>` / компонента, исключая бесшумный сброс браузера в `grid-cols-1` или `gap: 0`.
   - **Silent-Clipping DOM Scanner (No-Hidden-Overflow-Clip Gate):**
     Автоматический программный обход всех контейнеров страницы с `overflow: hidden`, `overflow-y: hidden`, `overflow-x: hidden`. Для каждого контейнера проверяется:
     1. `container.scrollHeight <= container.clientHeight + 1` (контейнер не имеет скрытого переполнения).
     2. Для каждого прямого дочернего элемента: `childRect.bottom <= containerRect.bottom + 1` (дочерний элемент не вылезает за нижнюю кромку родителя).
     Категорически запрещено срезать нижние строки, сервисные плашки или кнопки границей контейнера. Поля ввода `<textarea>` обязаны иметь гибкий адаптивный `min-height` ($\le 90$px) и внутренний скролл, а сервисные плашки под ними (`#import-live-counter`) обязаны иметь `shrink-0` и оставаться на 100% видимыми при любой высоте экрана $\ge 650$px.
   - **Interactive Control-Sweep Gate & Zero-Blind-Spot Click Plan:**
     Категорический запрет на поверхностные аудиты, ограничивающиеся статическими снимками пассивного состояния! Любое модальное окно, мастер или экран обязаны иметь детерминированный сценарий **100% кликового покрытия всех интерактивных элементов**. Каждый интерактивный контрол (`button`, `select`, `input`, `checkbox`, `filter chip`, вторичные модалки `[Детали]`, переключатели исключения) обязан быть программно кликнут, активирован и сфотографирован в открытом/измененном виде.
   - **Top-Layer Stacking Context Integrity Gate (Dialog-in-Dialog Assertion):**
     Любые дочерние диалоги, карточки подробностей (`task-detail-overlay`), поповеры и тултипы, открываемые из нативного `<dialog>` (`dialog.showModal()`), обязаны монтироваться внутрь контейнера самого диалога (`.editor-import-modal-shell` / `#import-modal`), а **не** в `document.body` (где элементы DOM оказываются под Top Layer браузера, становятся невидимыми и блокируются свойством `inert`). Программно проверяется:
     1. `document.elementFromPoint(x, y)` в центре и по 4 углам вторичного оверлея возвращает сам оверлей или его дочерний элемент, а не родительскую модалку;
     2. Нажатие `Escape` обязано перехватываться (`e.stopPropagation()`, `e.preventDefault()`) и закрывать **только** вторичный оверлей, сохраняя родительский диалог открытым без потери данных.
   - **Anti-Duplicate Glyph Assertion:**
     Категорически запрещено дублировать графическую иконку одинаковым текстовым символом в теле одного бейджа или кнопки (например, иконка `<span class="material-symbols-outlined">check_circle</span>` в паре с текстом `✓ Готово` $\rightarrow$ визуальный дефект «две галочки подряд»). Все строковые лейблы обязаны содержать чистый текст без ручных Unicode-глифов (`"Готово"`, `"Ошибка"`, `"Требует внимания"`, `"Конфликт"`).
   - **Dropdown Chevron Clearance Assertion (Anti-Arrow-Overlap Gate):**
     Все выпадающие списки `<select>` обязаны оформляться по дизайн-системе ACTRA: `appearance-none`, кастомный шеврон `expand_more` с `pointer-events-none absolute right-2.5 top-1/2 -translate-y-1/2` и достаточный правый внутренний отступ `pr-8` ($\ge 32$px), полностью гарантирующий, что текст выбранного пункта любой длины не перекроет стрелку селекта.
    - **Subpixel Border & Tab Edge Clearance Assertion (`assertNoClippedBorders`):**
      Для всех интерактивных элементов (вкладки уровней, карточки, слоты, кнопки, поля ввода):
      `childRect.bottom <= parentRect.bottom - parentPaddingBottom + 0.5px`
      `childRect.top >= parentRect.top + parentPaddingTop - 0.5px`
      `childRect.left >= parentRect.left + parentPaddingLeft - 0.5px`
      `childRect.right <= parentRect.right - parentPaddingRight + 0.5px`
      Категорически запрещено срезать внешние границы элементов родительскими контейнерами с `overflow: hidden`. Любое усечение рамки даже на 0.5px признается блокирующим дефектом.
    - **Category Scalability Stress-Matrix ($N \in \{3, 5, 9\}$):**
      Автоматический раннер обязан валидировать интерфейс на стресс-матрице с 3, 5 и 9 категориями:
      1. Отсутствие появления паразитного внутреннего горизонтального скроллбара в боковой панели (`scrollWidth === clientWidth`);
      2. Сохранение минимальной зоны клика кнопки таба ($\ge 40$px) и читаемости текста с адаптивным переносом (`overflow-wrap: anywhere`);
      3. Отсутствие коллизий между соседними плашками категорий при многострочном заворачивании (`seqh-tabs--wrap`).
    - **Dynamic Motion & Layout Transition Gate (`assertSmoothLayoutTransition`):**
      Покадровый инструментальный замер кинетики при динамических мутациях (вставка, удаление, перенос карточек):
      1. Захват не менее 10 промежуточных кадров на протяжении 240ms анимации;
      2. Максимальный скачок высоты между двумя соседними кадрами не должен превышать 20px (полный запрет моментального $0$ms скачка верстки);
      3. Непрерывное следование соединительных линий SVG (`seqh-link`) за границами карточек на каждом кадре анимации;
      4. **Anti-False-Positive Frame Assertion:** Обязательная криптографическая проверка различия хэшей растровых кадров:
         `hash(midFrameScreenshot) !== hash(finalExpandedScreenshot)`. Фиктивный захват одинаковых статичных кадров после финиша анимации блокируется тестом как ложноположительный аудит.
    - **Slot Contrast & Subpixel Dashed Border Continuity Gate (`assertSlotBorderContinuity`):**
      Программная проверка четкости и контрастности пунктирных контуров слотов на всех рядах схемы (1, 2, 3, 4+) при масштабах $100\%$, $80\%$ и $60\%$:
      1. Базовая толщина пунктира обязана составлять $\ge 2$px dashed, предотвращая субпиксельное схлопывание Chromium Skia при зуме;
      2. Контрастность пунктира относительно фоновой полосы уровня (`seqh-band`) обязана удовлетворять WCAG Non-text Contrast ($\ge 3:1$);
      3. Исходная точка SVG-коннекторов обязана иметь клиренс $\ge 2$px от нижней границы родителя, исключая перекрытие пунктира сплошной линией связи.
    - **Strict Anti-Matryoshka Nesting Gate (`assertMaxNestingDepth`):**
      Программный подсчет уровней вложенности рамок от внешней панели до интерактивного контрола. Внутри рабочей карточки (`surface-1`) допустим максимум 1 уровень рамок. Тройные рамки (`surface-1` $\rightarrow$ контур контейнера $\rightarrow$ рамка кнопки) блокируются как грубое нарушение эргономики.
    - **S2 Hierarchy & Assembly Editor Headless Gate Matrix (`reformed_s2_editor_gate.mjs`):**
      Специализированный детерминированный шлюз автоматической верификации редактора последовательностей и иерархий (S2), блокирующий регрессии эргономики холста:
      1. `assertSegmentedControlClearance`: Защита сегментированных переключателей режимов (`#se-display-mode-tabs`, `#se-mode-tabs-pill`). Замер: `pill.right <= container.right - paddingRight` и `overflow: hidden; box-sizing: border-box;` (0px усечение и вылезание активных вкладок за границу контейнера);
      2. `assertNoFooterButtonOverflow`: Защита карточек узлов (`.se-node-card`) от выдавливания экшенов. Для всех кнопок карточек: `button.left >= card.left + paddingLeft - 0.5px` и `button.right <= card.right - paddingRight + 0.5px` (0px выталкивание кнопок «+ Элемент» влево в межколоночный зазор);
      3. `assertUndoRedoTextIntegrity`: Целостность стека `UndoManager` при вводе текста. Ввод названий элементов/узлов обязан сохраняться в историю (debounced 400ms и немедленный flush перед мутациями/blur). Нажатие `Ctrl+Z` обязано откатывать добавленные узлы без потери введённых текстовых названий оставшихся элементов;
      4. `assertEmptySlotValidationHighlighter`: Информативный контекст валидации при сохранении с пустыми элементами/гнездами. Запрет абстрактных тостов. Обязательна подсветка проблемной карточки (`.se-node-card--error`), поля (`.se-field--error`), запуск кинетического шейка (`.se-shake`), автоматический центрирующий скролл к первому проблемному элементу, автофокус и мгновенный сброс ошибки при начале набора;
      5. `assertPrecisionZoomSlider`: Двусторонняя непрерывная синхронизация аналогового слайдера масштабирования (`#se-zoom-slider`). Изменение слайдера обязано трансформировать холст `scale(...)` и метку сброса, а клики по дискретным кнопкам зума `[+]` / `[-]` или зум колесом обязаны синхронно смещать бегунок слайдера;
      6. `assertKineticTransitions`: Плавные переходы добавления/удаления элементов (`.se-node-item-row--entering` / `.se-node-item-row--exiting`) без полного сброса и моргания холста, синхронизированные с пересчетом SVG-путей связей (`trackConnectorAnimation`) через 60fps RAF loop;
      7. `assertColorDifferentiationPermanent`: Перманентная цветовая дифференциация узлов по уровням (`data-color-tint`) при полном удалении рудиментарного переключателя-чекбокса из DOM и модели редактора.
    - **Anti-Vacuous-Pass & Selector Existence Gate (`assertNonEmptySelection`):**
      Любой цикл проверки геометрии, коллизий, видимости или наложений в Playwright обязан начинаться с явного ассерта ненулевого количества целевых узлов (`if (elements.length < expectedMin) throw new Error(...)`). Тест, в котором селектор вернул 0 элементов и цикл проверок выполнился 0 раз, категорически запрещено признавать успешным (PASS) — это признаётся грубейшим дефектом фиктивного тестирования («пустая истина»). Дополнительно: при внедрении любого условного CSS-правила (по `data-*` атрибутам или классам) обязательна программная валидация `document.querySelectorAll(selector).length > 0` в целевом состоянии в браузере.
    - **Internal SVG BBox & Cross-Locale Collision Gate (`assertSvgInternalGeometry`):**
      Для всех встроенных SVG-иллюстраций, миниатюр и схем во всех поддерживаемых локалях (`ru`, `en`, `uk`) детерминированно проверяется внутренняя геометрия через `SVGGraphicsElement.getBBox()`:
      1. *Text-in-Box Containment:* Для любого `<text>`, расположенного внутри плашки/карточки `<rect>`, обязательны условия `textBBox.x >= rectBBox.x + 2` и `textBBox.x + textBBox.width <= rectBBox.x + rectBBox.width - 2`, исключающие протыкание или касание границ карточек текстом и значками `✓`.
      2. *Sibling No-Overlap:* Ни один текстовый элемент `<text>` не имеет права пересекаться по `getBBox()` с соседними `<text>`, бейджами `<rect>` или маркерами `<circle>` (зазор $\ge 4$px).
    - **Scrollport Safety Margin Assertion (`assertScrollportSafetyMargin`):**
      Для любых интерактивных элементов внутри контейнеров со скроллом (`overflow-y: auto`, `overflow-x: hidden`, `overflow: auto`) программно валидируется минимальный зазор до границы скроллпорта:
      `childRect.left - containerRect.left >= 4px` и `containerRect.right - childRect.right >= 4px`.
      Если отступ $< 4$px, тест падает автоматически. Это гарантирует, что границы `border`, фокус-кольца (`outline`) и внешние тени `box-shadow` (1–2px) никогда не будут срезаны вертикальной плоскостью отсечения скроллпорта.
    - **Corner Radius Curvature Integrity Assertion (`assertCornerCurvatureIntegrity`):**
      Для элементов со скруглёнными углами (`border-radius > 0`) программно валидируется отсутствие вертикального или горизонтального среза границ: в углах элемента пиксели границы обязаны формировать плавную дугу (монотонное изменение координаты $x$ по $y$). Если фиксируется прямой вертикальный срез ($x = \text{const}$ на высоте $> 2$px в зоне скругления) — фиксируется дефект обрезания границы скроллпортом.
    - **Parent Corner Boundary Containment (`assertParentCornerContainment`):**
      Дочерний элемент обязан полностью укладываться в зону до начала скругления родителя:
      `childRect.right <= parentRect.right - (parentBorderRadius * 0.4)` и `childRect.left >= parentRect.left + (parentBorderRadius * 0.4)`.
      Категорически запрещено вытеснять дочерние плашки в зону радиуса скругления родителя.
    - **DOM Zero-Ghost Gate (Полное уничтожение vs Сокрытие):**
      Если контрол/плашка признаётся избыточной или удаляется из интерфейса, запрещено оставлять её в DOM и маскировать через CSS `display: none`. Она обязана быть полностью удалена из HTML-шаблона и JS-генератора. Линтер проверяет отсутствие элементов-призраков с нулевыми габаритами в рабочей области.
    - **Strict System Theme Matrix (`light-a` & `dark-a` Default Parity):**
      Тестовая матрица Playwright обязана тестировать именно системную тему по умолчанию `light-a` (Contrast, фиолетовый акцент), а не только `light-b` (песочную).
    - **Clinical & Didactic Realism Scanner (`assertNoGamificationSlop`):**
      Детерминированный регексп-сканер всех текстовых нод в превью и модалках на запрет синтетических геймификационных AI-клише: `«Точность 100%»`, `«Score»`, `«Level N»`, `«Correct 100%»`, `«Вы набрали N очков»`. Все учебные превью обязаны формулироваться исключительно в терминах предметной области (медицина, биология, физика).
    - **Shared Lifecycle & Bidirectional State Transition Gate:**
      1. *Call-Site Impact Audit:* Перед модификацией базовых методов жизненного цикла (`closeModals`, `renderSidebar`, `sync*`) агент обязан через полнотекстовый поиск найти все места их вызова и строго разделить сценарий *пользовательского действия* (`userInitiated: true`) и *программного сброса состояния* (`programmaticReset`). Запрещено внедрять деструктивные сайд-эффекты (например, завершение тура или сброс несохранённых данных) в общие методы без явного флага контекста вызова.
      2. *Bidirectional Transition Gate:* Любой скрипт верификации пошагового мастера или онбординг-тура обязан валидировать не только прямой переход, но и полный двунаправленный цикл переходов: `Шаг 1 → ... → Шаг N → Назад (Шаг N-1) → Далее (Шаг N) → Закрытие [×]`.
    - **No-Cloned-Implementation Gate:**
      Категорически запрещено копировать или заново объявлять тестируемые функции/методы фронтенда внутри `beforeEach` или тела тестового файла (`*.test.mjs`). Юнит- и интеграционные тесты обязаны импортировать и вызывать реальный производственный код из каталогов `frontend/`.
3. **Обязательный матричный охват состояний (Dynamic States Matrix):**
   Запрещено инспектировать только пассивное состояние покоя (`idle`). Проверка обязана включать:
   - `idle` (чистое состояние покоя);
   - `focused / active` (активный ввод в самом длинном/нагруженном блоке данных с включённым фокус-кольцом);
   - `dirty / unsaved` (состояние несохранённых изменений с широкими предупреждающими бейджами);
   - **`heavy-stress-payload` («Стена текста» & Extreme Capacity):** Запрещено ограничиваться скромными 4 строками! Обязательна заливка реальной «Стены текста» $\ge 1500$–$2500$ символов (15–20 параграфов) и длинных неразрывных строк $\ge 80$ символов. Проверяется наличие адаптивного потолка высоты (`max-height: min(...)`), отсутствие растяжения на 2000px и плавный внутренний скролл.
   - **`worst-case-geometry` (Экстремальные пространственные координаты):** Тестирование интерактивных состояний на самых неблагоприятных пространственных позициях:
     - самый нижний элемент нижнего уровня у границы подвала страницы;
     - крайний правый элемент у сайдбара;
     - элемент непосредственно под sticky-шапкой.
4. **Прокурорская деконструкция по 9 смертным грехам верстки:** Агент обязан посмотреть на скриншот глазами стороннего придирчивого критика и выписать найденные дефекты по чек-листу ниже. Запрещены общие фразы вроде «интерфейс в целом выглядит хорошо».
5. **Adversarial Quota (Принцип «Адвоката дьявола»):**
   Промпты для субагентов-аудиторов обязаны требовать нахождения **не менее 3 конкретных дефектов верстки** (с селекторами, координатами и замерами). Отчёты с формулировками «всё выглядит отлично, дефектов не найдено» признаются поверхностными и автоматически бракуются.
6. **Best-of-N архитектурный выбор:** Предложить 2–3 альтернативных компоновочных решения, опираясь на скиллы (`universal-design-principles`, `anti-ui-slop`, `checklist-design`), аргументировать выбор сильнейшего.
7. **Контрольный снимок До / После:** Реализовать изменения, снять проверочный скриншот, просмотреть его через `view_file` и встроить в финальный отчет.

#### 2. Шлюз проверки: 9 смертных грехов верстки (Cold-Eye Checklist)
Перед завершением любой UI-задачи агент обязан проинспектировать реальный рендер по 9 критериям:
1. **«Дыры и сироты» (Void & Orphan Gate):** 
   - Запрещен неконтролируемый `flex-wrap` для разнородных бейджей, образующий рваный правый край и пустоту на последней строке.
   - Сетка обязана быть либо строгой табличной (`grid grid-cols-2`), либо центрированной, либо широкие элементы обязаны явно растягиваться на всю ширину (`col-span-2`).
2. **«Раздутые карточки и висячие кнопки» (Balloon Cards & Proximity Violation Gate):**
   - Запрещено использовать жесткое растяжение сетки (`items-stretch`) в сочетании с `justify-between`, если элементы в ряду содержат разное количество строк. Это приводит к раздуванию карточек с коротким текстом огромной белой пустотой (дырой) и отрыву кнопок навигации от текста на 50–100px.
   - **Закон близости Гештальта (Gestalt Proximity):** Элементы управления обязаны физически прилегать к контенту, которым они управляют. Контейнеры должны обнимать свой контент (`height: fit-content` / `items-start`), либо кнопки управления должны выноситься в шапку карточки, либо пустота должна поглощаться активным полем ввода, а не мёртвой зоной.
3. **«Слоёный пирог / Кладбище плашек» (Pill Pileup Gate):**
   - Запрещено нагромождать несколько слоев мелких плашек подряд (например, ряд кнопок над рядом бейджей над полем).
   - Более 1 ряда разнородных плашек подряд запрещено — переводить во вложенный/единый селектор, аккордеон или структурированную таблицу.
4. **«Асимметрия колонок» (Column Mismatch Gate):**
   - Запрещен разнобой, когда в одной колонке подряд идут блоки с разным делением ширины (например, сверху 3 колонки, под ним 2, под ним 4). Все блоки обязаны подчиняться единой визуальной сетке.
5. **«Серая каша и потеря аффорданса» (Muddy Surface & Ghost Controls):**
   - Интерактивные элементы обязаны иметь явный физический аффорданс (собственную светлую подложку `surface-1`, субтильную границу `border-border-subtle`, hover-состояние и тень).
   - Запрещено бросать голый текст кнопок на серый фон (`surface-2`), превращая интерфейс в некликабельную «серую кашу».
   - Запрещены вложенные серые коробки (`surface-2` внутри `surface-2`).
6. **«Обрезки и многоточия» (Zero Truncation Gate):**
   - Запрещены паразитные многоточия (`...`) в заголовках, табах, кнопках, счетчиках и статусах на десктопных разрешениях $\ge 1280$px.
   - Длинные слова (например, «Последовательность», «Открытый ответ») обязаны либо иметь достаточную фиксированную ширину, либо выноситься в контролы полной ширины.
   - Запрещено перегружать шапку статическими префиксами («Редактирование: ...»), ворующими полезную ширину у названия документа.
7. **«Конфликт шапки» (Header Collision Gate):**
   - Заголовок панели и вспомогательные контролы/бейджи не должны бороться за ширину в одной строке, вызывая сжатие текста. При риске коллизии контрол переносится на отдельную строку или компактно реорганизуется.
8. **«Иерархия весов» (Visual Hierarchy Gate):**
   - Основная рабочая зона пользователя (например, поле ввода редактора) обязана визуально доминировать по площади, контрасту и размеру первичного CTA над вспомогательными панелями и памятками.
9. **«Слепые оверлеи и срезанные контролы» (Blind Overlay & Occluded Dismiss Gate):**
   - **Запрет на перекрытие контекстом наложения:** Любой раскрывающийся оверлей обязан возвышать весь свой путь в дереве (`z-index: 40/45/50` на уровень, слот-враппер и саму карточку), чтобы нижележащие уровни и карточки никогда не срезали его своим непрозрачным фоном.
   - **Заповедь безусловной видимости выхода:** Кнопка сворачивания/закрытия обязана быть доступна моментально. Если элемент раскрывается вниз у границы экрана, обязателен плавный автоскролл в зону видимости, либо дублирующий контрол сворачивания в шапке элемента.
   - **Запрет на бесконечный вылет (Adaptive Capping):** Любой раскрывающийся блок обязан иметь потолок `max-height: min(16rem, 36vh)` с внутренним скроллом, чтобы карточка физически не могла перерасти треть экрана.

#### 3. Паритет статической разметки и гидратации (Zero Hydration Lag Gate)
- Текстовые строки в исходных HTML-файлах (шаблонах до запуска JavaScript) обязаны быть на 100% синхронизированы с текущими словарями `ru.json`, `en.json`, `uk.json`.
- Категорически запрещено оставлять в HTML устаревшие термины или заглушки, рассчитывая, что скрипт локализации перезапишет их в рантайме. При любых задержках сети или ошибках гидратации интерфейс обязан оставаться терминологически безупречным.

#### 4. Канон адаптивной геометрии модальных окон (Step-Aware Modal Geometry Canon)
- **Запрет на монолитный жесткий каркас модалки:** Категорически запрещено задавать единый фиксированный размер (`width: min(94vw, 76rem); height: min(90vh, 56rem);`) для всего модального окна без учета текущего шага и объема данных.
- **Двухрежимная адаптивность (Dialog vs. Studio):**
  - *Шаги выбора, онбординга и подтверждения (Диалоговый режим / Step 1 & Confirm):* Обязаны облегать свой контент (`width: min(92vw, 48rem); height: auto; max-height: min(88vh, 44rem);`), контентная зона `flex: 0 1 auto`. Окно аккуратно центрируется по вертикали, футер прилегает к контенту без пустот, вертикальный скроллбар строго запрещен (`hasVerticalScroll === False`).
  - *Шаги авторской работы, редактора и предпросмотра (Студийный режим / Step 2 & 3):* Расширяются в полноразмерную студию (`width: min(94vw, 76rem); height: min(90vh, 56rem);`), контентная зона `flex: 1 1 0%` со скроллом только внутри специализированных панелей (текст, шпаргалка, сетка карточек).
  - *Синхронизация через data-current-step:* Корневой элемент `<dialog>` или `.modal-shell` обязан поддерживать атрибут `data-current-step="${step}"`, управляющий размерами и плавным переходом `transition: width 0.25s, max-height 0.25s`.
- **Заповедь четкой гештальт-группировки секций:** Каждый обособленный функциональный блок внутри шага обязан иметь секционный заголовок (`text-xs font-bold uppercase tracking-wider text-text-secondary`) или явный визуальный разделитель. Запрещено бросать поля ввода без смыслового якоря (например, переход от выбора формата к выбору модуля без заголовка «ЦЕЛЕВОЙ РАЗДЕЛ»).

### 11. Протокол независимого мультиролевого аудита (Multi-Role Subagent Panel Protocol)
Для исключения когнитивных искажений разработчика («у меня всё работает», замыливание взгляда), дежурного формализма и туннельного зрения по чек-листам любой аудит сложного интерфейса в ACTRA **обязан проводиться независимой панелью субагентов по 4 ролям (Триада специалистов + 1 Свободный критик без рельс)** с жестким пятифазным регламентом.

#### 1. Коллегия аудиторов (The Audit Panel: 3 Specialists + 1 Wildcard)
Каждый субагент запускается изолированно (`invoke_subagent`), наделяется уникальным мировоззрением и оценивает интерфейс через призму своего профиля и **7 фундаментальных законов восприятия первого порядка (Macro-Perceptual Invariants)**:

##### Базис мышления: 7 фундаментальных законов восприятия (The 7 Macro-Perceptual Invariants)
Перед оценкой любого экрана каждый аудитор обязан пропустить увиденное через 7 фильтров первого порядка:
1. **Закон смысло-пространственной эквивалентности («Налог на мертвую площадь» / Dead Surface Tax):**  
   Каждый вертикальный пиксель в первичной рабочей зоне обязан оправдывать своё существование плотностью смысла. Если на экране появляется полоса/панель на всю ширину (или высотой $\ge 36$px), содержащая лишь одно пассивное предложение или пару радиокнопок — это грубый архитектурный порок. Контрол обязан быть интегрирован в существующий тулбар, заголовок или статусную строку, не отбирая воздух у рабочей сцены.
2. **Закон активного светового окна (Active Frustum Optical Centering):**  
   Оптический центр и баланс массы оцениваются исключительно внутри *чистого светового просвета* (Frustum = Viewport minus active Drawers/Sidebars), а не по физическим границам экрана. Если при открытой боковой панели контент центрируется относительно всего монитора, он выглядит как сбитый в бок груз. Холст обязан центрироваться по центру *оставшейся свободной видимой зоны*.
3. **Закон сохранения пространственной траектории и поводка объекта (Spatial Anchor Leash & Object Permanence):**  
   В физическом мире объект оставляет след там, куда он скрылся. Метафора шторки требует сохранения точки привязки на той границе, куда она свернулась. Категорически запрещена телепортация контролов: если панель сворачивается вправо — её ручка (тонкий вертикальный рейл/закладка) обязана оставаться у правого края на всю высоту. Кнопка возврата не имеет права перелетать в верхний тулбар на противоположный конец экрана, вызывая мышечный и саккадический дискомфорт глаз.
4. **Закон целостности физического субстрата (Common Substrate / Gestalt Unified Body):**  
   Таблица, матрица или иерархия — это единый физический лист бумаги (Common Fate). Заголовки строк/уровней не могут быть оторванными аппликациями с обрезанными краями, висящими отдельно от ячеек. Они обязаны быть полноправной Колонкой 1 единой координатной сетки, иметь общую фоновую линию со своей строкой и масштабироваться/перемещаться в одной связке с содержимым.
5. **Принцип достоинства контента vs «Прокрустово ложе» (Content-Driven Geometry vs Procrustean Rigidity):**  
   Контейнер служит контенту, а не контент уродуется ради слепой одинаковости коробок. Если в карточке текст диагноза или статусная плашка разрывается на несколько строк при наличии океана пустого места вокруг — это дефект догматической верстки («прокрустово ложе»). Ширина узлов должна динамически адаптироваться под семантический объём текста.
6. **Закон знаковой дифференциации и стресс-тест масштабирования (Semiotic Disambiguation & Scalability Stress-Test):**  
   Знаки разной смысловой природы, стоящие рядом, обязаны принадлежать разным знаковым системам (например, римские цифры для уровней и арабские для счётчиков количества). Соседство двух одинаковых цифр (`Ур. 1 (1)`) создаёт визуальную кашу и заставляет мозг спотыкаться. Кроме того, любой компонент группировки (табы, фильтры, теги) обязан мысленно тестироваться на масштабирование: что произойдёт при $N = 6, 8, 12$? Имеет ли он встроенную изоляцию переполнения (overflow scroll) или взорвёт верстку?
7. **Принцип органической интеграции контрола vs «Прилепленный стикер» (Organic Surface Integration vs Grafted Widget):**  
   Кнопка или триггер раскрытия обязаны вырастать из самой поверхности и типографики блока, а не выглядеть чужеродной пластмассовой кнопкой, приклеенной сбоку на двусторонний скотч. Контрол аккордеона `[Развернуть ▾]` не должен спорить с текстом превью, выпадать из ритма рамки или выглядеть отдельной сиротливой капсулой.

##### Ролевая специализация Коллегии

> [!IMPORTANT]
> **Фундаментальная аксиома целевой аудитории проекта ACTRA (Core Target Audience Mandate):**
> В реалиях проекта задания создают в абсолютном большинстве **обычные школьники, ученики и студенты**, у которых есть стремление саморазвиваться и большой объём учебной литературы (книги, конспекты, статьи, атласы, методички), который они превращают в интерактивные задания, чтобы самостоятельно выучить и запомнить материал (создатель проекта сам является одним из таких учеников). Практикующие врачи и преподаватели входят в аудиторию, но **первичный фокус продукта — самообучающийся ученик/студент**.
> **Следствия для UI, текстов, примеров и аудита:**
> 1. Запрещено замыкать примеры, иллюстрации и описания в интерфейсе на узкоспециализированный врачебный жаргон (`BI-RADS 4B`, `PI-RADS v2.1`, `RECIST 1.1`, `Couinaud`), который отпугивает или сбивает с толку обычного школьника/студента.
> 2. Все обучающие превью, подсказки и шаблоны обязаны быть универсально понятными любому учащемуся, работающему со своими учебниками и конспектами (схемы, таблицы классификаций, определения, поиск ошибок в формулировках, последовательность процессов).

1. **Роль 1: Самообучающийся ученик / студент и начинающий автор (Self-Directed Student & First-Time Learner-Author)**
   - **Профиль:** Обычный школьник, ученик или студент (а также преподаватель без технического бэкграунда), который открыл платформу, чтобы превратить главу учебника, конспект, схему или статью в серию заданий для запоминания и самопроверки. Не терпит заумного сленга, перегруженных аббревиатур и несоответствия превью реальному редактору.
   - **Специализированные фильтры мышления:**
     - **Понятность для перевода книги в задание:** Сразу ли понятно, какой тип и подтип выбрать, чтобы выучить конкретный кусок литературы (таблицу, схему из учебника, определение, цепочку событий или типичные ловушки в формулировках)?
     - **Знаковая дифференциация:** Не смешиваются ли порядковые номера и количества в бейджах (`I (2)` vs `Ур. 1 (1)`)? Не вызывает ли это замешательства у ученика?
     - **Пространственная ориентация и потерянные контролы:** Понятно ли, куда исчезли настройки при закрытии шторки? Интуитивно ли их возвращение?
     - **Защита от потери данных (DLP):** Наличие подтверждений при очистке и четкий статус несохраненных правок.

2. **Роль 2: Опытный создатель учебных комплексов / Методист самообучения (Power Learner-Author, Didactics & Ergonomics)**
   - **Профиль:** Продвинутый студент или автор курсов, который перерабатывает целые книги и большие темы в десятки заданий и ценит скорость сборки, честность инструментов и дидактическую эффективность.
   - **Специализированные фильтры мышления:**
     - **Смысло-пространственная эквивалентность (Налог на мертвую площадь):** Не съедает ли экран драгоценную высоту ради одиночных строк с фидбеком проверки? Достаточно ли видна рабочая схема на стандартном экране ноутбука?
     - **Стресс-тест масштабирования (N = 3, 5, 9):** Как поведёт себя панель доступных элементов и матрица, если в классификации из учебника 5 или 9 категорий? Не возникнет ли паразитных горизонтальных скроллбаров или обрезанных табов? Переходят ли табы в компактный wrap-режим?
     - **Достоинство контента:** Помещаются ли развернутые формулировки из учебников и статусы («Порядок изменен») без нелепого дробления на 2–3 строки?

3. **Роль 3: Строгий визуальный критик и хранитель дизайн-системы (Cold-Eye Visual & Design System Guardian)**
   - **Профиль:** Беспристрастный внешний архитектор интерфейсов (уровня Google AI Studio / Linear / Figma). Презумпция скрытых пороков верстки.
   - **Специализированные фильтры мышления:**
     - **Активное световое окно (Active Frustum):** Проверка строгого оптического центрирования холста в реальном просвете между боковыми шторками.
     - **Целостность субстрата (Common Substrate):** Отсутствие обрезанных краев у свимлейнов и уровней; строгая принадлежность Колонки 1 к единой координатной сетке.
     - **Органическая интеграция контролов:** Отсутствие «прилепленных стикеров» и чужеродных плашек-капсул в аккордеонах и шапках.
     - **18 детерминированных шлюзов:** Проверка `:focus-visible`, `elementFromPoint`, темной темы, anti-matryoshka (строгий лимит вложенности рамок ≤ 1), subpixel border clearance, smooth layout transition (кинетика без рывков > 20px) и WCAG AA.

4. **Роль 4: Непредвзятый живой критик / Свободный глаз (The Wildcard / Zero-Rails Gut-Check Reviewer)**
   - **Профиль:** Живой человек с острым визуальным чутьем и здоровым скепсисом. Полный антипод формалиста по чек-листам. Ему плевать на селекторы, пиксели и оправдания разработчиков.
   - **Входные данные:** **Исключительно** общие скриншоты страниц целиком. Запрещены подсказки, микрокропы и технические замеры.
   - **Динамический телеологический контракт (JTBD Context):**
     На Фазе 1 формируется **Телеологический паспорт экрана (JTBD Passport)**: `TARGET_PERSONA`, `PRIMARY_JTBD`, `USAGE_CONTEXT`.
   - **Динамический шаблон инструкции для субагента (The 7 First-Principles Gestalt Lenses):**
     > «Перед тобой скриншот интерфейса.  
     > **Контекст экрана:**  
     > - **Пользователь:** ${TARGET_PERSONA}  
     > - **Его главная цель на этом экране (JTBD):** ${PRIMARY_JTBD}  
     > - **Среда / сценарий:** ${USAGE_CONTEXT}  
     > 
     > Забудь про CSS, технические селекторы и формальные чек-листы. Оцени экраны целиком через 7 макроскопических оптических фильтров первого порядка (First-Principles Gestalt Lenses):  
     > 
     > 1. **Активное световое окно и центр тяжести (Active Frustum Centering):**  
     >    Оценивай оптический центр сцены ТОЛЬКО в чистом видимом просвете (без учета открытых боковых шторок). Не смещен ли чертёж вправо или влево? Лежит ли он по центру оставшегося листа?  
     > 2. **Налог на мертвую площадь (Dead Surface Tax):**  
     >    Оправдывает ли каждый горизонтальный этаж экрана свою высоту? Нет ли огромной полосы на 50px, выделенной ради одной банальной строчки текста или пары кнопок?  
     > 3. **Пространственный поводок и сохранение объекта (Spatial Leash & Object Permanence):**  
     >    Если шторка/панель свернулась вправо — осталась ли её ручка на правом краю? Не заставляет ли интерфейс мои глаза прыгать в противоположный угол экрана (в шапку), чтобы вернуть то, что только что исчезло справа?  
     > 4. **Целостность чертёжного полотна (Common Substrate):**  
     >    Выглядит ли матрица как единая чертёжная таблица на одном ватмане? Или заголовки уровней кажутся обрезанными аппликациями с висящими краями, живущими отдельной жизнью от карточек?  
     > 5. **Достоинство контента vs Прокрустово ложе (Content-Driven Geometry):**  
     >    Не зажаты ли слова в узкие коробочки ради слепой одинаковости? Не ломаются ли надписи и статусы на 2 строки там, где вокруг разлито море свободного места?  
     > 6. **Тест расфокусировки и знаковая дифференциация (Squint Test & Numeric Clash):**  
     >    Если прищуриться: различимы ли сущности по силуэту? Не слипаются ли рядом одинаковые знаки (цифра рядом с цифрой `1 (1)`, иконка со стрелкой)? Что будет, если элементов станет в 2 раза больше?  
     > 7. **Ритм живой речи и органичность деталей (Read-Aloud Cadence & Organic Controls):**  
     >    Прочти все надписи вслух. Звучит ли это естественно? Вырастают ли кнопки раскрытия из самой строки, или выглядят как чужеродные стикеры, прилепленные программистом сбоку?  
     > 
     > > 8. **Кинетическое спокойствие и физика движения (Kinetic Stability & Fluid Motion):**  
     >    Вставь карточку в гнездо и удали её. Вздрагивает ли экран? Не скачет ли высота уровня рывком (0ms snap), от которого рябит в глазах? Движутся ли линии связи непрерывно вместе с карточкой, или прыгают с отрывом?  
     > 
     > Пиши прямо, бескомпромиссно, своими словами. Что здесь ощущается органично, а что выглядит нелепо, глупо, искусственно или вызывает раздражение у живого человека?»
   - **Строгий запрет (Anti-Railroad Mandate):** Категорически запрещено навязывать агенту списки типов ошибок. Единственная адаптация — телеологический паспорт (Кто, Зачем, В каких условиях).

#### 2. Пятифазный регламент исполнения (Phased Audit Pipeline)
Любой аудит интерфейса выполняется строго по 5 фазам:

- **Фаза 1: Инвентаризация интерактивных элементов и сценарное моделирование (Control Tree Inventory & Scenario Design)**
  - **Телеологический паспорт экрана (JTBD Passport):** Главный агент обязан явно зафиксировать триаду смыслов экрана: `TARGET_PERSONA`, `PRIMARY_JTBD` и `USAGE_CONTEXT` (для динамической передачи в Роль 4 на Фазе 3).
  - **Запрет на слепой захват без сценариев:** До написания любого тестового скрипта и захвата скриншотов агент обязан провести структурную инвентаризацию интерфейса по разметке/коду и зафиксировать полный перечень доступных элементов:
    - Все кнопки (первичные, вторичные, контекстные, закрытие, очистка, исключение, модальные вызовы `[Детали]`);
    - Все поля ввода, выпадающие списки (`<select>`), чекбоксы, радиокнопки, переключатели;
    - Все вкладки, фильтр-чипы, аккордеоны, раскрывающиеся меню, пагинаторы, зоны скролла;
    - Все пограничные и деструктивные состояния (потеря несохранённых данных при выходе, ошибки парсинга, пустые состояния).
  - **Построение матрицы сквозных сценариев (100% Control Coverage):**
    На базе инвентаризации проектируются сквозные пользовательские сценарии, гарантирующие, что **каждый интерактивный элемент активируется, кликается и проверяется в открытом/измененном виде**:
    1. *Сценарий чистого состояния (`idle / blank`):* Первое открытие, начальные селекты, плейсхолдеры;
    2. *Сценарий первичного заполнения и набора данных:* Ввод, автосохранение, изменение полей;
    3. *Сценарий стресс-нагрузки (`heavy-stress-payload`):* «Стена текста» $\ge 1500$–$2500$ символов, 15–20 параграфов, длинные неразрывные строки, предельное количество карточек;
    4. *Сценарий интерактивных ветвлений и вторичных контролов:* Клик по каждому селекту (политики конфликтов, фильтры типов), клик по кнопкам `[Детали]` (проверка открытия вторичных модалок поверх родительской в Top Layer), клик по чипам фильтрации и кнопкам ручного исключения/включения;
    5. *Сценарий отмены и защиты от потери данных (`DLP`):* Нажатие `Escape` (изоляция закрытия вторичного диалога без сброса родительского), клик по крестику и мимо модалки с несохранёнными данными.

- **Фаза 2: Исполнение сценариев и генерация инструментальной матрицы снимков (Playwright Scenario Execution & Capture)**
  - Поднятие локального окружения (`.\start-dev.ps1` / порт 8000, 5433).
  - Программный запуск спроектированных в Фазе 1 сценариев через Playwright в двух обязательных разрешениях: базовом **1280×800** и компактном **1280×720** (или 1280×680):
    - Снимки всех экранов, шагов и активированных состояний (открытые селекты, активные поля в фокусе, открытые вторичные диалоги `[Детали]`, отфильтрованные списки, предупреждения);
    - Нарезка micro-crops зон повышенного риска (`crop_footer_boundary.png`, `crop_inter_section_rhythm.png`, `crop_focus_ring.png`, `crop_conflict_select.png`, `crop_status_badge.png`);
    - Детерминированный прогон Headless Assertions Gate (Silent-Clipping DOM Scanner, Zero-Truncation, Top-Layer Stacking `elementFromPoint`, Chevron Clearance, Anti-Duplicate Glyph).

- **Фаза 3: Открытая ролевая ревизия субагентами без «рельс» (Autonomous, Unconstrained Role-Based Evaluation)**
  - Запуск независимых субагентов через `invoke_subagent` по Коллегии из 4 ролей (Преподаватель-новичок, Методист/Эргономист, Визуальный критик, Свободный критик без рельс).
  - Роль 4 запускается с динамически подставленным Телеологическим паспортом экрана (JTBD Passport), сформированным на Фазе 1.
  - **Категорический запрет на «рельсы» и искусственные шоры (Anti-Tunnel-Vision):**
    Запрещено сужать кругозор субагента директивами вроде *«Смотри только на фокус-кольцо инпута»* или *«Проверь только нижнюю рамку поля и игнорируй остальное»*. Субагент получает **полный комплект скриншотов всех состояний сценария** и оценивает интерфейс целостно, обладая свободой формулировать любые замечания со своей профессиональной колокольни:
    - *Преподаватель-новичок:* Открыто критикует двусмысленности, непонятный жаргон, запутанную логику шагов, страх потери данных, неочевидность кнопок и действий.
    - *Методист/Эргономист:* Анализирует полноту методических данных на карточках, удобство массовой вычитки, прозрачность логики автоприсвоения названий, читаемость длинных диагнозов, дидактическую непротиворечивость.
    - *Визуальный критик:* Оценивает визуальную чистоту всего макета, композицию, ритм, шрифты, контрастность в светлой и тёмной темах, огрехи выравнивания.
    - *Свободный критик (Wildcard):* Оценивает только общие планы экрана целиком через призму JTBD без чек-листов и без классификаций; выписывает разговорным языком всё, что выглядит нелепо, глупо, чужеродно или является смысловым мусором.
  - **Обязательный тест слепого распознавания схем и иллюстраций (Blind Recognition Test):**
    Субагент обязан ответить: *«Если скрыть текстовые подписи и оставить только SVG/рисунок, однозначно ли распознаётся изображённый объект (кость, сустав, клетка, прибор, орган) профильным специалистом/учащимся? Если изображение выглядит как абстрактный набор геометрических фигур, тёмная балка или синтетическая заглушка — выставить BLOCKER с требованием предметной перерисовки.»*
  - **Инспекция микро-кропов стыков в системной теме `light-a` (200% Zoom Clearance):**
    Субагент обязан открыть микро-кропы всех 4 углов и внешних границ активных элементов в системной светлой теме `light-a` при 200% зуме и убедиться, что зазор до края контейнера составляет не менее 4px, а скругление углов симметрично и не обрезано прямой линией.
  - **Adversarial Quota:** Каждый субагент обязан предоставить не менее 3 конкретных дефектов / точек трения с точными указаниями экранов, селекторов (или зон экрана) и аргументацией. Дежурные похвалы («всё выглядит отлично») строго запрещены.
  - Субагенты работают исключительно с реальными артефактами через `view_file` и кодом.

- **Фаза 4: Единый накопительный реестр замечаний (`audit_findings_registry.md`)**
  - Главный агент агрегирует выводы коллегии (всех 4 рецензентов) в единый артефакт в директории conversation: `audit_findings_registry.md`.
  - Структура записи обязана включать верификационное доказательство:
    `| ID | Роль-источник | Компонент / Экран | Описание дефекта | Критичность (Blocker/Major/Minor/Nitpick) | Инженерное решение | Доказательство (`git diff` file:lines + Test ID) | Статус |`
  - **Zero-Diff Resolution Ban:** Категорически запрещено переводить дефект в статус `ИСПРАВЛЕНО / PASS` на словах («подтверждена поддержка в коде»). Если субагент зафиксировал отсутствие обработки в файле `X.js`, статус `ИСПРАВЛЕНО` разрешён **исключительно** при наличии реального `git diff` в файле `X.js` и автоматического теста, проверяющего эту ветку.

- **Фаза 5: Пакетированная инженерная реализация и контрольный шлюз (Remediation & Post-Fix Gate)**
  - Дефекты разбиваются на логические пакеты (CSS-геометрия, JS-логика/безопасность, локализация, UX-копирайтинг).
  - Правки внедряются последовательно.
  - Повторный запуск скрипта сценариев и генерация снимков До / После.
  - **Mandatory Subagent Re-Verification & Visual Sign-Off:**
    Главный агент **не имеет права** единолично закрывать дефекты. Для подтверждения закрытия обязательны:
    1. Прямой вызов `read_file` на каждом перегенерированном PNG-кропе изменённого компонента (запрещено полагаться только на числовые ассерты Playwright);
    2. Отправка (`send_message`) обновлённых скриншотов и `git diff` профильным субагентам коллегии (Роль 3 — для SVG и визуала, Роль 4 — для интерактивных сценариев и туров) для подтверждения закрытия дефекта (Adversarial Post-Fix Review).
  - Автоматические тесты: прогон Vitest (`npm test`), шлюз локализации (`scripts/audit_i18n_leaks.py --ci`), детерминированный матричный аудит.
  - Перевод всех пунктов реестра в статус `[FIXED / RESOLVED]` с заполнением колонки доказательств.

### 11. Телеологический продуктовый аудит и First-Principles мышление (JTBD & Teleological First-Principles Gate)

Агент и любые субагенты, привлекаемые к оценке, проектированию или аудиту интерфейсов в проекте ACTRA, **категорически обязаны начинать ревизию с первых принципов (First Principles) и целеполагания (Jobs To Be Done)**, а не с локальной косметической полировки.

#### 1. Запрет на «рабство существующего макета» (No Sacred Cows & Escape Local Optima)
- **Ловушка локального оптимума:** Традиционные аудиторы принимают структуру экрана (сетку, колонки, блоки) как данность и пытаются лишь подровнять отступы, добавить скругления или улучшить контрастность. В проекте ACTRA такой подход признается грубейшим дефектом мышления.
- **Обязанность на деконструкцию:** Аудитор обязан смело ставить фундаментальный вопрос: *«Зачем этот блок существует на этом экране? Имеет ли он вообще право находиться здесь в постоянном виде?»* Если концепция или размещение блока противоречат истинной цели пользователя, аудитор обязан требовать его скрытия, сворачивания в on-demand (Progressive Disclosure) или полного выноса в профильный сценарий, а не «аккуратного выравнивания колонок».

#### 2. Четыре фундаментальных вопроса первого порядка (First-Principles Questions)
Перед анализом любого экрана или шага сценария аудитор обязан ответить на 4 вопроса:

1. **Primary Job vs. Space Allocation (Соответствие площади экрана главной цели):**
   - *В чем главная работа (JTBD), ради которой пользователь пришел на этот экран?*
   - *Соответствует ли распределение экранного пространства приоритету этой задачи?*
   - Если цель экрана — «вставить и отредактировать текст заданий», то 100% фокуса и максимальная полезная площадь обязаны принадлежать редактору. Постоянное отчуждение 30–50% экрана под пассивный контент признается критическим архитектурным дефектом.

2. **The Burden of Existence (Бремя оправдания постоянного присутствия):**
   - Каждый постоянный блок на экране обязан непрерывно доказывать свою ценность в процессе выполнения целевого действия.
   - **Дихотомия «Действие vs. Справка» (Action vs. Reference Duality):** Памятки, подсказки синтаксиса, документация и шаблоны — это *справочный материал*, а не рабочая среда. Справочный материал обязан подчиняться принципу *Progressive Disclosure* (раскрытие по требованию: drawer, collapsible panel, popover), освобождая место для непосредственного действия.

3. **The 10th-Session Test (Тест десятой рабочей сессии):**
   - *Что почувствует опытный пользователь, открывающий этот экран в 5-й, 10-й или 50-й раз?*
   - Если элемент нужен исключительно в ознакомительных целях (новичку на первом шаге), его постоянное нахождение на экране превращается в визуальный мусор, раздражитель и кражу рабочего пространства. Повторный пользователь не должен платить экраном за нужды первого визита.

4. **Context Integrity & Feature Leaks (Контекстная изоляция и чистота функционала):**
   - *Не решает ли этот блок задачу чужого экрана или другого сценария?*
   - Например, подробнейшая памятка оформления с шаблонами промптов критически важна для сценария «ИИ-импорт» (где пользователь передает правила внешней нейросети), но в сценарии прямого «Импорта из текста» она лишь перегружает когнитивный ресурс пользователя, который пришел с уже готовым материалом.

#### 3. Безопасность контекста пользователя (User Context & Clipboard Protection)
- Вспомогательные действия интерфейса не имеют права уничтожать пользовательские данные.
- Кнопки копирования примеров и шаблонов не должны затирать системный буфер обмена (`navigator.clipboard`), где у пользователя уже может лежать подготовленный текст задания. Предпочтительный паттерн — прямое безопасное действие в интерфейсе («Вставить образец в редактор»), а копирование в буфер — вторичная опция.
