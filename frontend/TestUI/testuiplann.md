\# 1. Общая идея



\- \*\*Цель:\*\* реализовать в S1 универсальный интерфейс для заданий типа `Тест`, который:

&nbsp; - повторяет критичное поведение Tk-интерфейса;

&nbsp; - вписывается в текущую структуру \[S1/index.html](cci:7://file:///d:/Ai%20Ai/radioproject/Plan%20UI%20and%20Smth/S1/index.html:0:0-0:0);

&nbsp; - опирается на \*\*один канонический паттерн\*\*:

&nbsp;   - слева (или справа) — \*\*панель вопросов\*\* (sidebar);

&nbsp;   - по центру — \*\*тело вопроса\*\* с вариантами/ответом и картинками;

&nbsp;   - над/под — таймер, статус, подсказки;

&nbsp;   - внизу — общие кнопки S1 (`Проверить`, `Дальше`, и т.п.), уже существующие.



\- \*\*Типы тестовых вопросов:\*\*

&nbsp; - выбор одного варианта;

&nbsp; - выбор нескольких вариантов;

&nbsp; - (позже) открытый ответ, но сейчас фокус на вариативных.

\# 3. Логическая структура и компоненты



Опишу абстрактные «компоненты» (по сути, JS-модули + DOM-структура внутри S1).



\## 3.1. TestRoot



\- \*\*Ответственность:\*\* собрать все подкомпоненты, держать локальное состояние одного тестового задания.

\- \*\*Входные данные:\*\*

&nbsp; - `taskPayload` — JSON задачи из `/api/session/{id}/task` (см. 4.1).

&nbsp; - `initialStateFromServer` — если есть (например, уже были данные о выделенных вариантах, пометках и т.п.).

\- \*\*Внешние зависимости:\*\*

&nbsp; - функции S1:

&nbsp;   - `sendTaskSubmit(userPayload)` — вызывается на кнопку `Проверить`;

&nbsp;   - `applyCheckResult(serverCheckResult)` — вызывается S1 после успешного `/task/submit`;

&nbsp; - глобальные обработчики кнопок S1 (на HUD / внизу).

\- \*\*Экспортируемые методы (для S1 JS):\*\*

&nbsp; - `render(containerElement, taskData)`

&nbsp; - `getUserAnswerPayload()` — вернуть данные для отправки в `/task/submit`;

&nbsp; - `applyCheckFeedback(feedbackData)` — применить результаты проверки (правильно/ошибка по вариантам и по вопросу);

&nbsp; - `setMode(mode)` — смена режима `answering/review`.



\## 3.2. QuestionSidebar



\- \*\*Ответственность:\*\* отрисовать список вопросов и позволять навигацию.

\- \*\*Входные данные:\*\*

&nbsp; - `questions: Array<QuestionMeta>`

&nbsp; - `currentQuestionIndex: number`

&nbsp; - `questionStates: Array<QuestionStateMeta>` — статус каждого вопроса.

\- \*\*События:\*\*

&nbsp; - `onSelectQuestion(index)` — клики по элементам списка.

\- \*\*Состояние элемента списка:\*\*

&nbsp; - номер (`1, 2, 3, ...`);

&nbsp; - иконки/метки:

&nbsp;   - \*\*текущий\*\*;

&nbsp;   - \*\*уже отвечен\*\*;

&nbsp;   - \*\*правильно/неправильно\*\* (в режиме review);

&nbsp;   - \*\*помечен для повторения\*\* (если такое поведение нужно из Tk).



\## 3.3. QuestionBody



\- \*\*Ответственность:\*\* показывать текущий вопрос.

\- \*\*Структура:\*\*

&nbsp; - заголовок/текст вопроса;

&nbsp; - (опционально) картинка/картинки;

&nbsp; - список вариантов ответа (один/много);

&nbsp; - зона подсказок/комментариев (в режиме review).

\- \*\*Входные данные:\*\*

&nbsp; - `question: Question` (см. 4.1);

&nbsp; - `selection: QuestionSelection` — текущий выбор пользователя;

&nbsp; - `mode: 'answering' | 'review'`.

\- \*\*События:\*\*

&nbsp; - `onChangeSelection(newSelection)` — пользователь меняет выбор;

&nbsp; - `onToggleFlag()` — пометка вопроса флажком (если нужно);

\- \*\*Особенности:\*\*

&nbsp; - при `mode='answering'` нельзя показывать правильный ответ;

&nbsp; - при `mode='review'`:

&nbsp;   - подсветка выбранных/правильных;

&nbsp;   - при наличии текстового фидбэка (из Tk/серверной логики) — показать.



\## 3.4. AnswerOptionsList



\- \*\*Ответственность:\*\* рендерить варианты ответа.

\- \*\*Типы:\*\*

&nbsp; - `single` — радио-кнопки;

&nbsp; - `multiple` — чекбоксы.

\- \*\*Входные данные:\*\*

&nbsp; - `options: Array<AnswerOption>`

&nbsp; - `selection: Set<optionId>` или один `optionId` для single;

&nbsp; - `correctOptionIds?: Set<optionId>` (при review);

&nbsp; - `perOptionFeedback?: Record<optionId, 'correct' | 'wrong' | 'neutral'>`.

\- \*\*События:\*\*

&nbsp; - `onSelect(optionId)` / `onToggle(optionId)`.



\## 3.5. QuestionHeader / MetaPanel



\- \*\*Ответственность:\*\* показать:

&nbsp; - номер вопроса / общее количество (`Вопрос 3 из 10`);

&nbsp; - сложность для конкретного вопроса, если она есть;

&nbsp; - флажок «пометить/снять пометку»;

&nbsp; - небольшой индикатор статуса (ответ дан/нет).

\- \*\*Взаимодействие:\*\*

&nbsp; - взаимодействует с `QuestionSidebar` (тот же флажок синхронен в обоих местах).

\# 4. Форматы данных (API и локально)



\## 4.1. Формат тестового задания из `/api/session/{id}/task`



Предлагаемый (можно адаптировать под реальный):



```json

{

&nbsp; "task\_id": "string",

&nbsp; "task\_type": "test",

&nbsp; "difficulty": "easy" | "hard",

&nbsp; "time\_limit\_seconds": 120, 

&nbsp; "test": {

&nbsp;   "questions": \[

&nbsp;     {

&nbsp;       "id": "q1",

&nbsp;       "order": 1,

&nbsp;       "text": "Текст вопроса",

&nbsp;       "images": \[

&nbsp;         {"url": "/static/img/...", "alt": "описание"}

&nbsp;       ],

&nbsp;       "answer\_type": "single" | "multiple",

&nbsp;       "options": \[

&nbsp;         {

&nbsp;           "id": "opt1",

&nbsp;           "text": "Вариант ответа",

&nbsp;           "image": {"url": "...", "alt": "..."}

&nbsp;         }

&nbsp;       ]

&nbsp;     }

&nbsp;   ]

&nbsp; },

&nbsp; "initial\_user\_state": {

&nbsp;   "selections": {

&nbsp;     "q1": \["opt1", "opt3"]

&nbsp;   },

&nbsp;   "flags": {

&nbsp;     "q1": true

&nbsp;   }

&nbsp; }

}

```



Важно:



\- `task\_type` позволяет S1 понять, что нужно подключать `TestUI`.

\- `test.questions` — \*\*единый массив\*\*, порядок определяется `order`.

\- `initial\_user\_state` — опционально: нужно, чтобы при возврате к задаче/релоаде не терять выбор.



\## 4.2. Формат отправки ответа `/task/submit`



S1 уже шлёт что-то вроде `user\_input`. Для теста договоримся:



```json

{

&nbsp; "task\_id": "string",

&nbsp; "task\_type": "test",

&nbsp; "user\_input": {

&nbsp;   "selections": {

&nbsp;     "q1": \["opt1", "opt3"],

&nbsp;     "q2": \["opt5"]

&nbsp;   },

&nbsp;   "flags": {

&nbsp;     "q1": true,

&nbsp;     "q3": false

&nbsp;   }

&nbsp; }

}

```



`TestRoot.getUserAnswerPayload()` должен вернуть именно вот такую структуру (встроенную в общий JSON S1).



\## 4.3. Формат ответа `/task/submit` (результат проверки)



Для теста полезен формат:



```json

{

&nbsp; "ok": true,

&nbsp; "result": {

&nbsp;   "task\_id": "string",

&nbsp;   "score": 0.8,

&nbsp;   "is\_solved": true,

&nbsp;   "per\_question": {

&nbsp;     "q1": {

&nbsp;       "is\_correct": true,

&nbsp;       "correct\_option\_ids": \["opt1", "opt3"],

&nbsp;       "user\_option\_ids": \["opt1", "opt3"],

&nbsp;       "feedback": "Краткий комментарий, если есть"

&nbsp;     },

&nbsp;     "q2": {

&nbsp;       "is\_correct": false,

&nbsp;       "correct\_option\_ids": \["opt5"],

&nbsp;       "user\_option\_ids": \["opt2"],

&nbsp;       "feedback": "Подсказка/объяснение"

&nbsp;     }

&nbsp;   }

&nbsp; }

}

```



S1 уже как-то обрабатывает результаты; мы добавляем:



\- вызов `testUI.applyCheckFeedback(result.per\_question)` и `setMode('review')`;

\- интеграцию `result.score` / `is\_solved` в уже существующий UI S1 (общий индикатор успешности задания).

\# 5. Локальное состояние и стейты



\## 5.1. Главное состояние `TestRootState`



```ts

type Mode = 'answering' | 'review';



interface TestRootState {

&nbsp; mode: Mode;                     // answering до submit, затем review

&nbsp; currentQuestionIndex: number;   // 0..N-1

&nbsp; selections: {

&nbsp;   \[questionId: string]: string\[];  // список выбранных option.id

&nbsp; };

&nbsp; flags: {

&nbsp;   \[questionId: string]: boolean;   // пометка для повторения

&nbsp; };

&nbsp; checkFeedback?: {

&nbsp;   \[questionId: string]: {

&nbsp;     is\_correct: boolean;

&nbsp;     correct\_option\_ids: string\[];

&nbsp;     user\_option\_ids: string\[];

&nbsp;     feedback?: string;

&nbsp;   }

&nbsp; };

}

```



\## 5.2. Жизненный цикл (state machine)



\- \*\*INIT\*\*

&nbsp; - `mode = 'answering'`

&nbsp; - `currentQuestionIndex = 0`

&nbsp; - `selections` и `flags` из `initial\_user\_state` или пустые.



\- \*\*ANSWERING\*\*

&nbsp; - пользователь переключает вопросы, меняет выбор.

&nbsp; - кнопка `Проверить`:

&nbsp;   - S1 вызывает `getUserAnswerPayload()` → `/task/submit`.

&nbsp;   - при `ok`:

&nbsp;     - S1 вызывает `TestRoot.applyCheckFeedback(result.per\_question)`;

&nbsp;     - S1 меняет глобальный статус задания (`is\_solved`) и может включить кнопку `Дальше`.

&nbsp;     - `mode = 'review'`.



\- \*\*REVIEW\*\*

&nbsp; - пользователь может переключать вопросы, смотреть подсветку правильных/ошибок и текстовый фидбэк.

&nbsp; - выбор по идее уже не меняется (можно сделать недоступным изменение или разрешить, но без отправки).

&nbsp; - переход к следующему заданию происходит вне TestUI (кнопка `Дальше` S1).

\# 6. Поведение по сложностям (easy/hard)



Тестовый UI должен учитывать сложность только визуально и, возможно, легкой вариацией поведения:



\- \*\*easy:\*\*

&nbsp; - более явные подсказки (например, надпись «Можно выбрать несколько вариантов»);

&nbsp; - можно показать сообщение „Выберите хотя бы один ответ“ при попытке проверки без ответа.



\- \*\*hard:\*\*

&nbsp; - более сдержанный UI, минимум подсказок;

&nbsp; - можно не выводить вспомогательные надписи (но архитектурно это тот же UI).



В ТЗ: это \*\*условная ветка оформления и подсказок\*\*, без изменения формата данных.

\# 7. Интеграция с кнопками и HUD S1



\- \*\*Кнопка `Проверить` в S1:\*\*

&nbsp; - если `task\_type === 'test'`:

&nbsp;   - перед отправкой:

&nbsp;     - собрать payload `user\_input` через `TestRoot.getUserAnswerPayload()`;

&nbsp;     - при отсутствии ответов: показать локальное предупреждение;

&nbsp;   - после успешного ответа:

&nbsp;     - S1 показывает общий блок результата (уже реализован);

&nbsp;     - вызывает `TestRoot.applyCheckFeedback(...)` и переводит в review-режим.



\- \*\*Кнопка `Дальше` / `Следующее задание`:\*\*

&nbsp; - логика остаётся в S1 (запрос `/task/next` и перерисовка всего экрана).

&nbsp; - при новом задании:

&nbsp;   - S1 уничтожает старый TestRoot (очищает `taskSpecificContainer`);

&nbsp;   - если новый `task\_type === 'test'` — создаёт новый TestRoot.



\- \*\*HUD-прогресс:\*\*

&nbsp; - общая полоска/счётчик в S1 остаётся как есть (счёт по всей сессии).

&nbsp; - если надо отразить \*\*прогресс внутри теста\*\* (например `ответили X из N`), это делает `QuestionSidebar`/`QuestionHeader`:

&nbsp;   - подсчёт `answeredQuestionsCount = количество вопросов, где есть непустой selection`.

\# 8. Визуальная спецификация (кратко)



Без пиксель-перфект, но зафиксируем принципы.



\- \*\*Sidebar:\*\*

&nbsp; - вертикальный список `Q1, Q2, ...`:

&nbsp;   - текущий вопрос: выделен фоном;

&nbsp;   - отвеченные: отмечены «галочкой»/цветом;

&nbsp;   - в review:

&nbsp;     - правильные — зелёная рамка/иконка;

&nbsp;     - ошибочные — красная.

\- \*\*Main:\*\*

&nbsp; - сверху:

&nbsp;   - `Вопрос 3 из 10`, флаг, статус.

&nbsp; - далее:

&nbsp;   - текст вопроса;

&nbsp;   - под ним — картинка (если есть), вписанная по ширине.

&nbsp; - ниже:

&nbsp;   - варианты ответа списком, каждый — зона с:

&nbsp;     - текстом,

&nbsp;     - опциональной миниатюрой/картинкой;

&nbsp;     - в review:

&nbsp;       - подсветка: зелёный (правильный и выбранный), светло-зелёный (правильный, но не выбранный), красный (выбранный, но неправильный), обычный (прочие).

&nbsp; - снизу:

&nbsp;   - (опционально) текстовый комментарий из `feedback`.

\## 10. Маппинг на существующие макеты



Этот раздел фиксирует соответствие ранее согласованных макетов (из папки с Test UI-мокапами) компонентам и состояниям, описанным в ТЗ. Если возникает расхождение между реализацией и макетами, проверяем вот по этому списку.



\### 10.1. Базовый экран теста



\- \*\*Макеты:\*\*  

&nbsp; - L1-M1 (и все его «варианты без точек», где слева список вопросов, справа тело вопроса).

\- \*\*Компоненты:\*\*  

&nbsp; - `TestRoot` (общий контейнер внутри `taskSpecificContainer` в S1).  

&nbsp; - `QuestionSidebar` — вертикальный список вопросов, выбранный вопрос подсвечен.  

&nbsp; - `QuestionBody` — текущий вопрос по центру, текст + картинка (если есть) + варианты.

\- \*\*Состояние:\*\*  

&nbsp; - `mode = 'answering'`.  

&nbsp; - Нет подсветки правильных/неправильных, только отображение выбора пользователя.



\### 10.2. Многовопросовый тест с навигацией



\- \*\*Макеты:\*\*  

&nbsp; - Все «многовопросовые» варианты, где:

&nbsp;   - слева — номера вопросов (1..N),

&nbsp;   - по центру — один активный вопрос,

&nbsp;   - есть визуальное различие «отвечен / не отвечен».

\- \*\*Компоненты и данные:\*\*  

&nbsp; - `QuestionSidebar`:

&nbsp;   - берёт массив `questions\[]` из `task.test.questions`.

&nbsp;   - визуально показывает:

&nbsp;     - текущий вопрос;

&nbsp;     - состояние «ответ дан» (есть выбор в `selections\[questionId]`).

&nbsp; - `QuestionHeader`:

&nbsp;   - показывает текущий индекс и общее количество: «Вопрос X из N».

\- \*\*Состояние:\*\*  

&nbsp; - Навигация по `currentQuestionIndex`, изменения `selections` при выборе.



\### 10.3. Экран проверки / review-режим



\- \*\*Макеты:\*\*  

&nbsp; - Варианты с подсветкой:

&nbsp;   - правильных и неправильных вариантов;

&nbsp;   - статусов «правильно/неправильно» по вопросу;

&nbsp;   - визуально отличающихся вопросов в списке слева.

\- \*\*Компоненты:\*\*  

&nbsp; - `AnswerOptionsList`:

&nbsp;   - использует `correct\_option\_ids` и `user\_option\_ids` из `checkFeedback\[qId]`:

&nbsp;     - зелёный/красный/нейтральный фон вариантов согласно макетам.

&nbsp; - `QuestionSidebar`:

&nbsp;   - в режиме `review` отображает:

&nbsp;     - правильные вопросы (иконка/цвет);

&nbsp;     - ошибочные вопросы (другая иконка/цвет).

&nbsp; - `QuestionBody`:

&nbsp;   - при наличии текстового комментария (`feedback`) — показывает его под вариантами.

\- \*\*Состояние:\*\*  

&nbsp; - `mode = 'review'` (устанавливается после успешного `/task/submit`).

&nbsp; - Сопоставимо с макетами «после проверки», где видно правильные ответы.



\### 10.4. Флажки / пометки вопросов



\- \*\*Макеты:\*\*  

&nbsp; - Варианты, где у вопроса есть иконка/чекбокс «пометить», и/или в списке слева для некоторых вопросов стоит маркер «отложить/проверить позже».

\- \*\*Компоненты:\*\*  

&nbsp; - `QuestionHeader`:

&nbsp;   - кнопка/иконка «флажок» → `onToggleFlag()` → меняет `flags\[questionId]`.

&nbsp; - `QuestionSidebar`:

&nbsp;   - для вопросов с `flags\[qId] === true` рисует соответствующую иконку.

\- \*\*Состояние:\*\*  

&nbsp; - `flags: Record<questionId, boolean>` хранится в `TestRootState`.  

&nbsp; - Может сохраняться/отправляться в `user\_input.flags` при submit (если потребуется на бэкенде).



\### 10.5. Разные уровни сложности (easy / hard)



\- \*\*Макеты:\*\*  

&nbsp; - Пары макетов для easy/hard, где:

&nbsp;   - на easy больше вспомогательных надписей/пояснений;

&nbsp;   - на hard интерфейс более «сухой».

\- \*\*Компоненты/поведение:\*\*  

&nbsp; - `TestRoot` получает `difficulty` из S1 (`task.difficulty`).

&nbsp; - `QuestionBody`:

&nbsp;   - при `difficulty = 'easy'`:

&nbsp;     - явно пишет подсказки «Можно выбрать несколько вариантов», «Выберите хотя бы один ответ» и пр.

&nbsp;   - при `difficulty = 'hard'`:

&nbsp;     - убирает лишние подсказки, оставляя только минимально необходимое.

\- \*\*Состояние:\*\*  

&nbsp; - `difficulty` просто влияет на текст/подсказки/микро-оформление, логика данных и API одна.



\### 10.6. Макеты без точек/каруселей



\- \*\*Макеты:\*\*  

&nbsp; - Ранние версии с точками/каруселью (dot-indicators) **декларированы как устаревшие**.

\- \*\*Решение в ТЗ:\*\*  

&nbsp; - Единственный канонический способ навигации — `QuestionSidebar`.  

&nbsp; - Макеты с точками рассматриваем как эволюционные, но не нормативные; реализация им не обязана соответствовать.



\### 10.7. Текущее состояние реализации в S1/TestUI



\- **QuestionSidebar (C1):**  

&nbsp; - Соответствует DOM-элементу `sidebar` и функции `renderQuestionSidebarC1` внутри `TestUI` в `S1/index.html`.  

&nbsp; - Использует массив `state.questions` и `state.selections`/`state.questionResults` для отображения:

&nbsp;   - текущего вопроса;  

&nbsp;   - факта «ответ дан»;  

&nbsp;   - статуса «правильно/неправильно/без ответа» в режиме review.  



\- **QuestionHeader (C2):**  

&nbsp; - Реализован как верхний блок `header` в функции `renderQuestionViewC2C3C4`.  

&nbsp; - Показывает `Question X of N` и `difficulty` конкретного задания.  

&nbsp; - Логически соответствует `QuestionHeader / MetaPanel` из раздела 3.5 и используется как часть основного тела вопроса.



\- **QuestionBody (C3):**  

&nbsp; - Представлен контейнером `body` в `renderQuestionViewC2C3C4`.  

&nbsp; - Включает текст вопроса и список вариантов ответа (`raw.answers`), отрисованных в виде набора `label` с радио/чекбоксами.  

&nbsp; - Многовариантность определяется как через глобальный `testType`, так и через количество правильных ответов в `raw.answers`.



\- **QuestionFeedback (C4):**  

&nbsp; - Представлен нижней частью `body`: статусной строкой с текстом о результате для текущего вопроса.  

&nbsp; - Использует данные из `state.questionResults[questionId]` (поле `status`), приходящие из `applyCheckFeedback`.  

&nbsp; - В режиме `review` меняет текст и цвет в соответствии с результатом.



В совокупности `renderQuestionSidebarC1` + `renderQuestionViewC2C3C4` реализуют базовые сценарии 10.1–10.3 (answering/review) без привязки к конкретным пиксельным значениям макетов, но с сохранением их композиции: C1 слева, C2+C3+C4 в основной колонке.
