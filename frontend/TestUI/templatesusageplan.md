Сейчас цель — превратить набор разрозненных макетов в \*\*целостную модель «Теста в S1»\*\*: какие есть состояния, какие данные нужны, какие компоненты общие.



Предлагаю такой план «сборки организма», без реализации:



---



\## 1. Зафиксировать уровни абстракции



Разделим на 3 слоя:



\- \*\*Слой сценариев\*\* (что делает пользователь):

&nbsp; - проходит тест вопрос за вопросом;

&nbsp; - просматривает результат по каждому вопросу;

&nbsp; - в некоторых случаях — видит общий итог по тесту до S2/S3.



\- \*\*Слой состояний UI\*\*:

&nbsp; - «идёт прохождение»;

&nbsp; - «проверка вопроса»;

&nbsp; - «режим просмотра после завершения теста».



\- \*\*Слой компонент\*\* (повторно используемые блоки):

&nbsp; - панель вопросов (каноническая боковая из L1‑M1);

&nbsp; - область текущего вопроса (вариант текст/картинка/открытый ответ);

&nbsp; - панель статуса/обратной связи по вопросу;

&nbsp; - вспомогательные элементы (таймер, флажок «вернуться позже» и т.п.).



Дальше все макеты привязываем к этим слоям.



---



\## 2. Определить конечный автомат состояний для «Тест» в S1



Нужен простой state‑machine (без кода, как диаграмма):



\- \*\*S0: init\*\*

&nbsp; - загрузили `task` типа `test`, тест ещё не начат (опционально: экран «описание + кнопка начать»).



\- \*\*S1: answering (проход теста)\*\*  

&nbsp; Для каждого вопроса:

&nbsp; - `answering\_single`: выбор вариантов (L1‑T1 / IMG‑A1 / IMG‑Q1);

&nbsp; - `answering\_open`: ввод текста (L2‑O1, но «один вопрос»).

&nbsp; Переходы:

&nbsp; - `select\_answer`, `type\_answer` → обновление состояния;

&nbsp; - \[next\_question](cci:1://file:///d:/Ai%20Ai/radioproject/task\_system/ui/components/trainer/test\_executor.py:320:4-371:190) / \[prev\_question](cci:1://file:///d:/Ai%20Ai/radioproject/task\_system/ui/components/trainer/test\_executor.py:310:4-318:60) / `jump\_to\_question`.



\- \*\*S2: checked\_question (ответ проверен)\*\*

&nbsp; - для текущего вопроса UI переходит в «после проверки»:

&nbsp;   - L1‑T3 для вариантов;

&nbsp;   - L2‑O2‑per‑question для open.

&nbsp; - переходы:

&nbsp;   - \[next\_question](cci:1://file:///d:/Ai%20Ai/radioproject/task\_system/ui/components/trainer/test\_executor.py:320:4-371:190) → другой вопрос, который может быть всё ещё в S1;

&nbsp;   - `view\_previous\_question` → просмотр другого в состоянии S2/S1.



\- \*\*S3: test\_finished (все вопросы обработаны / время вышло)\*\*

&nbsp; - общий итог по тесту (опциональный summary‑блок);

&nbsp; - весь тест в режиме просмотра:

&nbsp;   - боковая панель показывает статусы всех вопросов;

&nbsp;   - центральная часть показывает любой вопрос в режиме «после проверки».



Главное: \*\*один граф состояний, а не отдельный для каждого макета\*\*.



---



\## 3. Нормализовать набор компонент



Из макетов и существующего Tk вытекает единый набор компонент:



\- \*\*\[C1] QuestionSidebar\*\* (боковая панель вопросов)

&nbsp; - отображается \*\*во всех состояниях теста\*\*, где это возможно;

&nbsp; - умеет:

&nbsp;   - показывать номер;

&nbsp;   - пометку «есть ответ» / «ошибка» / «ок» / «флажок»;

&nbsp;   - переключать текущий вопрос.



\- \*\*\[C2] QuestionHeader\*\*

&nbsp; - номер вопроса;

&nbsp; - «Вопрос X / N»;

&nbsp; - возможно — мини‑прогресс/индикатор.



\- \*\*\[C3] QuestionBody\*\*

&nbsp; - \*\*вариант A (L1‑T1/IMG‑Q1/IMG‑A1)\*\*: текст + (опционально) изображения + варианты;

&nbsp; - \*\*вариант B (L2‑O1)\*\*: текст + (опционально) изображения + многострочное поле ответа.



\- \*\*\[C4] QuestionFeedback\*\*

&nbsp; - текстовый блок «верно/неверно» + краткое пояснение;

&nbsp; - индикаторы подсветки для вариантов/ответа.



\- \*\*\[C5] TestToolbar (локальная, внутри блока теста)\*\* — опционально:

&nbsp; - таймер;

&nbsp; - кнопки «предыдущий / следующий»;

&nbsp; - флажок «пометить вопрос».



Каждый макет = конкретная комбинация этих компонент в одном из состояний автомата (S1/S2/S3).



---



\## 4. Свести макеты к этим состояниям/компонентам



Теперь «привязываем»:



\- \*\*L1‑T1\*\* → S1 / C2 + C3(A)  

&nbsp; Однотипный вопрос с вариантами, до проверки.



\- \*\*L1‑T3\*\* → S2 / C2 + C3(A) + C4  

&nbsp; Тот же вопрос, но в состоянии «проверен».



\- \*\*IMG‑Q1 / IMG‑A1\*\* → вариации C3(A):  

&nbsp; те же состояния S1/S2, но с подтипом «с картинками».



\- \*\*L1‑M1\*\* → S1/S2 с C1 (панель) + C2 + C3(A/B) + C5  

&nbsp; Это основной «композитный» макет.



\- \*\*L2‑O1 / L2‑O2\*\* → те же S1/S2, но C3(B) вместо C3(A)  

&nbsp; Open‑вопрос по одному за раз.



То есть логика: \*\*макет = (состояние автомата) × (вариант QuestionBody)\*\*, плюс везде один и тот же C1.



---



\## 5. Решить, что делаем с «общим итогом теста» внутри S1



Нужно явно определиться:



\- Делаем ли мы \*\*локальный summary теста в S1\*\* (до перехода к S2/S3) или:

\- Считаем, что \*\*общий итог всегда показывается только на S2/S3\*\*, а S1 отвечает только за per‑question фидбек.



С учётом того, что у тебя уже есть S2/S3 и они работают:



\- рационально для первой итерации:

&nbsp; - \*\*не городить отдельный «экран итогов теста» в S1\*\*;

&nbsp; - в S1:

&nbsp;   - показывать только per‑question обратную связь и статус;

&nbsp;   - по завершении теста переходить к S2 (итоги итерации) или к S3 (финал комплекса).



Тогда автомат упрощается: S3 (test\_finished) = «внутренняя точка», после которой S1 триггерит переход на S2/S3.



---



\## 6. План «сборки» как шаги



Когда дойдём до реализации, логика такая:



1\. \*\*Спецификация данных:\*\*

&nbsp;  - для каждого вопроса: `id`, `type`, `text`, `images\[]`, `answers\[]` или формат ответа open;

&nbsp;  - для теста: `total\_questions`, `current\_index`, `question\_states`, `timer`, `finished`.

2\. \*\*Реализовать C1/C2/C3/C4/C5 в web (S1/TestUI):\*\*

&nbsp;  - один раз, без завязки на конкретные макеты;

&nbsp;  - визуально можно переиспользовать стили/идеи из `TestUI`, но компоненты — общие.

3\. \*\*Подвязать состояния автомата:\*\*

&nbsp;  - связываем `task\_type == "test"` + состояние (answering/checked/finished) с отображением нужных компонент.

4\. \*\*Удалить из web‑UI все «лишние» артефакты макетов:\*\*

&nbsp;  - никаких точек/квадратиков под карточкой;

&nbsp;  - никаких локальных мини‑настроек теста в комплексном режиме (их можно оставить только для одиночных тестов, если нужно).
