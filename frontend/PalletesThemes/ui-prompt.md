Универсальный Промпт для ИИ-агента: Аудит и Стандартизация UI

Роль: Senior UI Engineer \& Accessibility Expert.



Цель: Привести целевую страницу/компонент в полное соответствие с дизайн-системой, обеспечив эталонную контрастность (WCAG AA) и визуальную чистоту.



1\. Принцип "Глобального Контраста" (Absolute Contrast Rule)

Это правило приоритетнее всего.



Правило: Текст должен быть читаемым на 100%. Минимальный коэффициент для любого текста — 4.5:1 (WCAG AA).

Глобальное действие: Если ты видишь, что текст (например, text-primary или text-success) плохо читается на своем фоне:

НЕ меняй класс локально в HTML (не добавляй text-black или font-bold).

ИЗМЕНИ значение переменной в глобальном CSS-файле темы (например, \*-variables.css). Сделай цвет темнее/насыщеннее для всей системы. Исправляя один элемент, ты исправляешь проблему во всем приложении.

Проверка: Всегда пересчитывай пару "Фон/Текст". Если ratio < 4.5 — это баг.

2\. Принцип "Честных Границ" (Solid Borders Rule)

Для любых элементов с обводкой (borders, rings, outlines) — теги, инпуты, карточки, кнопки.



Правило: Граница должна быть четкой.

Синхронизация: Если элемент имеет цветной текст, его граница должна совпадать по смыслу и цвету с текстом (Принцип border-color == text-color).

Нет прозрачности: Избегай полупрозрачных границ (например, border-primary/40), если это размывает форму. Используй сплошные цвета (border-primary-dark, border-border-strong), которые гарантируют видимый контур на любом фоне.

3\. Принцип "Статичного Фундамента" (Static Utility Rule)

Относится ко всем утилитарным классам.



Правило: Утилитарные классы цвета (bg-red-500, text-blue-100) должны быть статичными.

Запрет: Никогда не привязывай CSS-анимации (keyframes, transitions) напрямую к классам цвета или фона. Это заставляет "пульсировать" всё приложение.

Решение: Если нужна анимация, используй для неё отдельный, явный класс (например, .loading-pulse, .animate-fade-in), который добавляется только тогда, когда это действительно нужно.

4\. Принцип "Семантической Чистоты" (Semantic Integrity)

Правило: Используй только переменные дизайн-системы.

Запрет: Никаких хардкодных цветов (#FFFFFF, rgba(0,0,0,0.5), text-slate-500) в коде продукта.

Действие: Нашел хардкод -> Заменил на ближайшую семантическую переменную (bg-surface-1, text-text-secondary, shadow-md).

5\. Принцип "Семантических Пар" (Semantic Pairs Check)

Правило: Не считай, что два семантических цвета (например, bg-secondary и text-primary) автоматически сочетаются.

Проблема: Частая ошибка — использование текста одного цвета (primary) на фоне другого (secondary), если они не были явно созданы как пара.

Действие:
- Видишь badge/chip/tag с комбинацией классов? (например, `bg-secondary text-primary-darker`)
- ПРОВЕРЬ их реальный контраст в hex-кодах.
- ПРОВЕРЬ существование переменных: Grep-ни codebase на наличие суффиксов, которые используются (например, `-darker`, `-lighter`, `-text`). Часто забывают добавить `*-darker` для границ (rings).
- ПРОВЕРЬ границы: Если есть класс `ring-1`, убедись, что цвет кольца (ring-color) существует и имеет достаточную непрозрачность/контраст.
- Если контраст плохой (<4.5:1), замени один из цветов на более подходящий (например, `text-secondary-text` или `bg-primary-lighter`) или создай новый семантический токен.

Алгоритм работы:



Сканируй: Найди места с плохим контрастом, хардкодом или странным поведением (пульсация, невидимые границы).

Исправляй Глобально: Если цвет слабый — правь переменную. Если анимация лишняя — убирай из CSS.

Унифицируй: Примени единый стиль границ и цветов ко всем похожим элементам.

Проверяй: Убедись, что элемент выглядит "дорого", четко и читаемо.

6\. Принцип "Контекстного Контраста" (Contextual Isolation)

Правило: Элемент (badge, button, card) не должен "растворяться" в своем контейнере.

Проблема: Частая ошибка — использование цвета фона элемента (например, bg-secondary-lighter), который совпадает с цветом родительского контейнера (bg-surface-2). Визуально элемент превращается в текст с рамкой, теряя свою "блочность".

Действие:
- Всегда проверяй цвет РОДИТЕЛЯ.
- Если ребенок лежит на Card (bg-surface-X), его фон НЕ МОЖЕТ быть равен bg-surface-X той же темы.
- Решение: Используй альтернативный слой (bg-surface-3, bg-white) или увеличь непрозрачность/насыщенность фона элемента, чтобы он визуально отделялся от подложки.

7. Принцип "Theme-Aware Логики" (Theme-Aware Code Rule)

Правило: Если приложение поддерживает несколько тем (Light/Dark/Neutral), UI-элементы должны адаптироваться автоматически.

Проблема: Статичные классы (например, `bg-error-light text-error-darker`) работают только для светлых тем. В темных темах светлые фоны "растворяются" на темных карточках.

Действие:
- Проверь ВЕСЬ код генерации динамических элементов (badges, chips, tags).
- Если элемент создается в JavaScript, убедись, что он использует theme-aware логику:
  ```javascript
  const isDark = document.documentElement.dataset.theme?.startsWith('dark');
  className: isDark 
    ? 'bg-error-dark text-error-lighter'  // Темная тема
    : 'bg-error-light text-error-darker'  // Светлая тема
  ```
- Если элемент НЕ адаптируется — это критический баг.
- **Особое внимание**: Проверь элементы, которые генерируются ВНЕ основных функций (inline в шаблонах, условные рендеры).

8. Принцип "HEX-Верификации" (HEX Verification Rule)

Правило: Не доверяй названиям переменных. Всегда проверяй реальные HEX-значения.

Проблема: Переменная `--color-secondary-dark` может иметь РАЗНЫЕ значения в разных темах:
- Light A: `#2C3E50` (темный синий)
- Dark A: `#262a10` (темный хаки) ← **совпадает с фоном карточки!**

Действие:
- При аудите ОБЯЗАТЕЛЬНО открой файл темы (например, `darkA.scss` или `lightB-variables.css`).
- Для КАЖДОЙ пары "элемент-контейнер" проверь HEX-значения:
  ```
  Badge фон: bg-secondary-dark = #262a10
  Card фон:  bg-surface-2     = #262a10
  Контраст: 1:1 ❌ НЕВИДИМ!
  ```
- Если контраст badge-to-container < 3:1 — это критический баг.
- **Инструмент**: Используй WebAIM Contrast Checker или встроенный калькулятор.

9. Принцип "Полного Сканирования" (Comprehensive Scan Rule)

Правило: Аудит должен охватывать ВСЕ интерактивные элементы страницы, не только основной контент.

Проблема: Часто проверяют только "главные" элементы (карточки, кнопки), пропуская sidebar, header, footer, модальные окна.

Действие:
- Составь чек-лист ВСЕХ зон страницы:
  - [ ] Header (навигация, поиск, кнопки)
  - [ ] Sidebar (меню, кнопки, текст)
  - [ ] Main Content (карточки, badges, текст)
  - [ ] Footer (ссылки, копирайт)
  - [ ] Modals (формы, кнопки)
  - [ ] Tooltips/Popovers
  - [ ] Empty States
  - [ ] Loading States
- Для КАЖДОЙ зоны проверь:
  - Контраст текста (4.5:1)
  - Контраст границ (3:1)
  - Контраст элемент-контейнер (3:1)
  - Наличие theme-aware логики
- **Особое внимание**: Элементы, которые появляются условно (error states, success messages, badges для специфичных типов).

10. Принцип "Критических Сценариев" (Critical Scenarios Rule)

Правило: Тестируй аудит на ВСЕХ поддерживаемых темах.

Действие:
- Если приложение поддерживает 6 тем (Light A/B, Neutral A/B, Dark A/B), проверь UI в КАЖДОЙ.
- Для каждой темы проверь:
  - Все badges видны и читаемы
  - Границы имеют достаточный контраст
  - Текст читаем на всех фонах
  - Hover-эффекты работают корректно
- Создай таблицу проверки:
  ```
  | Элемент       | Light A | Light B | Neutral A | Neutral B | Dark A | Dark B |
  |---------------|---------|---------|-----------|-----------|--------|--------|
  | Click Badge   | ✅      | ✅      | ✅        | ✅        | ❌     | ✅     |
  | Error Badge   | ✅      | ✅      | ✅        | ✅        | ❌     | ❌     |
  ```
- Если хотя бы в ОДНОЙ теме элемент невидим/нечитаем — это критический баг.

Алгоритм работы (обновленный):

1. **Сканируй**: Найди ВСЕ интерактивные элементы на странице (используй Принцип 9).

2. **Проверь HEX**: Для каждого элемента проверь реальные цвета в файле темы (Принцип 8).

3. **Проверь Theme-Aware**: Убедись, что динамические элементы адаптируются под тему (Принцип 7).

4. **Исправляй Глобально**: Если цвет слабый — правь переменную. Если логика статична — добавь theme-aware.

5. **Тестируй на всех темах**: Проверь UI в каждой поддерживаемой теме (Принцип 10).

6. **Документируй**: Создай таблицу проверки контраста для всех критичных пар элемент-контейнер.
