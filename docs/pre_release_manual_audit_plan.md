# Предрелизный план ручной функциональной инспекции

## Статус

- Дата: 2026-03-04
- Назначение: финальный ручной аудит продукта перед релизом
- Формат: один проход по всем ключевым экранам + единая таблица дефектов + итоговое решение `go / conditional go / no-go`

## Зачем нужен этот документ

Автотесты в проекте уже закрывают часть рисков, но они не отвечают на три главных продуктовых вопроса:

1. Понимает ли пользователь, зачем он оказался на конкретном экране.
2. Может ли он с помощью доступных инструментов добиться своей цели без тупиков и лишнего трения.
3. Выглядит ли этот экран как живая часть продукта, а не как техническая заготовка.

Этот план нужен не для поиска косметики. Он нужен, чтобы перед релизом честно ответить:

- работает ли основной пользовательский путь;
- хватает ли минимально необходимой механики;
- не врёт ли интерфейс о своих возможностях;
- есть ли у продукта связное ядро ценности.

## Что считать основным контуром продукта

В рамках финального аудита считаем критичными следующие поверхности:

1. Welcome / онбординг
2. Главная
3. Список комплексов
4. Конструктор комплекса
5. Редактор заданий
6. Сессия прохождения `S1`
7. Результаты итерации `S2`
8. Итоговые результаты `S3`
9. Календарь
10. Статистика
11. Микрокарточки
12. Настройки

Если хотя бы одна из поверхностей 1-10 не даёт пройти свой базовый сценарий, релиз считается под угрозой. Поверхности 11-12 можно временно допустить к релизу только при условии, что они не ломают основной поток.

## Что подготовить до ручного прохода

### 1. Зафиксировать релизный кандидат

- Не вносить новые фичи до завершения прохода.
- Проводить аудит на конкретном коммите.
- Все найденные баги складывать в отдельный список без параллельного хаотичного фикса.

### 2. Подготовить тестовые состояния

Нужны минимум три профиля/состояния:

1. `guest`
2. Новый пользователь без истории
3. Активный пользователь с прогрессом, хотя бы одной завершённой сессией, хотя бы одной ошибкой, хотя бы одной паузой и хотя бы одной активностью в календаре

### 3. Подготовить тестовый контент

Минимум:

- 2 модуля
- 2 темы
- 2 комплекса
- 1 теория, привязанная к комплексу
- 1 задача тестового типа
- 1 задача с открытым ответом
- 1 sequence-задача
- 1 click/mistakes-задача, если они входят в релизный каталог
- 1 колода микрокарточек

### 4. Зафиксировать окружение

- Проверка в desktop-режиме и в web-режиме, если оба поддерживаются релизом
- Проверка минимум на desktop-ширине и узкой ширине окна
- Чистый запуск после перезапуска приложения

## Какие автопроверки прогнать до ручного обхода

Это не замена ручному аудиту. Это фильтр, чтобы не тратить время на UI при уже сломанном базовом контракте.

Рекомендуемый минимальный smoke-набор:

```powershell
python -m pytest desktop-app\tests\integration\test_server_smoke.py -v
python -m pytest desktop-app\tests\integration\test_phase1_e2e.py -v
python -m pytest desktop-app\tests\integration\test_phase2_e2e.py -v
python -m pytest desktop-app\tests\integration\test_phase6_e2e.py -v
python -m pytest desktop-app\tests\integration\test_session_api_http.py -v
python -m pytest desktop-app\tests\integration\test_editor_api.py -v
python -m pytest desktop-app\tests\integration\test_profile_selection_logic.py -v
python -m pytest desktop-app\tests\integration\test_statistics_screen_logic.py -v
python -m pytest desktop-app\tests\integration\test_microcards_api.py -v
```

Если хотя бы один из этих тестов падает, ручной обход всё равно можно делать, но дефект сразу помечается как системный риск, а не как локальная UI-проблема.

## Единые правила оценки для каждого экрана

На каждом экране заполняются три оценки:

- `Ценность`
- `Надёжность`
- `Понятность`

Шкала:

- `2` — работает и помогает пользователю без заметного трения
- `1` — работает, но с трением, неочевидностью или недостающим фидбеком
- `0` — сломано, вводит в заблуждение или не даёт пройти ключевой сценарий

### Интерпретация

- Если на критичном экране `Надёжность = 0`, это `no-go` до исправления.
- Если на трёх и более критичных экранах `Понятность = 0/1`, это минимум `conditional go`.
- Если суммарно по критичным экранам больше трёх дефектов уровня blocker/high, релиз не выпускать.

## Единая форма фиксации дефекта

Для каждого найденного дефекта записывать:

1. Экран
2. Сценарий
3. Шаги воспроизведения
4. Ожидаемое поведение
5. Фактическое поведение
6. Влияние на пользователя
7. Severity: `blocker / high / medium / low`
8. Статус: `release-blocking / can-ship / polish`

## Глобальные вопросы, которые задаются на каждом экране

Перед переходом к следующему экрану ответить на них письменно:

1. Зачем пользователь сюда пришёл?
2. Что на этом экране является главным действием?
3. Видно ли это главное действие сразу?
4. Достаточно ли инструментов для достижения цели?
5. Есть ли ложные обещания: кнопки, заглушки, нерабочие переходы, молчаливые ошибки?
6. Получает ли пользователь честную обратную связь при загрузке, сохранении, ошибке и успехе?
7. Сохраняется ли состояние там, где пользователь этого ожидает?
8. Что здесь отсутствует, но критично для минимальной пригодности?
9. Что не критично, но заметно улучшило бы комфорт?

## Обязательные сквозные пользовательские петли

Это главные product-level проверки. Если ломаются они, отдельная исправность экранов уже не спасает.

### Петля A. Первый вход и первая ценность

`Welcome -> создание/выбор профиля -> Главная -> старт обучения -> завершение -> результат`

Проверить:

- новый пользователь понимает, что делать;
- путь до первого полезного действия занимает минуты, а не “надо ещё разобраться”;
- после первого прохождения видно, что продукт действительно что-то даёт.

### Петля B. Возвращение и продолжение

`Главная -> быстрый доступ или resume -> S1 -> S2/S3 -> обновление календаря/статистики`

Проверить:

- пользователь может продолжить незавершённое;
- интерфейс не теряет контекст;
- данные после действия синхронно отражаются в остальных разделах.

### Петля C. Авторинг контента

`Редактор заданий -> создание задачи -> конструктор комплекса -> сохранение -> запуск созданного комплекса`

Проверить:

- контент реально создаётся, а не “сохраняется с ошибками”;
- новая сущность сразу пригодна для прохождения;
- нет ощущения, что редактор и runtime — это две несвязанные системы.

### Петля D. Быстрое повторение

`Главная или Календарь -> Микрокарточки -> короткая сессия -> возврат -> обновлённая аналитика`

Проверить:

- сценарий действительно быстрый;
- ошибки возвращаются в повтор;
- микрокарточки встроены в продукт, а не живут отдельно.

## 1. Welcome / Онбординг

### Цели пользователя

- Понять, что это за приложение
- Выбрать существующий профиль
- Создать новый профиль
- Ознакомиться с юридическими документами
- Войти по паролю, если профиль защищён

### Инструменты

- Список профилей
- Кнопка создания профиля
- Consent gate
- Модалки условий/приватности
- Парольная форма

### Обязательные сценарии

- Гость понимает, что делать на первом экране
- Новый пользователь проходит создание профиля без подсказки разработчика
- `Enter` работает там, где пользователь ожидает submit
- Неверный пароль даёт понятную ошибку
- Закрытие модалок и отмена не ломают состояние
- После успешного входа переход ведёт в следующий логичный экран

### Что спросить у себя

- Не перегружен ли экран первым контактом
- Нет ли юридического шага, который выглядит как барьер, а не как нормальная часть онбординга
- Достаточно ли явно объяснено, зачем нужен профиль

### Оценка

- Ценность: `0/1/2`
- Надёжность: `0/1/2`
- Понятность: `0/1/2`

- Понимает ли пользователь, почему метрика растёт или не растёт
- Не требуется ли уже сейчас фильтрация по комплексу как must-have

## Классификация итогов после прохода

### `GO`

Релиз допустим, если:

- все 4 сквозные петли проходятся;
- нет blocker-дефектов;
- нет критичных экранов с `Надёжность = 0`;
- все оставшиеся проблемы не ломают базовую ценность.

### `CONDITIONAL GO`

Релиз условно допустим, если:

- ядро работает;
- есть `high/medium` проблемы, но они не ломают основной путь;
- требуется список обязательных пост-релизных фиксов.

### `NO-GO`

Релиз останавливается, если:

- ломается хотя бы одна из 4 сквозных петель;
- теряются данные;
- пользователь застревает без понятного выхода;
- разные разделы показывают противоречивое состояние прогресса;
- ключевые CTA ведут в заглушки или неработающие переходы.

## Что считать минимально достаточным продуктом

Проект можно считать жизнеспособным в релизном состоянии, если одновременно верны все пункты:

1. Новый пользователь получает первую ценность без помощи разработчика.
2. Возвращающийся пользователь может быстро продолжить обучение.
3. Автор может создать контент и тут же использовать его в runtime.
4. Прогресс согласован между сессией, календарём, статистикой и главной.
5. На ключевых экранах нет ощущения “функция обещана, но не существует”.

Если эти 5 условий не выполняются, проблема уже не только в багах. Это означает, что продуктовый контур ещё не собран до конца.

## Рекомендуемый порядок самого обхода

Идти в таком порядке, чтобы ловить не локальные, а причинно-связанные дефекты:

1. Welcome
2. Главная
3. Список комплексов
4. Редактор заданий
5. Конструктор комплекса
6. `S1`
7. `S2`
8. `S3`
9. Календарь
10. Статистика
11. Микрокарточки
12. Настройки

После этого отдельно повторить 4 сквозные петли целиком без остановок.

## Практическое правило на финал

Если в конце обхода остаётся вопрос “ну технически вроде можно выпустить”, это ещё не критерий.
Критерий только один: может ли реальный пользователь зайти, понять, пройти, получить пользу и захотеть вернуться.
