# Catalog Screen Design Brief

Дата обновления: `2026-04-08`

## Зачем нужен этот документ

Этот документ нужен как техническое задание для дизайнера, который будет делать один HTML-макет экрана каталога.

Задача макета:

- не просто показать “красивый новый экран”;
- а отразить все ключевые состояния будущего каталога в одном артефакте;
- так, чтобы после этого разработка могла собрать экран из уже существующих UI-блоков проекта и не ломать текущую визуальную систему.

## Главный принцип

Макет должен быть **один**, но он должен показывать **все важные состояния**.

То есть нужен не один “герой-скрин”, а один HTML-файл, внутри которого есть:

- основной вид каталога;
- показ нескольких типов карточек;
- показ разных статусов `Add to Library`;
- показ деталей объекта;
- показ preview перед добавлением в библиотеку;
- показ success/state после добавления.

Проще говоря: это должен быть **единый демонстрационный экран-сценарий**, а не один статичный кадр.

## Что дизайнеру нужно знать о проекте

### Визуальный контекст

Проект уже использует собственную визуальную систему. В макете нельзя придумывать новую систему “с нуля”.

Нужно опираться на уже существующие паттерны:

- семантические цветовые переменные;
- существующие карточки, pills, badges, secondary/primary actions;
- модальные окна проектного типа;
- тосты/уведомления проектного типа;
- мягкие градиентные фоны и layered surfaces;
- существующую анимационную лексику без перегруза.

### Что особенно важно не делать

- не использовать browser-default окна;
- не использовать случайные дефолтные web-компоненты;
- не строить новый визуальный язык отдельно от проекта;
- не делать “маркетплейс в вакууме”, который потом невозможно собрать из текущих блоков;
- не смешивать много разных стилевых направлений в одном экране.

## Технические ограничения для макета

Макет должен быть передан в виде **HTML**.

Желательно:

- один HTML-файл;
- с подключаемыми стилями или встроенным CSS;
- без тяжёлого JS-рантайма, если он не нужен для демонстрации;
- с desktop-first компоновкой;
- с понятным mobile-state хотя бы на уровне одной адаптивной секции или отдельного блока в том же файле.

Макет не обязан быть production-ready кодом.
Но он обязан быть:

- визуально достаточно точным;
- структурно читаемым;
- пригодным для разборки на блоки.

## Что экран должен решать

Будущий экран каталога должен позволять пользователю:

- искать опубликованные `Комплексы` и `Теории`;
- фильтровать результаты;
- быстро понимать, чей это контент и что это за тип;
- видеть, добавлен ли объект уже в библиотеку;
- открыть preview перед `Add to Library`;
- увидеть, что именно будет создано или переиспользовано;
- после добавления открыть свою copy.

## Что обязательно должно быть показано в одном макете

### 1. Основной экран каталога

Нужно показать:

- заголовок экрана;
- подзаголовок с кратким смыслом;
- строку поиска;
- фильтры;
- зону списка/сетки результатов;
- вид пустого состояния фильтра или поиска;
- вид панели быстрых действий.

### 2. Два типа контента

На экране должны быть показаны оба publishable типа:

- `Комплекс`
- `Теория`

Они должны быть визуально родственны, но различимы.

Пользователь должен без чтения длинного текста понимать:

- что перед ним;
- можно ли это взять себе;
- уже есть ли это у него.

### 3. Состояния карточек

На одном макете нужно показать минимум такие карточки:

- обычная карточка комплекса;
- обычная карточка теории;
- карточка “это уже в библиотеке”;
- карточка “это мой опубликованный объект”;
- карточка “это чужой объект, доступный для добавления”;
- карточка в hover/active-ready состоянии;
- карточка с более длинным названием и плотными метаданными.

### 4. Обязательные метаданные на карточке

На карточке или рядом с ней должны читаться:

- тип: `Комплекс` / `Теория`;
- автор;
- источник/статус публикации;
- дата или свежесть публикации;
- базовая размерность:
  - для комплекса: сколько заданий;
  - для теории: условная насыщенность контента;
- состояние относительно библиотеки пользователя:
  - `Можно добавить`
  - `Уже в библиотеке`
  - `Открыть copy`
  - `Мой объект`

### 5. Фильтры

На одном экране надо показать фильтры, которыми реально будут пользоваться:

- поиск по строке;
- тип контента;
- автор / мои / чужие;
- состояние:
  - не добавлено;
  - уже в библиотеке;
  - опубликовано мной.

Не нужно добавлять декоративные фильтры ради красоты.

### 6. Детальный просмотр объекта

Нужно показать, как выглядит раскрытие одного элемента:

- либо боковая панель;
- либо detail modal;
- либо нижний detail block.

В деталях должны быть видны:

- название;
- автор;
- описание;
- ключевые badges;
- состав / summary;
- основные CTA.

Для комплекса важно показать:

- сколько внутри заданий;
- есть ли связанные теории;
- есть ли сложная структура.

Для теории важно показать:

- что это отдельный объект;
- что её можно добавить без комплекса.

### 7. Preview перед Add to Library

Это очень важный блок. Его надо обязательно включить в макет.

Нужно показать, как интерфейс объясняет пользователю:

- будет создана новая copy или уже есть существующая;
- сколько сущностей создастся;
- сколько будет переиспользовано;
- что произойдёт после подтверждения.

Для комплекса preview должен явно показывать состав:

- комплексы;
- модули;
- темы;
- задания;
- теории.

Для теории preview должен быть проще, но тоже отдельным и осмысленным.

### 8. Состояние “уже в библиотеке”

Нужно показать не только кнопку `Добавить`, но и альтернативное состояние:

- `Уже в библиотеке`
- `Открыть copy`

Это один из ключевых сценариев, потому что backend уже работает идемпотентно по `catalog version`.

### 9. Success-state после добавления

Нужно показать, как выглядит состояние сразу после успешного действия:

- success toast;
- success-block в модалке;
- CTA `Открыть copy`;
- возможно CTA `Вернуться в каталог`.

Нужен именно проектный success-state, а не абстрактная зелёная галочка.

### 10. Empty / no results state

Нужно показать отдельный блок для случая, когда:

- поиск ничего не нашёл;
- фильтры слишком сузили выборку.

Этот блок не должен выглядеть как “ошибка”.
Он должен быть спокойным, полезным и в стилистике проекта.

## Что должно быть видно про поведение, даже если макет статичный

В одном HTML-макете нужно заложить подсказки о поведении:

- где hover-состояния;
- где secondary actions;
- где основной CTA;
- где reusable modal pattern;
- где проектный toast pattern;
- где активный фильтр;
- где selected state.

Если нужны анимации, они должны быть лёгкими и уже знакомыми проекту:

- fade/slide модалки;
- мягкий hover/raise карточки;
- спокойный state transition у badges и CTA.

Без декоративной “анимации ради анимации”.

## Какой формат макета нужен от дизайнера

Лучший вариант:

- один HTML-файл;
- внутри несколько секций одного сценария;
- каждая секция подписана;
- из макета видно, где:
  - default state;
  - filtered state;
  - detail state;
  - preview modal;
  - success state;
  - empty state.

То есть это скорее **presentation-layout одного экрана с состояниями**, чем “одна страница = одно состояние”.

## Что важно для последующей разработки

Этот макет потом не будет просто вставлен как есть.
Мы будем:

- изучать его как эталон;
- разбирать на блоки;
- собирать экран из уже существующих компонентов и визуальных паттернов проекта;
- при необходимости слегка доадаптировать детали под текущую UI-систему.

Поэтому дизайнеру нужно сразу дать установку:

- использовать композицию, которую можно разобрать;
- не плодить уникальные одноразовые элементы без необходимости;
- по возможности повторять типы блоков;
- делать макет как систему, а не как постер.

## Готовый текст ТЗ для передачи дизайнеру

Ниже текст, который можно почти без изменений отправить исполнителю.

---

Нужно создать **один HTML-макет экрана каталога контента** для web-версии проекта.

Важно: это должен быть не один красивый скрин, а **один HTML-артефакт, внутри которого показаны все ключевые состояния экрана**.

Экран нужен для поиска и добавления в личную библиотеку опубликованных:

- Комплексов
- Теорий

Нужно обязательно показать в одном макете:

- основной экран каталога;
- поиск и фильтры;
- карточки двух типов контента;
- состояния карточек:
  - можно добавить;
  - уже в библиотеке;
  - мой опубликованный объект;
- детальный просмотр элемента;
- preview перед Add to Library;
- success-state после Add to Library;
- empty-state при отсутствии результатов.

Очень важно:

- не придумывать новую визуальную систему;
- опираться на уже существующий интерфейс проекта;
- не использовать browser-default окна;
- если нужен modal, toast, badge, pill, фильтр, secondary action — использовать проектный по духу паттерн;
- делать макет так, чтобы его можно было потом разобрать на переиспользуемые блоки.

Для комплекса в preview нужно показать, что будут добавлены/переиспользованы:

- модуль(и)
- тема(ы)
- задание(я)
- теория(и)

Для теории нужен более простой preview.

Нужен HTML-макет desktop-first, но с пониманием адаптации под mobile.

Макет должен быть пригоден не только для презентации, но и как ориентир для реальной сборки экрана разработкой.

---

## Следующий шаг после макета

Когда макет будет готов, мы:

1. разберём его как систему состояний;
2. сверим с уже существующими UI-блоками проекта;
3. соберём рабочий экран каталога из существующих паттернов, а не будем слепо переносить HTML один-в-один.
