# План имплементации: прохождение комплексов в hosted_web

## Цель

Довести прохождение комплексов до полностью рабочего состояния в `hosted_web` как главную функцию проекта.

## Критерий готовности

Трек считается завершенным только если одновременно выполняется все ниже:

- пользователь может открыть комплекс, начать, пройти, поставить на паузу и продолжить с того же места
- корректно работают переходы между заданиями, итерациями, уровнями и ветками логики
- проверка ответов работает для всех типов заданий и уровней сложности
- финальные результаты корректно попадают в статистику и календарь
- все это устойчиво работает в hosted-окружении, а не только в локальном single-process режиме
- существует отдельный hosted e2e/smoke-контур, который это подтверждает

## Что входит в объем работ

В данный трек включается весь контур прохождения комплексов:

- вход в комплекс и старт сессии
- восстановление активной или paused-сессии
- выдача текущего задания
- сохранение и восстановление `ui_state`
- submit/check для всех типов заданий
- переходы `next`, повторы, retry, skip-логика
- логика итераций
- промежуточные результаты итерации
- финальные результаты
- запись в календарь
- запись в статистику комплексов
- hosted persistence
- hosted concurrency/isolation
- hosted smoke/e2e и документация готовности

## Фаза 1. Срочная стабилизация текущего потока

### Цель

Убрать явные регрессии и восстановить базовую целостность прохождения.

### Задачи

- исправить `500` на получении текущего задания
- восстановить зеленый полный интеграционный цикл прохождения
- нормализовать работу с ассетами задач для веба
- зафиксировать поведение `start_iteration`
- привести в порядок старт комплекса из UI-списка

### Ожидаемые изменения

- исправление текущих ошибок типизации и обвязки в session API
- явная валидация входных параметров старта
- преобразование путей task assets в hosted/web-safe формат
- предсказуемое поведение при невалидной стартовой итерации: либо нормализация, либо явная ошибка, но не silent-empty-session

### Критерий завершения

- зеленый полный интеграционный сценарий прохождения
- зеленые целевые Playwright-сценарии старта, паузы, resume и continue
- отсутствие `500` на базовом S1-потоке

## Фаза 2. Формализация домена "прохождение комплексов"

### Цель

Зафиксировать поддерживаемое поведение, чтобы дальше не чинить систему вслепую.

### Задачи

- составить canonical spec по состояниям сессии
- зафиксировать переходы `new -> active -> paused -> resumed -> iteration_results -> final_results -> completed/cancelled`
- зафиксировать обязательные persisted-поля
- зафиксировать supported matrix по типам заданий, уровням сложности, правилам продвижения между итерациями и retry/skip semantics

### Артефакты

- отдельный документ со спецификацией прохождения комплексов
- отдельный checklist definition of done for complex passage

### Критерий завершения

- у команды есть один эталонный документ, по которому можно писать тесты и принимать работу

## Фаза 3. Hosted persistence для сессий

### Цель

Убрать критическую зависимость от локальных JSON-сессий.

### Задачи

- спроектировать `HostedSessionRepository`
- вынести хранение сессий из `data/users/.../sessions/*.json`
- перенести в hosted storage метаданные сессии, текущее положение в комплексе, pause/resume state, iteration results, базу для final result payload и нужные UI-state данные
- подключить hosted repository через runtime/persistence settings, а не через локальную файловую ветку

### Точки изменений

- `desktop-app/services/session_repository.py`
- `desktop-app/services/adaptive_session_manager.py`
- `desktop-app/server.py`
- `desktop-app/api/session_api.py`

### Критерий завершения

- прохождение не зависит от локального диска
- рестарт процесса не теряет paused/active session state
- поведение одинаково в локальном hosted-mode и в реальном hosted deployment

## Фаза 4. Hosted persistence для статистики комплексов

### Цель

Сделать финальную запись результатов hosted-надежной.

### Задачи

- вынести `complex_statistics` из локального файла в hosted-backed storage
- определить источник истины: отдельный hosted stats repository или агрегирование из hosted session/progress data
- проверить согласованность с календарем и прогрессом
- сделать запись результатов идемпотентной

### Критерий завершения

- завершение комплекса стабильно и однократно обновляет статистику в hosted-среде
- статистика не зависит от локального файла `complex_statistics.json`

## Фаза 5. Runtime isolation и concurrency

### Цель

Убрать архитектурный долг с общим in-process controller и глобальным lock.

### Задачи

- убрать зависимость от одного глобального `ComplexSessionController`
- убрать зависимость от одного глобального `TaskController`
- перейти к per-session-safe модели
- разделить domain-логику, persisted state и request-time execution context
- обеспечить корректность при параллельных запросах одного пользователя, параллельных пользователях и нескольких воркерах/инстансах

### Практический подход

- сначала выделить domain state machine сессии
- затем сделать repository-backed load/transition/save
- только после этого убирать глобальный lock

### Критерий завершения

- корректность не держится на глобальной сериализации запросов
- hosted runtime масштабируем и изолирован по сессиям

## Порядок реализации

Рекомендуемый порядок работ:

1. Фаза 1. Срочная стабилизация текущего потока
2. Фаза 2. Формализация домена "прохождение комплексов"
3. Фаза 3. Hosted persistence для сессий
4. Фаза 4. Hosted persistence для статистики комплексов
5. Фаза 5. Runtime isolation и concurrency
6. Фаза 6. Полный тестовый контур прохождения комплексов
7. Фаза 7. Hosted документация и матрица готовности

Минимально обязательный путь, без которого migration нельзя считать завершенной:

1. исправить текущие регрессии
2. перевести session persistence на hosted
3. перевести stats persistence на hosted
4. закрыть hosted e2e для полного цикла

## Definition of done по этапам

Каждая фаза принимается только если есть одновременно:

- реализованы изменения в runtime
- есть тесты на новый контракт
- обновлена документация
- нет известных красных тестов в целевом контуре
- нет файловой зависимости там, где обещан hosted persistence
