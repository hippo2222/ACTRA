# Catalog Mockup Audit

> Historical note (`2026-04-13`): этот документ описывает первый mockup под copy-based `Add to Library`. Текущий целевой курс проекта смещён на linked-library model. Читать вместе с [implementation_memory.md](D:/Ai Ai/radioproject_git/docs/hosted_web_migration/implementation_memory.md) и [stage5_linked_library_plan.md](D:/Ai Ai/radioproject_git/docs/hosted_web_migration/stage5_linked_library_plan.md).

Дата обновления: `2026-04-09`

## Зачем нужен этот документ

Этот документ фиксирует скрупулёзный аудит макета [catalog-mockup.html](D:/Ai%20Ai/radioproject_git/frontend/Catalog/catalog-mockup.html) на соответствие:

- уже реализованному foundation в `Stage 4` и `Stage 5`;
- зафиксированным принципам из [implementation_memory.md](D:/Ai%20Ai/radioproject_git/docs/hosted_web_migration/implementation_memory.md);
- планируемой продуктовой семантике будущего каталога.

Важно:

- макет не должен закреплять неверное понимание модели данных;
- особенно осторожно нужно относиться к `модулям`, `темам`, `заданиям` и `теориям` внутри комплекса;
- не всё, что реально существует в import graph, обязательно должно становиться prominent-пользовательской метаданной на карточке каталога.

## Краткий вывод

Макет в целом движется в правильную сторону, но внутри него есть два разных уровня семантики, которые нельзя смешивать:

1. `Публичный каталог`
- верхнеуровневые publishable объекты: только `Комплекс` и `Теория`.
- пользователь ищет и фильтрует именно их.

2. `Внутренняя структура personal copy`
- при `Add to Library` комплекс может создать или переиспользовать `modules/topics/tasks/theories`.
- это уже не публичная сущность каталога, а внутренний graph будущей workspace-копии.

Главный спорный момент макета сейчас:

- `модули` и `темы` в нём местами показаны так, как будто это нормальная публичная размерность самого каталога;
- на самом деле по текущему plan/foundation это **не самостоятельные catalog entities**, а внутренние контейнеры complex import graph.

Из этого следует правило:

- в `Preview Add to Library` показывать `модули/темы` корректно;
- в `catalog cards` и, вероятно, в `detail panel` показывать их надо либо очень осторожно, либо вообще убрать до отдельного продуктового решения.

## Базовое продуктовое решение

Самый важный приоритетный вывод для каталога:

- универсальная единица, которой имеет смысл делиться ради цели проекта, — это `Комплекс`.

Почему:

- цель проекта — изучение теории через практическое применение знаний;
- `Комплекс` уже естественно связывает:
  - учебную цель;
  - практические задания;
  - структуру прохождения;
  - связанные теории;
- именно он лучше всего передаёт полноценный учебный сценарий, а не фрагмент.

Что из этого следует:

- `Теория` остаётся отдельным publishable объектом, но как вторичная единица обмена;
- `Задание`, `Тема` и `Модуль` не должны восприниматься как главные shareable units публичного каталога;
- если есть сомнение, что именно делать prominent в UI, по умолчанию центр тяжести должен смещаться в сторону `Комплекса`, а не его внутренних контейнеров.

## Что уже зафиксировано в реализации

На данный момент у нас уже зафиксировано:

- публичный каталог v1 содержит только `Комплексы` и `Теории`;
- `Add to Library` для комплекса импортирует задания и связанные контейнеры;
- автоматического merge по имени нет;
- reuse идёт только по `source lineage`;
- `Add to Library` идемпотентен на уровне конкретной `CatalogVersion`;
- `preview/status/execute` уже backend-реализованы для user-facing catalog flow.

Это значит, что экран каталога уже можно проектировать, но нельзя придумывать поверх него новую модель контента.

## Аудит по секциям

### 1. Основной экран каталога

Что соответствует:

- заголовок, поиск, фильтры по типу и статусу;
- разделение карточек по типам `Комплекс` / `Теория`;
- состояния `Можно добавить`, `В библиотеке`, `Моя публикация`;
- карточки с `Открыть копию` для идемпотентного состояния;
- наличие более плотной карточки и hover-demo как часть демонстрации состояния.

Что спорно:

- у карточек комплекса показаны `модули` как обычная user-facing метрика;
- это создаёт риск, что пользователь начнёт воспринимать `модуль` как публичную единицу каталога;
- по текущей архитектуре это не так.

Рекомендация:

- на карточке комплекса оставлять только безопасные верхнеуровневые признаки:
  - количество заданий;
  - наличие или отсутствие связанных теорий;
  - автор;
  - дата публикации;
  - статус относительно библиотеки;
- `модули` и `темы` не использовать как основную метрику карточки без отдельного product decision.

Дополнительный спорный момент:

- у теории используется метка вроде `Подробная`;
- такой density/richness metric в backend пока не закреплён как реальный контракт;
- если это останется в финальном UI, нужен отдельный field/derived metric;
- иначе лучше заменить на что-то, что реально существует.

Статус секции:

- `частично aligned, требует product cleanup`

### 2. Detail panel

Что соответствует:

- боковая панель как паттерн раскрытия объекта;
- автор, описание, summary, CTA;
- primary action как вход в preview, а не мгновенный импорт.

Что спорно:

- detail panel сейчас показывает:
  - `Модули`
  - `Темы`
  - `Задания`
  - `Теории`
- для `Preview` это нормально, для `Detail` это уже неочевидно.

Почему это спорно:

- `Detail panel` — это часть публичного каталога;
- если в ней prominently показывать `модули` и `темы`, мы визуально повышаем их до публичной семантики;
- но у нас пока нет решения, должны ли пользователь вообще видеть complex internals именно в этих терминах.

Приоритетное продуктовое правило здесь:

- если detail panel должна помогать понять, стоит ли брать объект себе, она должна прежде всего отвечать на вопрос:
  - “чему я научусь и как это будет применяться на практике?”
- а не на вопрос:
  - “из скольких внутренних контейнеров это собрано?”

Самый безопасный вариант:

- оставить в detail panel только:
  - `Задания`
  - `Связанные теории`
  - короткое описание учебной цели или практического фокуса
  - возможно `Версия` или `Дата публикации`
  - возможно общую метку вроде `Составной комплекс`

Допустимый, но более рискованный вариант:

- оставить `модули/темы` только в detail panel, но явно как вторичную internal structure;
- не дублировать это на карточках;
- перед этим принять явное решение, что complex structure допускается к показу пользователю.

Статус секции:

- `needs decision`

### 3. Preview: Комплекс

Что соответствует:

- это именно тот экран, где `модули/темы/задания/теории` показывать правильно;
- preview должен объяснять, что будет создано и что будет переиспользовано;
- preview обязан быть version-aware и сходиться с execute;
- уже реализованный backend именно это и умеет.

Почему здесь `модули` и `темы` уместны:

- здесь это не описание публичного объекта каталога;
- здесь это explanation layer для будущего graph import;
- пользователь видит последствия `Add to Library`, а не публичную типологию каталога.

Что важно оставить:

- `Комплекс`
- `Модули`
- `Темы`
- `Задания`
- `Теории`
- created/reused semantics
- пояснение, что совпадение имён не даёт auto-merge

Что важно не упростить слишком сильно:

- если убрать из complex preview `модули` и `темы`, пользователь не поймёт, почему после импорта в библиотеке появились дополнительные контейнеры;
- а это как раз одна из ключевых особенностей нашей системы.

Статус секции:

- `aligned`

### 4. Preview: Теория

Что соответствует:

- отдельное simplified preview;
- теория может добавляться отдельно от комплекса;
- создаётся личная копия пользователя.

Что ещё проверить позже при живой реализации:

- если `library-status` уже показывает existing copy, preview теории должен уметь переключаться в `open_existing`, а не только в create-copy сценарий.

Статус секции:

- `aligned`

### 5. Success

Что соответствует:

- success toast;
- success modal;
- CTA `Открыть копию`;
- возврат в каталог.

Что уже исправлено:

- success теперь описывает создание личной копии, а не абстрактное “добавление”;
- текст выровнен под реальную semantics, а не под generic marketplace-copy.

Что ещё важно помнить:

- success не должен обещать ничего про live sync с автором;
- это именно локализованная personal workspace copy.

Статус секции:

- `aligned`

### 6. В библиотеке

Что соответствует:

- отдельное идемпотентное состояние;
- явный переход в `Открыть копию`;
- отсутствие повторного создания дубля.

Что уже исправлено:

- состояние теперь явно привязано к `этой версии`, а не просто к абстрактному объекту;
- это соответствует нашему текущему backend contract.

Что важно не потерять:

- идемпотентность у нас на уровне `CatalogVersion`, а не “вообще когда-то добавлял что-то с таким названием”.

Статус секции:

- `aligned`

### 7. Empty state

Что соответствует:

- спокойное non-error пустое состояние;
- поиск и фильтры остаются видимыми;
- есть действие `Сбросить фильтры`.

Замечание:

- эта секция не вызывает архитектурных противоречий.

Статус секции:

- `aligned`

## Спорные места, которые надо решить до живой сборки экрана

### Вопрос 1. Нужно ли показывать `модули` и `темы` в публичном catalog detail?

Текущее состояние:

- в import preview это точно нужно;
- в catalog card это скорее лишнее;
- в detail panel вопрос открыт.

Рекомендация:

- пока считать `модули` и `темы` internal structure import graph;
- в публичных catalog surfaces не поднимать их до заметной пользовательской метрики;
- если захочется показать структуру комплекса, делать это позже отдельным осознанным решением.

### Вопрос 2. Нужна ли пользователю отдельная “насыщенность теории” как метрика?

Текущее состояние:

- макет её показывает;
- backend contract пока её не фиксирует.

Рекомендация:

- либо убрать;
- либо позже ввести отдельный реальный field/heuristic и только после этого показывать в UI.

### Вопрос 3. Какой detail-summary для комплекса считается каноническим?

Сейчас есть три возможных уровня:

1. Консервативный
- задания
- связанные теории
- дата
- автор

2. Средний
- задания
- связанные теории
- признак составной структуры

3. Глубокий
- модули
- темы
- задания
- теории

Рекомендация:

- для первой живой версии экрана брать `консервативный` или максимум `средний`.

## Решение, которое предлагается зафиксировать

До отдельного product decision считаем так:

- `Каталог` как публичный экран показывает только publishable-уровень:
  - `Комплекс`
  - `Теория`
- основная shareable learning unit каталога — `Комплекс`
- `Модули` и `Темы` не используются как prominent public metadata в карточках каталога.
- `Модули` и `Темы` допустимы:
  - в `Preview Add to Library` для комплекса;
  - возможно в будущих более глубоких деталях состава, если это будет отдельно утверждено.
- `Теория` не получает декоративные метрики, которые пока не поддержаны backend contract.

## Следующий правильный шаг

Перед началом живой сборки catalog UI нужно сделать ещё один проход по [catalog-mockup.html](D:/Ai%20Ai/radioproject_git/frontend/Catalog/catalog-mockup.html) уже не “на глаз”, а по этому аудиту:

- убрать или ослабить `modules/topics` в public catalog surfaces;
- оставить их в complex preview;
- решить судьбу `theory richness` метрики;
- после этого считать макет продуктово согласованным источником для реализации.

## Решения, зафиксированные после обсуждения

Дата фиксации: `2026-04-09`

Считаем утверждённым:

1. `Модули` и `Темы` в `detail panel` не показываются совсем.

2. Канонический public summary комплекса:
- количество заданий;
- наличие теории;
- количество теорий, если их больше двух.

3. Декоративная метрика теории вроде `подробная / средняя / насыщенная` убирается.

4. Главное сообщение complex-card:
- сколько заданий;
- есть ли теория;
- краткое описание комплекса, если оно задано.

5. Отдельный фильтр авторства `Все / Чужие / Мои публикации` в первой версии не нужен.

6. Отдельный блок “чему я научусь” в первой версии не обязателен.

7. Пользователю показывается только свежесть публикации, без явной version-метки.

8. `Теория` подаётся как вторичный тип с меньшим визуальным весом относительно `Комплекса`.

9. Количество связанных теорий показывается только если их больше двух.

10. `Detail panel` комплекса строится вокруг:
- описания;
- количества заданий;
- и, при необходимости, количества связанных теорий.
