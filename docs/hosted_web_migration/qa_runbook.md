# Hosted Web QA Runbook

Дата обновления: `2026-04-17`

Этот документ превращает `smoke_matrix.md` в практический ручной прогон-лист.
Формат простой: идём сверху вниз, для каждого сценария ставим один итоговый статус:
- `pass`
- `fail`
- `blocked`

## Как пользоваться

Для каждого сценария заполнять:

- `Status:`
- `Notes:`

Если сценарий упирается не в баг, а в незафиксированную продуктовую развилку, ставить `blocked`, а не `fail`.

## Набор пользователей

Нужны минимум два аккаунта:
- `Автор`
- `Потребитель`

Если есть готовые smoke-аккаунты, использовать их. Если нет, создать две отдельные hosted-учётки.

## Базовая подготовка

Перед прогоном:

1. Убедиться, что hosted runtime поднят и открывается `Welcome`.
2. Подготовить один комплекс автора с прикреплённой теорией.
3. Убедиться, что потребитель ещё не добавлял этот комплекс в библиотеку.
4. Очистить контекст прошлых прогонов, если он мешает интерпретации результатов.

## Прогон-лист

### 1. Hosted auth baseline

#### `AUTH-01` Вход и регистрация через `Welcome`

Шаги:
1. Открыть `Welcome` в чистой сессии браузера.
2. Переключиться в режим регистрации.
3. Создать нового пользователя с `display name + login + email + password`.
4. Выйти.
5. Войти этим же пользователем обратно.

Ожидаемый результат:
- пользователь регистрируется без legacy profile-picker;
- после регистрации виден verification-state, а не ложное “email уже подтвержден”;
- после входа попадает в hosted-приложение;
- logout/login не ломает request-scoped user flow.

Status:
Notes:

#### `AUTH-02` Подтверждение почты и forgot/reset password через `Welcome`

Шаги:
1. На только что созданном аккаунте дождаться экрана подтверждения почты.
2. Нажать `Отправить ещё раз` и убедиться, что повторная отправка не ломает state.
3. Открыть письмо подтверждения и перейти по ссылке.
4. Убедиться, что `Welcome` показывает успешное подтверждение.
5. На экране входа запустить `Забыли пароль?`.
6. Отправить письмо восстановления.
7. Открыть reset link из письма, задать новый пароль и войти им.

Ожидаемый результат:
- verification link подтверждает текущий email и убирает unverified state;
- повторная отправка verification email работает без странных ошибок;
- reset password работает только по валидному token flow и после смены пароля старый пароль больше не подходит.

Status:
Notes:

#### `AUTH-03` Смена email в `Settings` через pending-confirmation flow

Шаги:
1. Войти под существующим hosted пользователем с уже подтверждённой почтой.
2. В `Settings` указать новый email.
3. Убедиться, что текущий active email не заменился мгновенно и UI показывает pending state.
4. Нажать `Отправить ещё раз` для pending email.
5. Открыть письмо подтверждения нового адреса и перейти по ссылке.
6. Вернуться в `Settings` и проверить, что новый email стал active и confirmed.

Ожидаемый результат:
- смена email staged, а не мгновенная;
- неподтверждённый новый email не считается active;
- после подтверждения active email действительно меняется;
- при попытке указать занятый другим аккаунтом email UI не раскрывает лишнее про существование чужого аккаунта.

Status:
Notes:

### 2. Авторский publish flow

#### `PUB-01` Публикация комплекса

Шаги:
1. Зайти под `Автором`.
2. Открыть страницу `Комплексы`.
3. Найти локальный комплекс с прикреплённой теорией.
4. Открыть publish/manage publication flow.
5. Опубликовать комплекс в режиме `Публично`.

Ожидаемый результат:
- публикация завершается успешно;
- на карточке или в author UI видно, что комплекс опубликован;
- у публикации появляется корректный статус видимости.

Status:
Notes:

#### `PUB-02` Переключение visibility `public -> access_code -> private`

Шаги:
1. Не выходя из аккаунта автора, открыть управление публикацией того же комплекса.
2. Переключить visibility в `По коду`.
3. Скопировать или записать access code.
4. Переключить visibility обратно в `Публично`.
5. Затем переключить в `Приватно`.

Ожидаемый результат:
- каждое изменение visibility подтверждается без ошибки;
- UI показывает текущий режим доступа без рассинхрона;
- access code появляется для режима `По коду`.

Status:
Notes:

#### `PUB-03` Автор видит собственные публикации в `Каталоге`

Шаги:
1. Под `Автором` открыть `Каталог`.
2. Проверить опубликованный комплекс в режимах:
   - `Публично`
   - `По коду`
   - `Приватно`

Ожидаемый результат:
- автор видит собственную публикацию во всех трёх режимах;
- публикация не пропадает из author view только потому, что она не публичная.

Status:
Notes:

### 3. Consumer add/open flow

#### `CAT-01` Потребитель видит публичную публикацию автора

Шаги:
1. В отдельной сессии войти под `Потребителем`.
2. Открыть `Каталог`.
3. Найти комплекс автора, пока он в режиме `Публично`.

Ожидаемый результат:
- публикация видна в списке;
- карточка и detail не выглядят как owned-by-current-user.

Status:
Notes:

#### `ADD-01` Добавление комплекса из каталога

Шаги:
1. Под `Потребителем` открыть detail комплекса автора в `Каталоге`.
2. Нажать `Добавить в библиотеку`.
3. Дождаться успешного завершения.

Ожидаемый результат:
- добавление завершается успешно;
- при повторном нажатии не создаются дубли;
- UI переключается в состояние “уже в библиотеке” или эквивалентное.

Status:
Notes:

#### `ADD-02` Добавление комплекса по коду со страницы `Комплексы`

Шаги:
1. Под `Автором` перевести публикацию комплекса в режим `По коду`.
2. Скопировать access code.
3. Под `Потребителем` открыть страницу `Комплексы`.
4. Запустить flow добавления по коду.
5. Вставить access code и завершить добавление.

Ожидаемый результат:
- комплекс добавляется без перехода в `Каталог`;
- UI не сообщает ложных ошибок `not found` или `forbidden`;
- комплекс появляется в библиотечной части `Комплексов`.

Status:
Notes:

#### `ADD-03` Связанная теория подтягивается вместе с комплексом

Шаги:
1. После `ADD-01` или `ADD-02` остаться под `Потребителем`.
2. Открыть карточку добавленного комплекса на странице `Комплексы`.
3. Проверить индикацию, что у комплекса есть связанная теория.

Ожидаемый результат:
- UI показывает наличие связанной теории;
- не возникает рассинхрона “теория есть”, но фактически ничего не подтянулось.

Status:
Notes:

#### `OPEN-01` Потребитель открывает linked complex

Шаги:
1. Под `Потребителем` открыть добавленный комплекс из своей библиотеки.
2. Если для комплекса есть runtime/read surface, открыть его штатным способом.

Ожидаемый результат:
- комплекс открывается как linked content;
- не создаётся впечатление скрытой personal copy по умолчанию.

Status:
Notes:

#### `OPEN-02` Потребитель открывает attached theory у linked-комплекса

Шаги:
1. Под `Потребителем` на странице `Комплексы` открыть attached theory у добавленного комплекса.
2. Если теория открывается в отдельном viewer, дождаться полной загрузки.

Ожидаемый результат:
- теория открывается без `404` на чужой `theory-library` entry;
- не возникает ошибка вида `theory_library_entry_not_found`;
- если отдельной theory entry нет, должен сработать embedded fallback.

Status:
Notes:

### 4. Author-side reopen checks

#### `OPEN-03` Автор открывает attached theory у собственного комплекса

Шаги:
1. Переключиться обратно на `Автора`.
2. На странице `Комплексы` открыть attached theory у того же опубликованного комплекса.

Ожидаемый результат:
- теория открывается у автора;
- stale `linked_library` ссылка не ломает сценарий;
- если library entry уже невалидна, используется fallback к source workspace theory.

Status:
Notes:

### 5. Theory Center visibility

#### `TC-01` Потребитель не видит чужие неимпортированные материалы

Шаги:
1. Под `Потребителем` открыть `Центр теории`.
2. Переключить scope/фильтры так, чтобы были видны комплексы и теории.
3. Сравнить, что видно до и после добавления комплекса автора в библиотеку.

Ожидаемый результат:
- до импорта не светятся чужие неимпортированные комплексы и теории;
- после добавления видны только свои или реально импортированные/linked сущности.

Status:
Notes:

#### `TC-02` Linked content не выглядит как редактируемый локальный объект

Шаги:
1. Под `Потребителем` открыть linked theory или linked complex из `Центра теории`.
2. Проверить наличие edit-actions и формулировок, подразумевающих владение.

Ожидаемый результат:
- linked content визуально отделён от authoring surface;
- пользователь не видит ложного affordance редактирования чужого контента.

Status:
Notes:

### 6. Visibility and access transitions

#### `ACC-01` Existing linked entry требует код после visibility change

Шаги:
1. Под `Потребителем` убедиться, что комплекс уже добавлен в библиотеку.
2. Под `Автором` переключить visibility комплекса в `По коду`.
3. Вернуться к `Потребителю`.
4. Попробовать открыть linked complex и attached theory.
5. Если UI просит код, ввести актуальный access code.

Ожидаемый результат:
- linked entry не исчезает бесследно;
- контент не остаётся вечной автономной копией;
- доступ либо блокируется до ввода кода, либо корректно переавторизуется по коду.

Status:
Notes:

#### `ACC-02` Existing linked entry перестаёт открываться после `private`

Шаги:
1. Под `Автором` перевести публикацию в `Приватно`.
2. Под `Потребителем` снова попытаться открыть linked complex и attached theory.

Ожидаемый результат:
- linked entry остаётся reference или хотя бы не создаёт ложного впечатления, что доступ всё ещё есть;
- контент не открывается как автономная вечная копия, если продуктом не задумано иное.

Status:
Notes:

### 7. Surface ownership sanity

#### `OWN-01` У non-author комплекса нет `Редактировать`

Шаги:
1. Под `Потребителем` открыть страницу `Комплексы`.
2. Найти чужой linked-комплекс автора.
3. Проверить actions на карточке и в detail.

Ожидаемый результат:
- action `Редактировать` отсутствует для чужого комплекса.

Status:
Notes:

### 8. Deletion behavior

#### `DEL-01` Удаление linked-комплекса из библиотеки

Шаги:
1. Под `Потребителем` удалить linked-комплекс из своей библиотеки.
2. Обновить страницу `Комплексы`.
3. Проверить, исчез ли комплекс из library section.

Ожидаемый результат:
- complex-library entry удаляется;
- комплекс больше не выглядит как сохранённый в библиотеке;
- runtime-linked хвосты не мешают повторному добавлению.

Status:
Notes:

#### `DEL-02` Поведение связанной теории после удаления linked-комплекса

Шаги:
1. После `DEL-01` под тем же `Потребителем` открыть `Центр теории` или другие места, где может быть видна связанная теория.
2. Проверить, осталась ли linked theory entry.

Ожидаемый результат:
- это сценарий на фиксацию фактического поведения;
- если теория остаётся, это не обязательно баг, но должно быть явно записано;
- если поведение выглядит противоречиво, ставить `blocked`, а не угадывать продукт.

### 9. Hosted fallback pass

#### `FB-01` Базовый smoke в fallback-режиме

Шаги:
1. Поднять runtime в состоянии, где Postgres недоступен и приложение уходит в compatibility fallback.
2. Повторить минимально:
   - вход;
   - открытие `Каталога`;
   - открытие `Комплексов`;
   - открытие `Центра теории`;
   - открытие already-added linked complex;
   - открытие attached theory.

Ожидаемый результат:
- сценарии не деградируют в необъяснимые пустые экраны или 404;
- если fallback не поддерживает часть поведения, это должно быть явно видно и зафиксировано в notes.

Status:
Notes:

#### `FB-02` Attached theory в fallback-режиме

Шаги:
1. Оставаться в fallback-режиме.
2. Под `Потребителем` открыть attached theory у linked-комплекса.
3. Под `Автором` открыть attached theory у собственного комплекса.

Ожидаемый результат:
- не происходит перехода на чужую `theory-library` entry;
- author и consumer сценарии не ломаются из-за stale library references.

## Что пока не прогонять как `fail`

Следующие темы сейчас считаются открытыми продуктово-техническими развилками:

- нужен ли отдельный apply-migration path, если future inventory перестанет быть нулевым;
- насколько aggressively потом убирать compatibility read-fallback, если Postgres недоступен.

Если прогон упирается в одну из этих точек, ставить `blocked` и выносить на отдельное решение.
