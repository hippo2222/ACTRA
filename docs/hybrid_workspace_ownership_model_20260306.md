# Hybrid Workspace + Ownership Model - 2026-03-06

## Status

- Status: `product-decision`
- Date: `2026-03-06`
- Scope: `Complexes`, `Microcards`, `Theory Hub`, профили, связанные authoring/user surfaces
- Purpose: зафиксировать единую модель данных и UX для проекта, чтобы экосистема вокруг теории не распадалась на противоречивые куски.

## Decision

Продукт принимает модель `Hybrid workspace + ownership`.

Это означает:

- профиль не создаёт полностью изолированный мир;
- профиль изолирует личное обучение, прогресс и персональное состояние;
- учебный контент живёт в общей локальной библиотеке (`workspace-level`);
- у контента должна быть явная ownership-метка, чтобы пользователь понимал, что создано им, что общее и откуда это взялось.

Короткая формула решения:

- `Workspace-level`: общая библиотека учебного контента.
- `Profile-level`: личный прогресс и персональные рабочие состояния.
- `Ownership-level`: авторство, происхождение и, при необходимости позже, видимость.

## Why This Is The Right Model

Для текущего проекта эта модель лучше, чем `full profile-isolation`, по четырём причинам:

1. Она лучше поддерживает цельную экосистему вокруг теории: `module -> topic -> theory -> complex -> session -> results -> statistics -> repeat`.
2. Она не заставляет дублировать один и тот же учебный материал по профилям.
3. Она совпадает с фактическим направлением текущей архитектуры, а не требует ломать её ради искусственной "приватности".
4. Она позволяет позже добавить более зрелые механики владения и фильтрации без миграции всего продукта в отдельные workspace на профиль.

## Current Architectural Facts

Сейчас система уже частично ведёт себя как `hybrid`, даже если это ещё не сформулировано продуктово.

- `Complexes` хранятся глобально в `data/complexes/complexes.json` через `desktop-app/services/complex_service.py`.
- `ComplexService` не разделяет каталог по `user_id`.
- `Microcards` уже используют смешанную схему:
  - контент колод хранится глобально в `data/microcards/decks`;
  - review state и review events хранятся по пользователю в `data/users/{user_id}/microcards`;
  - это прямо зафиксировано в `desktop-app/services/microcards_service.py`.
- В `Microcards` ownership-метаданные уже частично существуют (`created_by_user_id`), но единая vocabulary-модель для всего продукта ещё не доведена.

Вывод: правильный шаг сейчас не "перевести всё в жёсткую изоляцию", а довести уже существующий `hybrid` до ясной и взрослой модели.

## Non-Goals

Что это решение сознательно не делает:

- не вводит `full profile-isolation` для `Complexes`, `Microcards`, `Theories` и связанного каталога;
- не обещает приватность контента там, где продукт пока не умеет её обеспечивать;
- не превращает профили в независимые workspace;
- не запускает тяжёлую миграцию хранения ради релиза.

## Scope Matrix

### Workspace-Level Entities

Это общая локальная библиотека контента. Она должна быть доступна всем профилям установки, если отдельно не введена приватность.

- модули;
- темы;
- задания;
- теории;
- связи theory <-> topic <-> complex;
- комплексы;
- колоды `Microcards` и содержимое карточек;
- результаты импорта и authoring-артефакты, которые порождают повторно используемый учебный контент.

### Profile-Level Entities

Это личный слой обучения. Он должен быть строго привязан к конкретному профилю.

- текущие и сохранённые сессии;
- прогресс и mastery;
- календарное планирование;
- статистика;
- quick access и персональные рекомендации;
- персональные настройки;
- recovery/draft-состояния, если они относятся к личной незавершённой работе;
- review state и review events для `Microcards`.

### Ownership-Level Metadata

Это метаслой, который объясняет происхождение и ответственность за контент.

Базовый набор полей, который стоит принять как единый стандарт:

- `created_by_user_id`
- `updated_by_user_id`
- `created_via`
- `updated_at`
- `created_at`

Рекомендуемые значения `created_via`:

- `manual_editor`
- `theory_hub`
- `text_import`
- `analysis_auto`
- `system_seed`

Опциональный следующий слой, но не обязательный для ближайшего батча:

- `visibility: workspace | private`

## Product Contract

Если продукт остаётся в модели `Hybrid workspace + ownership`, то интерфейсы должны говорить правду.

Обязательные UX-правила:

- не называть `Complexes` или `Microcards` "моими" по умолчанию, если они workspace-level;
- в пустых состояниях различать:
  - "в библиотеке ещё нет контента";
  - "у тебя пока нет личного прогресса";
- на экранах списка и деталей показывать происхождение или автора контента;
- не использовать один только цвет как единственный носитель смысла ownership/visibility;
- любые badge/filter-элементы должны жить на существующих semantic color tokens и сохранять контрастность в разных theme schemes;
- `Welcome` и `Main` должны честно объяснять, что профиль хранит личные данные обучения, а не отдельную копию всей библиотеки.

## UX Implications By Surface

### `Welcome`

Нужно объяснять:

- профиль хранит прогресс, статистику, настройки и текущие сессии;
- библиотека учебного контента может быть общей для устройства.

### `Complexes`

Нужно добавить и постепенно усилить:

- ownership badge;
- фильтры `Все / Моё / Создано мной`;
- честные empty states для случаев:
  - комплексов нет вообще;
  - комплексы есть, но у текущего профиля нет активности;
- позже, при необходимости, отдельный признак `private`.

### `Microcards`

Нужно явно показать, что:

- колоды могут быть общими;
- прогресс повторения у каждого профиля личный;
- "новая колода в библиотеке" и "мне есть что повторять" - это разные сигналы.

### `Theory Hub`

Нужно поддерживать единый граф:

- теория знает связанные темы и комплексы;
- связанные комплексы показывают ownership/source;
- переходы из theory context не должны создавать ощущение, что пользователь перескакивает между "чужими" и "своими" мирами без объяснения.

## Decision Rules For Future Features

По умолчанию новая сущность должна классифицироваться так:

- если это повторно используемый учебный материал, она `workspace-level`;
- если это состояние обучения, история, рекомендации, сессия или статистика, она `profile-level`;
- если пользователь должен понимать происхождение контента, нужен ownership-метаслой;
- если для сущности действительно нужна приватность, это должно быть отдельным продуктовым решением, а не молчаливым побочным эффектом хранения.

Простое правило для команды:

- `content is shared`
- `learning is personal`
- `ownership is explicit`

## Rollout Plan

### Phase 1. Formalize Without Breaking Storage

Цель: довести модель до честного продукта без большой миграции.

- выровнять словарь в UI и docs;
- добавить ownership-поля в `Complexes`;
- нормализовать ownership vocabulary в `Microcards`;
- показать badges/source labels на ключевых экранах;
- обновить тексты `Welcome`/`Main`, чтобы профиль не обещал ложную изоляцию контента.

### Phase 2. Add Usable Ownership UX

Цель: сделать модель не только честной, но и удобной.

- фильтры `Все / Моё / Создано мной`;
- сортировки по ownership/source;
- отдельные блоки "связано с этой теорией" и "создано мной";
- более точные empty states и summary-объяснения.

### Phase 3. Optional Privacy Layer

Цель: добавить приватность только если она действительно нужна продукту.

- `visibility: workspace | private`;
- safe duplication/share flow;
- ясные ограничения для private-content в theory graph и related views;
- только после этого можно обсуждать частичную изоляцию без превращения продукта в набор отдельных миров.

## What To Avoid

- не вводить жёсткую profile-isolation для `Complexes` и `Microcards` как "быстрый фикс";
- не смешивать в одной карточке сигналы "это моё" и "это общее" без явной подписи;
- не строить ownership UX только на цвете;
- не обещать пользователю приватность, которой ещё нет;
- не плодить дубли одного и того же теоретического материала между профилями.

## Immediate Backlog Slice

Следующие шаги, которые логично вытекают из этого решения:

1. Добавить ownership metadata в `Complexes` и унифицировать vocabulary с `Microcards`.
2. Вывести `created_by` / `source` badges в `Complexes`, `Microcards`, `Theory Hub`.
3. Исправить onboarding copy на `Welcome` и `Main`: профиль хранит личное обучение, а не отдельную библиотеку.
4. Добавить базовые фильтры `Все / Моё` там, где это уже даёт реальную пользу без перегруза.
5. Отложить `visibility/private` до отдельного product batch.

## Bottom Line

`Hybrid workspace + ownership` - это не компромисс "лишь бы не переделывать".

Для текущего проекта это и есть наиболее логичная взрослая модель:

- она поддерживает единую экосистему вокруг теории;
- она совпадает с тем, как архитектура уже начинает работать;
- она даёт ясную дорогу к ownership UX;
- она не убивает связность системы ради искусственной изоляции.
