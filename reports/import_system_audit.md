# Аудит системы импорта готовых заданий

**Дата:** 2026-02-12  
**Область:** Импорт заданий из ZIP-архивов (экспорт с другой машины → импорт на текущую)

## Архитектура системы

Система состоит из трёх слоёв:

| Слой | Файлы | Роль |
|------|-------|------|
| **Frontend** | `import_manager.js`, `dashboard.js` | 4-шаговый визард (режим → ввод → превью → импорт) |
| **API** | `server.py` — маршруты `/api/editor/import/*`, `/api/editor/export/*` | Валидация, парсинг, NDJSON-стриминг прогресса |
| **Service** | `import_export_service.py` | ZIP-безопасность, конфликты, атомарный импорт |
| **Parsers** | `task_import_parser.py` + 5 парсеров (`open_answer`, `sequence`, `click_text`, `click_words`, `test_import`) | Текстовый импорт из маркерного формата |

Два режима импорта:
1. **Из текста** — пользователь вставляет текст с маркерами (`@OPEN_ANSWER`, `@SEQUENCE` и т.д.)
2. **Из архива** — загрузка ZIP, экспортированного с другой машины

## БАГИ (BUG)

### BUG-1: `import_tasks_atomic` не атомарна — нет rollback при частичном сбое
**Файл:** `import_export_service.py:350-481`  
**Серьёзность:** Высокая  
Метод называется `import_tasks_atomic`, но при сбое на задаче N ранее импортированные задачи 1..N-1 остаются на диске. Код делает `errors_count += 1` и продолжает цикл — никакого отката нет. В отличие от текстового `import_execute` (в `server.py:4235-4256`), где rollback реализован. Архивный путь лишён этой защиты.

### BUG-2: `extractall()` без фильтрации — обход `ALLOWED_EXTENSIONS`
**Файл:** `import_export_service.py:383-384`  
**Серьёзность:** Средняя  
`_validate_zip_security` проверяет вложенность и размер, но **не фильтрует по расширению**. После валидации `extractall()` распаковывает абсолютно всё, включая `.exe`, `.bat`, `.py` и прочие файлы, которые не в `ALLOWED_EXTENSIONS`. Фильтр `ALLOWED_EXTENSIONS` объявлен, но нигде не применяется при распаковке.

### BUG-3: `_check_task_dependencies` — ложные срабатывания на строках-не-путях
**Файл:** `import_export_service.py:283-317`  
**Серьёзность:** Низкая  
Рекурсивный `scan_for_images` ищет **любую строку**, оканчивающуюся на `.jpg`, `.png` и т.д. Если в JSON-поле есть текст вроде `"Снимок сделан в формате .jpg"`, это вызовет ложную ошибку "Missing images". Нет проверки, является ли строка ключом `image`/`src`/`url` — сканируются все значения.

### BUG-4: Экспорт в текст (`/api/editor/export/text`) теряет error_indices для `word_errors`
**Файл:** `server.py:3919-3923`  
**Серьёзность:** Средняя  
Для `click` с `mode == "text_errors"` или `"word_errors"` экспортируется только текст, но **не экспортируются `error_spans` / `error_indices`**. При обратном импорте этого текста через `@CLICK_WORDS` парсер не сможет восстановить ошибки, если в тексте нет `[слово]`-маркировки. Цикл round-trip (экспорт → импорт) теряет данные.

### BUG-5: `_validate_single_task` у `OpenAnswerParser` мутирует `self.warnings` — стейт утекает между задачами
**Файл:** `open_answer_parser.py:122-166`, аналогично в `click_text_parser.py`, `click_words_parser.py`, `sequence_parser.py`  
**Серьёзность:** Низкая  
`_validate_single_task` вызывается из базового `validate_tasks`, но warnings аккумулируются в `self.warnings` без привязки к текущему вызову `parse_text`. Если парсер переиспользуется (а в `import_parse` создаётся новый экземпляр каждый раз — сейчас безопасно), warnings от предыдущего парсинга могут утечь. Потенциальная проблема при будущем рефакторинге.

### BUG-6: Manifest `app_version` захардкожена как `"1.0.0"`
**Файл:** `import_export_service.py:103`  
**Серьёзность:** Низкая  
Не читается реальная версия из `task_system/VERSION` или `pyproject.toml`. Невозможно определить совместимость при импорте на машине с другой версией.

## СЛАБЫЕ МЕСТА (WEAK)

### WEAK-1: Нет проверки совместимости версий при импорте архива
**Файл:** `import_export_service.py:126-181`  
Manifest содержит `app_version`, но при валидации она **полностью игнорируется**. Если формат задач изменится в будущей версии, импорт молча сломает данные.

### WEAK-2: Кэш архивов — утечка памяти и отсутствие лимита
**Файл:** `server.py:1257-1271`  
`_import_archive_cache` — глобальный dict без ограничения размера. При массовом использовании (или атаке) можно заполнить диск и RAM. `_cleanup_import_cache()` вызывается только при следующем `/check` — нет фонового сборщика.

### WEAK-3: `import_tasks_atomic` — нет `skip_errors` логики
**Файл:** `import_export_service.py:350-476`  
Параметр `skip_errors` передаётся в `params`, но **нигде не используется** в теле метода. Все ошибки всегда пропускаются (try/except → `errors_count += 1`).

### WEAK-4: Нет валидации типа задания при архивном импорте
**Файл:** `import_export_service.py:213-281`  
`_analyze_task_in_archive` проверяет наличие `id`, проверяет изображения и конфликты, но **не валидирует тип задания** и структуру `content`. Можно импортировать JSON с `type: "GARBAGE"` — он пройдёт как `valid`.

### WEAK-5: Конфликт-детекция основана на полном MD5 JSON — хрупкая
**Файл:** `import_export_service.py:340-344`  
Любое несущественное отличие (пробел, порядок несортируемого поля) приведёт к определению "overwrite" вместо "duplicate". `sort_keys=True` помогает, но вложенные списки (elements, options) не сортируются.

### WEAK-6: Нет прогресс-бара на фронтенде при архивном импорте
**Файл:** `import_manager.js:1070-1131`  
Прогресс-стриминг приходит через NDJSON, но отображается только в тексте кнопки: `btn.textContent = "Импорт... 50%"`. Нет визуального прогресс-бара. При большом количестве задач UX страдает.

### WEAK-7: `_find_task_in_storage` — полный скан O(N) на каждую задачу
**Файл:** `import_export_service.py:319-338`  
Для каждой задачи из архива вызывается `load_modules()` и перебираются все модули → темы → задачи. При 100 задачах в архиве и 1000 в хранилище — 100 000 итераций. Нужен индекс по ID.

### WEAK-8: Нет guest-проверки на маршрутах `/api/editor/import/*` и `/api/editor/export/tasks`
**Файл:** `server.py:1220-1382`  
Маршруты `import_check`, `import_confirm`, `export_tasks` не проверяют `_headless_app_ctx.user_id == "guest"`, в отличие от `create_editor_task`, `delete_editor_tasks` и т.д. Гость может экспортировать/импортировать.

## ОТСУТСТВУЮЩИЙ ФУНКЦИОНАЛ (MISSING)

### MISSING-1: Нет UI для выбора разрешения конфликтов при архивном импорте
**Файл:** `import_manager.js:224-233`  
При архивном импорте шаг 2 — спиннер валидации, затем сразу шаг 3 (превью). Конфликтные задачи отображаются на карточках, но пользователь **не может выбрать действие для конкретного конфликта** (пропустить/перезаписать/новый ID). Есть только глобальный `conflict-resolution-select` — одно решение на все конфликты.

### MISSING-2: Нет поддержки `error_detection` с `draw`-аннотациями при импорте/экспорте
Тип задачи `click` с `mode == "draw"` (рисование на изображении) полностью отсутствует в парсерах и в текстовом экспорте. Такие задачи нельзя ни экспортировать в текст, ни импортировать.

### MISSING-3: Нет dry-run режима для архивного импорта
Нет способа увидеть, что именно будет изменено, до подтверждения. Шаг валидации (`/check`) показывает конфликты, но не показывает diff между существующей и новой версией задачи.

### MISSING-4: Нет поддержки экспорта в ZIP из фронтенда для одной темы/модуля целиком
**Файл:** `dashboard.js:1146-1192`  
Экспорт возможен только для выбранных (selected) задач через selection mode. Нет кнопки "Экспортировать всю тему" или "Экспортировать весь модуль" в контекстном меню.

### MISSING-5: Нет логирования/истории импортов
Метаданные `meta.imported = true` и `meta.import_date` записываются в `task.json`, но нет единого журнала импортов (кто, когда, из какого файла, сколько задач). При расследовании проблем невозможно восстановить историю.

### MISSING-6: Нет валидации ссылок на изображения при текстовом импорте
Текстовый импорт (из маркеров `@OPEN_ANSWER` и т.д.) не проверяет и не обрабатывает изображения вообще. Если в задаче типа `click` нужно изображение, через текстовый импорт его невозможно добавить.

### MISSING-7: Manifest не сохраняется после импорта
**Файл:** `import_export_service.py:382-466`  
`manifest.json` из архива парсится при валидации, но **не сохраняется** ни на диск, ни в метаданные импортированных задач. Теряется информация о источнике.

### MISSING-8: Нет поддержки частичного экспорта настроек/сложности
Экспорт копирует всю папку задачи, включая `task.json`, но **не включает** связанные данные: настройки сложности из `difficulty_config.json`, прогресс, статистику. На другой машине задача импортируется "голой".

## УЛУЧШЕНИЯ (IMPROVE)

### IMPROVE-1: Фильтрация файлов при `extractall` — белый список расширений
Заменить `zf.extractall(temp_extract_dir)` на поштучную распаковку с проверкой `ALLOWED_EXTENSIONS`. Это закроет BUG-2.

### IMPROVE-2: Batch-оптимизация `_find_task_in_storage`
Загрузить `load_modules()` один раз, построить `dict[task_id → path]` и переиспользовать для всех задач архива. Закроет WEAK-7.

### IMPROVE-3: Визуальный прогресс-бар при импорте
Заменить текст на кнопке на полноценный прогресс-бар в UI (шаг 4 или оверлей). Закроет WEAK-6.

### IMPROVE-4: Per-task конфликт-резолюция
На шаге 3 (превью) для каждой конфликтной карточки показать dropdown: "Пропустить / Перезаписать / Новый ID". Закроет MISSING-1.

### IMPROVE-5: Round-trip тест (export → import → compare)
Добавить интеграционный тест: экспортировать задачу в текст, импортировать обратно, сравнить `content`. Выявит BUG-4 и подобные потери данных.

### IMPROVE-6: `TestImportParser` — `_validate_single_task` не реализован
**Файл:** `test_import_parser.py`  
Класс наследует `TaskImportParser` (ABC), но метод `_validate_single_task` **не определён**. Это нарушает контракт ABC. Работает только потому, что `validate_tasks` не вызывается напрямую при текстовом импорте (валидация идёт через `_validate_with_task_type` в server.py). Но при прямом вызове `parser.validate_tasks()` — `TypeError`.

### IMPROVE-7: Унифицировать `correct` vs `is_correct` в опциях click
Парсер `ClickTextParser` генерирует `{correct: true}`, а `_normalize_click_import_data` ожидает `{is_correct: true}`. Нормализация работает (`opt.get("is_correct", opt.get("correct", False))`), но лучше привести к единому формату в парсерах.
