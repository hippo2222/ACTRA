# Аудит механизма паузы комплексов

**Дата:** 2025-02-11  
**Область:** Пауза/возобновление прохождения комплексов  

---

## 1. Обзор архитектуры

### Компоненты, участвующие в механизме паузы:

| Слой | Файл | Роль |
|------|------|------|
| **Модель** | `complex_models.py` | Поля `paused`, `paused_at` в `ComplexSession` |
| **Сервис** | `adaptive_session_manager.py` | `pause_session()`, `resume_session()` |
| **API-фасад** | `session_api.py` | `pause_session()`, `resume_session()` — обёртки |
| **HTTP** | `server.py` | Эндпоинты `/pause`, `/resume`, guards на `/submit`, `/next` |
| **Репозиторий** | `session_repository.py` | Персистенция сессии в JSON |
| **Фронтенд (сессия)** | `S1/index.html`, `session-controls.js`, `ui-helpers.js`, `main.js` | Модалки паузы/возобновления, блокировка действий |
| **Фронтенд (список)** | `Complexes/index.html` | Бейдж "На паузе", кнопка "Продолжить" |
| **Фронтенд (главная)** | `MainLogic.js` | Quick-access карточки с индикацией паузы |

### Текущий flow:

1. **Пауза**: Пользователь нажимает "← К списку" → модалка → "Поставить на паузу и выйти"  
   → `POST /api/session/{id}/pause` → `session.paused = True, paused_at = now` → сохранение в JSON → redirect на `/ui/complexes`

2. **Возобновление**: На странице комплексов кнопка "Продолжить" → redirect на `/ui/session/{id}` → `GET /api/session/{id}/task` с `auto_resume=True` → снимает паузу → загружает задание

3. **Защита**: Submit и Next проверяют `session.paused` → HTTP 409 → фронтенд показывает модалку resume

## 2. Найденные дефекты (БАГИ)

### BUG-1: `pause_session()` НЕ удаляет сессию из `_active_sessions`, вопреки docstring

**Файл:** `adaptive_session_manager.py:398-418`  
**Серьёзность:** Средняя  

Docstring гласит: *"удаляет из активных сессий в памяти"*, но код этого **не делает**:

```python
def pause_session(self, session_id: str) -> None:
    session = self._active_sessions.get(session_id)
    if not session:
        return
    session.paused = True
    session.paused_at = datetime.utcnow()
    self.session_repository.save_session(session, session.user_id)
    # ← Нет удаления из _active_sessions!
```

**Последствия:** Сессия остаётся в памяти, что само по себе не критично (resume находит её), но вводит в заблуждение и противоречит заявленному контракту. При перезапуске сервера сессия восстановится из файла с `paused=True` корректно.

**Решение:** Либо удалить из docstring упоминание удаления, либо действительно удалять из `_active_sessions` (тогда `resume_session()` загрузит из файла).

---

### BUG-2: `cancel_session()` не работает для паузированных сессий, если сервер перезапустился

**Файл:** `adaptive_session_manager.py:451-486`  
**Серьёзность:** Средняя  

```python
def cancel_session(self, session_id: str) -> bool:
    session = self._active_sessions.pop(session_id, None)
    if not session:
        return False  # ← Если сессии нет в памяти, возвращает False
```

После перезапуска сервера `_active_sessions` пуст. Паузированная сессия существует только в файле JSON. `cancel_session()` не пытается загрузить её из файла → возвращает `False` → файл сессии на диске **не удаляется** → сессия "висит" навечно.

**Решение:** Добавить fallback-загрузку из `session_repository.load_session_by_session_id()`, аналогично `resume_session()`.

---

### BUG-3: Удаление комплекса не очищает паузированные сессии

**Файл:** `complex_service.py:269-288`, `server.py:2394-2403`  
**Серьёзность:** Средняя  

`delete_complex()` удаляет только запись комплекса из кэша и файла. JSON-файл сессии `data/users/{user_id}/sessions/{complex_id}.json` **остаётся на диске**. При следующем сканировании `/api/sessions/active` паузированная сессия удалённого комплекса будет возвращена и показана в UI.

`restore_session()` в `ComplexSessionController` проверяет существование комплекса и удаляет сессию, но это происходит только при попытке открыть сессию, а не при отображении списка.

**Решение:** В `delete_complex_endpoint()` после удаления комплекса вызывать `session_repository.delete_session(complex_id, user_id)`.

---

### BUG-4: `duration_seconds` в итоговой статистике **включает время паузы**

**Файл:** `adaptive_session_manager.py:2132-2136`  
**Серьёзность:** Высокая (искажение статистики)  

```python
if session.end_time and session.start_time:
    duration_seconds = int((session.end_time - session.start_time).total_seconds())
```

Если пользователь поставил сессию на паузу на 2 часа, а потом продолжил и завершил за 10 минут, `duration_seconds` покажет 2 часа 10 минут. Аналогично, `iteration_durations` включает время паузы.

**Решение:** Ввести поле `total_pause_duration` (суммарное время пауз) в `ComplexSession` и вычитать его при расчёте длительностей. Альтернатива: хранить массив `pause_intervals: List[Tuple[datetime, datetime]]`.

---

### BUG-5: `auto_resume=True` в `GET /task` снимает паузу без явного согласия пользователя

**Файл:** `session_api.py:259-282`, `server.py:2492`  
**Серьёзность:** Низкая (UX-проблема)  

```python
@app.route("/api/session/<string:session_id>/task", methods=["GET"])
def get_current_task(session_id: str) -> Any:
    data = session_api.get_current_task(session_id, auto_resume=True)
```

При переходе на страницу сессии GET-запрос автоматически снимает паузу. Это означает, что если пользователь просто откроет URL сессии (например, из закладки), пауза снимется автоматически. Фронтенд в `main.js:137-142` проверяет `response.paused` и показывает модалку, но `auto_resume` уже снял паузу до этого.

**Решение:** Не использовать `auto_resume=True` в GET-запросе. Паузу должен снимать только явный `POST /resume`.

---

### BUG-6: `list_active_sessions` загружает каждую сессию дважды

**Файл:** `server.py:2601-2643`  
**Серьёзность:** Низкая (перформанс)  

`repo.list_active_sessions()` уже вызывает `load_session()` внутри для каждого файла. Затем `list_active_sessions` endpoint вызывает `load_session_by_session_id()`, который снова сканирует и парсит все файлы. Двойная загрузка.

**Решение:** Рефакторить: `list_active_sessions()` в репозитории должен возвращать полные объекты `ComplexSession`, а не только метаданные.

## 3. Нереализованные аспекты

### MISSING-1: Нет индикации паузы на ГЛАВНОЙ СТРАНИЦЕ (`/ui/main`)

На главной странице (`MainLogic.js`) quick-access карточки уже показывают бейдж "На паузе" и текст "На паузе с {дата} · {прогресс}". **Это реализовано.**

Однако на странице **комплексов** (`Complexes/index.html`) бейдж "На паузе" показывается, но **нет прогресс-бара** визуально отображающего, какая часть итерации пройдена. Есть только текстовый "Прогресс: N/M".

**Предложение:** Добавить миниатюрный прогресс-бар под текстом паузы на карточке комплекса.

---

### MISSING-2: Нет лимита на длительность паузы / автоматическая очистка устаревших сессий

Паузированная сессия хранится на диске **бессрочно**. Нет механизма:
- Автоматического удаления сессий, которые на паузе больше N дней
- Предупреждения пользователя о "протухших" сессиях
- Ограничения количества паузированных сессий

**Предложение:** 
- Добавить настройку `max_pause_duration_days` (например, 30 дней)
- При загрузке списка сессий проверять `paused_at` и помечать устаревшие
- Показывать предупреждение и кнопку "Удалить устаревшие"

---

### MISSING-3: Нет возможности иметь несколько паузированных сессий одного комплекса

**Файл:** `session_repository.py:98-110`

Файл сессии хранится как `{complex_id}.json`. При создании новой сессии для того же комплекса файл **перезаписывается**, и предыдущая паузированная сессия теряется.

**Текущее поведение:** Если пользователь поставил сессию на паузу и затем начинает новую сессию для того же комплекса, старая паузированная сессия **уничтожается** без предупреждения.

**Предложение:**
- При запуске новой сессии проверять наличие паузированной
- Если есть паузированная — спрашивать: "Продолжить существующую или начать заново?"
- На уровне API endpoint `/api/session/{complex_id}/start` возвращать `"has_paused_session": true`

---

### MISSING-4: Нет учёта времени паузы в `iteration_timestamps`

Итерация может быть начата, затем поставлена на паузу, затем возобновлена. `iteration_timestamps[N]['start']` и `iteration_timestamps[N]['end']` не учитывают паузу — длительность итерации **завышается** на время паузы.

Связано с BUG-4.

---

### MISSING-5: Нет уведомления/напоминания о паузированных сессиях

При входе на главную страницу пользователь видит quick-access карточки, но нет **явного баннера** или уведомления типа "У вас есть незавершённая сессия комплекса X. Продолжить?".

**Предложение:** Показывать баннер-напоминание вверху главной страницы, если есть паузированные сессии.

---

### MISSING-6: Нет защиты от одновременного доступа к сессии из нескольких вкладок

Если пользователь откроет одну и ту же сессию в двух вкладках браузера:
- В одной вкладке поставит на паузу
- В другой вкладке продолжит отвечать

HTTP-guard на `/submit` проверяет `session.paused`, но между проверкой и отправкой ответа состояние может измениться. Нет механизма websocket-нотификации или lock-механизма.

**Предложение:** Добавить `session_version` / `etag`-подобный механизм для оптимистичной блокировки, или хотя бы фронтенд-проверку при `beforeunload`.

## 4. Слабые места архитектуры

### WEAK-1: Отсутствие идемпотентности `pause_session`

`SessionAPI.pause_session()` вызывает `self.get_session()` → если сессия не найдена, тихо возвращает `None`. Но `AdaptiveSessionManager.pause_session()` тоже тихо возвращает `None` если сессия не в `_active_sessions`. Нет различия между "сессия не найдена" и "сессия успешно поставлена на паузу".

HTTP endpoint уже проверяет и возвращает 404, но `SessionAPI.pause_session()` не возвращает результат (void).

**Предложение:** `pause_session()` должен возвращать `bool` или `Dict` с результатом.

---

### WEAK-2: `get_current_task()` с `auto_resume` — побочный эффект в GET-запросе

GET-запрос не должен менять состояние (идемпотентность HTTP). `auto_resume=True` нарушает это, снимая паузу и сохраняя сессию на диск.

---

### WEAK-3: Паузированная сессия не блокирует создание новой

При нажатии "Запустить" для комплекса, у которого есть паузированная сессия, фронтенд корректно показывает "Продолжить" и перенаправляет на существующую сессию. Но если вызвать API напрямую `POST /api/session/{complex_id}/start`, то:
- Создастся новая сессия
- Файл `{complex_id}.json` **перезапишется**
- Паузированная сессия потеряется

Нет серверной защиты.
