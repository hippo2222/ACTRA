## 1. Общая концепция

### 1.1. Текущее состояние

Сейчас импорт заданий работает в режиме **ручного конвейера**:
1. Пользователь копирует промпт из интерфейса.
2. Вставляет его в стороннюю нейросеть (ChatGPT, Claude и т.д.) вместе с материалом.
3. Копирует ответ нейросети.
4. Вставляет ответ в текстовое поле импорта.
5. Парсер разбирает текст → предпросмотр → импорт.

Шагов 2–4 можно избежать, если встроить вызов LLM прямо в бэкенд.

### 1.2. Целевое состояние

**Три режима импорта** в одном модальном окне:

| Режим | Когда используется |
|---|---|
| **ИИ-генерация** | Есть интернет + доступный API-провайдер. Полная автоматизация. |
| **Из текста** | Пользователь сам работает с нейросетью и вставляет результат. Фолбек, если API недоступен. |
| **Из архива** | Импорт готовых заданий из ZIP. Не связан с ИИ. |

### 1.3. Ключевые принципы

- **Graceful degradation**: если все API недоступны → автоматический переход в ручной режим с промптами.
- **Прозрачность**: пользователь всегда видит, что ИИ рекомендует, и может корректировать.
- **Минимум запросов**: один запрос на анализ + по одному запросу на каждый одобренный тип заданий.
- **Не зависим от конкретного провайдера**: абстракция над API позволяет подключить любого.
- **Защита от некорректного ввода**: валидация файлов, лимиты загрузок, понятные сообщения об ошибках — система рассчитана на неподготовленного пользователя.
- **API — дело разработчика**: пользователь не видит и не настраивает API-ключи. Все ключи хранятся на бэкенде.

## 2. Архитектура API-провайдеров

### 2.1. Цепочка фолбеков

```
┌─────────────────────────────────────────────────┐
│ 1. ОСНОВНОЙ: OpenRouter                         │
│    Модели: deepseek-chat, llama-3.1-8b и др.   │
│    Лимит: варьируется, ~20 req/min              │
│    API-ключ: sk-or-v1-... (бэкенд)             │
│    Преимущество: широкий выбор бесплатных       │
│    моделей, гибкость маршрутизации              │
├─────────────────────────────────────────────────┤
│ 2. ЗАПАСНОЙ №1: Google Gemini Free API          │
│    Модель: gemini-2.0-flash-lite (бесплатно)    │
│    Лимит: 30 req/min, 1500 req/day              │
│    API-ключ: AIzaSy... (бэкенд)                │
├─────────────────────────────────────────────────┤
│ 3. ЗАПАСНОЙ №2: Groq                            │
│    Модели: llama-3.1-70b, mixtral-8x7b и др.   │
│    Лимит: 30 req/min, 14400 req/day             │
│    API-ключ: gsk_... (бэкенд)                  │
│    Преимущество: высокая скорость инференса     │
├─────────────────────────────────────────────────┤
│ 4. ФОЛБЕК: Ручной режим                        │
│    Показываем промпты для самостоятельной       │
│    работы пользователя с любой нейросетью.      │
│    Это текущий функционал — он никуда не        │
│    уходит.                                       │
└─────────────────────────────────────────────────┘
```

> **Важно**: API-ключи хранятся **исключительно на бэкенде** в конфигурационном файле сервера. Пользователь не имеет доступа к настройке ключей — это зона ответственности разработчика/администратора.

### 2.2. Логика выбора провайдера

```
При открытии модального окна импорта:
1. Фронтенд запрашивает GET /api/editor/ai/status.
2. Бэкенд проверяет доступность провайдеров по цепочке:
   a. OpenRouter → пинг-проверка (HEAD/lightweight запрос).
   b. Если OpenRouter недоступен → Google Gemini → пинг-проверка.
   c. Если Gemini недоступен → Groq → пинг-проверка.
   d. Если все три недоступны → ai_available: false.
3. Запомнить активного провайдера в текущей сессии на бэкенде.
4. Фронтенд получает результат:
   - ai_available: true → кнопка «ИИ-генерация» активна.
   - ai_available: false → кнопка серая, tooltip:
     «Функция временно недоступна. Попробуйте позже».
```

### 2.3. Переключение при ошибке (runtime fallback)

```
При отправке запроса:
1. Отправить в активного провайдера (OpenRouter → Gemini → Groq).
2. Если ответ: таймаут (60с), 429, 500, 503 →
   a. Попробовать следующего провайдера из цепочки.
   b. Если все три провайдера исчерпаны →
      вернуть пользователю вежливое сообщение:
      «Извините, сервис генерации временно недоступен.
       Пожалуйста, попробуйте позже или воспользуйтесь
       ручным режимом.»
3. Если ответ OK, но парсинг ответа провалился →
   одна повторная попытка к тому же провайдеру,
   если снова провал → показать сырой текст пользователю
   с возможностью ручной вставки.
```

## 3. Двухфазная генерация: Анализ → Генерация

### 3.1. Фаза 1: Анализ материала (нулевой промпт)

**Цель**: Определить «образовательные единицы» в материале и рекомендовать оптимальную стратегию генерации.

**Вход**: Текст материала (вставленный или извлечённый из PDF/DOCX).

**Выход**: Структурированный JSON, который бэкенд может распарсить + человекочитаемое резюме.

#### 3.1.1. Формат ответа нулевого промпта

Промпт инструктирует ИИ вернуть ответ в двух секциях:

```
<human_summary>
[Краткое резюме для преподавателя: 3–5 предложений]
</human_summary>

<analysis_json>
{
  "material_volume": "small | medium | large",
  "educational_units": [
    {
      "id": 1,
      "title": "Этиология пневмонии",
      "type": "concept",
      "description": "Основные возбудители и факторы риска"
    },
    {
      "id": 2,
      "title": "Стадии крупозной пневмонии",
      "type": "process",
      "description": "Четыре последовательные стадии патогенеза"
    }
  ],
  "recommendations": [
    {
      "task_type": "TEST",
      "count": 5,
      "priority": "high",
      "covers_units": [1, 3, 4],
      "rationale": "Материал насыщен фактами и классификациями"
    },
    {
      "task_type": "SEQUENCE",
      "count": 2,
      "priority": "medium",
      "covers_units": [2],
      "rationale": "Стадии заболевания имеют чёткую хронологию"
    },
    {
      "task_type": "OPEN_ANSWER",
      "count": 3,
      "priority": "high",
      "covers_units": [1, 5],
      "rationale": "Причинно-следственные связи требуют формулирования"
    }
  ],
  "not_recommended": [
    {
      "task_type": "CLICK_WORDS",
      "reason": "Материал содержит мало плотных фактических абзацев"
    }
  ],
  "illustrations_detected": false,
  "illustrations_note": null,
  "warnings": []
}
</analysis_json>
```

#### 3.1.2. Парсинг ответа на бэкенде

```python
import re, json

def parse_analysis_response(raw_text: str) -> dict:
    """
    Извлекает JSON из ответа ИИ-агента.
    Ищет блок между маркерами <analysis_json> и </analysis_json>.
    Если маркеры не найдены, пытается найти первый валидный JSON-объект.
    """
    # Стратегия 1: По маркерам
    match = re.search(
        r'<analysis_json>\s*(\{.*?\})\s*</analysis_json>',
        raw_text, re.DOTALL
    )
    if match:
        return json.loads(match.group(1))
    
    # Стратегия 2: Найти JSON-блок
    match = re.search(r'\{[^{}]*"recommendations"[^{}]*\}', raw_text, re.DOTALL)
    if match:
        return json.loads(match.group(0))
    
    # Стратегия 3: Ответ непарсируем
    raise ValueError("Cannot parse analysis response")
```

#### 3.1.3. Что показывается пользователю после анализа

Фронтенд получает от бэкенда:
```json
{
  "ok": true,
  "human_summary": "Материал посвящён пневмонии...",
  "recommendations": [...],
  "educational_units": [...],
  "not_recommended": [...],
  "illustrations_detected": false,
  "illustrations_note": null,
  "warnings": []
}
```

И отображает:
1. **Резюме материала** — текстовый блок.
2. **Образовательные единицы** — список того, что будет прорабатываться (опционально, в collapsible-секции).
3. **Рекомендации по типам** — карточки с чекбоксами и ползунками количества:

```
┌──────────────────────────────────────────────────┐
│ ☑ TEST — 5 заданий                    [высокий] │
│   «Материал насыщен фактами...»         [- 5 +] │
├──────────────────────────────────────────────────┤
│ ☑ OPEN_ANSWER — 3 задания              [высокий] │
│   «Причинно-следственные связи...»      [- 3 +] │
├──────────────────────────────────────────────────┤
│ ☑ SEQUENCE — 2 задания                 [средний] │
│   «Стадии заболевания...»               [- 2 +] │
├──────────────────────────────────────────────────┤
│ ☐ CLICK_TEXT — не рекомендуется                  │
│   «Мало подходящих утверждений...»               │
├──────────────────────────────────────────────────┤
│ ☐ CLICK_WORDS — не рекомендуется                 │
│   «Мало плотных фактических абзацев»             │
└──────────────────────────────────────────────────┘
         [ Сгенерировать задания → ]
```

Пользователь может:
- Включить/выключить любой тип (чекбокс).
- Изменить количество заданий (инкремент/декремент) — **с предупреждением** (см. ниже).
- Включить нерекомендованный тип вручную (система не запрещает, только предупреждает).

#### 3.1.4. Предупреждение при увеличении количества заданий

При увеличении количества заданий сверх рекомендованного ИИ значения, рядом с контролом появляется предупреждение:

```
⚠ Увеличение количества заданий может снизить их качество.
  Рекомендуемое значение для этого типа: 5
```

**Проблема сложных тем и ограничений бесплатных моделей:**

Существует объективное противоречие: для сложных/объёмных тем пользователю может хотеться больше заданий, однако бесплатные LLM-модели имеют ограничения по качеству генерации при больших объёмах.

**Принятое решение — «умные лимиты»:**

| Объём материала | Макс. заданий на тип | Макс. заданий суммарно |
|---|---|---|
| Малый (~1 стр.) | 3–4 | 8 |
| Средний (~3–5 стр.) | 6–8 | 20 |
| Большой (~10+ стр.) | 10–12 | 30 |

- Пользователь **может** превысить рекомендацию, но не более чем на 50% от рекомендованного значения.
- При попытке выставить больше максимума — мягкое объяснение:
  ```
  Для сохранения качества генерации максимальное количество
  заданий этого типа ограничено значением N.
  Если вам нужно больше заданий — попробуйте разбить материал
  на части и загрузить их по отдельности.
  ```
- Это также помогает экономить лимиты бесплатных API.

### 3.2. Фаза 2: Генерация заданий

**Вход**: Текст материала + выбранные пользователем типы и количества.

**Стратегия генерации**: Один запрос на каждый выбранный тип задания.

#### 3.2.1. Почему один запрос на тип, а не один общий запрос

| Критерий | Один запрос на тип | Один общий запрос |
|---|---|---|
| Качество | Выше: промпт сфокусирован | Ниже: модель «размазывает» внимание |
| Надёжность парсинга | Выше: один формат на ответ | Ниже: смешанные маркеры, частые ошибки |
| Отказоустойчивость | Если один тип провалился, остальные ОК | Всё или ничего |
| Параллельность | Можно отправить одновременно | Невозможно |
| Кол-во запросов | 2–5 (только одобренные типы) | 1 |

**Решение**: Один запрос на тип. Запросы отправляются **параллельно** (Promise.all на фронте или asyncio/threading на бэкенде).

#### 3.2.2. Передача контекста из нулевого анализа в генерационные промпты

Генерационные промпты дополняются данными из нулевого анализа:

```
[Стандартный промпт для типа TEST]

<generation_parameters>
Сгенерируй ровно 5 тестовых вопросов.
Сфокусируйся на следующих образовательных единицах:
1. Этиология пневмонии — основные возбудители и факторы риска
2. Клиническая картина — симптомы и их патогенез
3. Диагностика — методы подтверждения диагноза
</generation_parameters>

<material>
[Текст материала пользователя]
</material>
```

Таким образом, каждый генерационный промпт получает:
- Стандартные инструкции формата (уже существуют).
- Точное количество заданий для генерации.
- Список образовательных единиц, на которые нацелена генерация.
- Сам материал.

#### 3.2.3. Обработка ответов

Каждый ответ прогоняется через соответствующий парсер (`OpenAnswerParser`, `SequenceParser`, `TestImportParser`, `ClickTextParser`, `ClickWordsParser`) — те же парсеры, что уже работают в `/api/editor/import/parse`.

```
Ответ от LLM → Парсер по типу → Валидация → Preview-объект
```

Если парсер не смог распарсить ответ:
1. Одна повторная попытка генерации (retry).
2. Если повтор тоже провалился → этот тип помечается ошибкой, пользователю предлагается сгенерировать вручную (показать промпт).

#### 3.2.4. Прогресс генерации

Пока идут запросы, фронтенд показывает прогресс:

```
Генерация заданий...

✓ TEST — 5 заданий сгенерировано          [2.3с]
⟳ OPEN_ANSWER — генерация...              
⟳ SEQUENCE — генерация...
```

Каждый тип обновляется независимо по мере получения ответов (т.к. запросы параллельные).

## 5. Фронтенд: изменения UI

### 5.0. Общие требования к UI-изменениям

> **Все** описанные ниже изменения UI реализуются с учётом:
> - **Системы цветовых схем** (тёмная/светлая тема) — каждый новый элемент должен корректно отображаться в обеих схемах.

> - **Существующих CSS-переменных** — использовать `var(--color-*)` вместо хардкода цветов.

### 5.0.1. Расширение модального окна импорта

Текущее модальное окно импорта заданий **ограничено по ширине**, что затрудняет восприятие контента, особенно в режиме ИИ-генерации (анализ, рекомендации, предпросмотр). 

**Решение**: расширить модальное окно до `max-width: 900px` (текущее ~600px) для комфортной работы с таблицами рекомендаций, предпросмотром заданий и формами загрузки файлов. На экранах < 768px — окно занимает 95% ширины viewport.

> **Решение**: пользовательского интерфейса настроек API-провайдеров **не будет**.

Пользователь взаимодействует с ИИ-генерацией как с «чёрным ящиком»: либо функция работает — и он ей пользуется, либо не работает — и он получает вежливое сообщение о временных неполадках.

### 5.5. Система лимитов и защиты (UI-компоненты)

#### 5.5.1. Счётчик дневных загрузок

В шапке режима ИИ-генерации (Step 1) отображается ненавязчивый индикатор:

```
Загрузки сегодня: ●●○  (2 из 3)
```

При исчерпании лимита:
```
Загрузки сегодня: ●●●  (3 из 3) — лимит исчерпан
Обновится завтра в 00:00
```

#### 5.5.2. Обоснование лимита в 3 файла/сутки

Один файл потенциально порождает до **6 генерационных запросов** (анализ + до 5 типов заданий). Три файла = до **18 запросов к API** в сутки на одного пользователя. Лимит:
- Защищает бесплатные API от исчерпания квот.
- Стимулирует осознанный подход к выбору материала.
- Легко увеличивается в конфиге при необходимости.

### 5.6. Обработка файлов: PDF и DOCX

#### 5.6.1. Поддерживаемые форматы

| Формат | Библиотека | Особенности |
|---|---|---|
| **PDF** (с текстовым слоем) | `PyMuPDF` (fitz) | Извлечение текста постранично, поддержка Unicode, игнорирование изображений |
| **PDF** (скан, без текста) | — | Распознавание **не поддерживается**. Вежливое объяснение пользователю (см. валидацию выше) |
| **DOCX** | `python-docx` | Извлечение текста из параграфов и таблиц, игнорирование стилей/картинок |
| **TXT** | стандартная библиотека | Автоопределение кодировки через `chardet` (UTF-8, Windows-1251, KOI8-R и др.) |

#### 5.6.2. Пайплайн обработки файла

```
Файл от пользователя
  │
  ├─► Проверка расширения (.pdf / .docx / .txt)
  │     └─ Нет → «Формат не поддерживается. Поддерживаемые: PDF, DOCX, TXT.»
  │
  ├─► Проверка размера (≤ 10 МБ)
  │     └─ Нет → «Файл слишком большой. Максимум — 10 МБ.»
  │
  ├─► Извлечение текста
  │     ├─ PDF: проверка текстового слоя → если нет → объяснение для пользователя
  │     ├─ DOCX: парсинг параграфов
  │     └─ TXT: определение кодировки → декодирование
  │
  ├─► Подсчёт слов
  │     ├─ < 50 слов → «Слишком мало текста»
  │     └─ > 15 000 слов → предложение обрезать
  │
  └─► Возврат extracted_text + метаданные
```

#### 5.6.3. Определение кодировки

Для TXT-файлов (и некоторых PDF) используется `chardet` с фолбеком:
1. Попробовать UTF-8.
2. Если ошибка → `chardet.detect()` для определения кодировки.
3. Если `chardet` не уверен (confidence < 0.7) → попробовать Windows-1251 (наиболее частая для русскоязычных документов).
4. Если ничего не помогло → сообщение пользователю с просьбой пересохранить в UTF-8.

## 6. Нулевой промпт: обновлённая версия

Текущий нулевой промпт (material_analysis) предназначен для чтения человеком. Для автоматического режима нужна версия с машиночитаемым выводом.

### 6.1. Стратегия: два варианта промпта

- **`material_analysis`** (для ручного режима) — текущий промпт, человекочитаемый вывод. Остаётся как есть.
- **`material_analysis_structured`** (для автоматического режима) — вызывается бэкендом, требует JSON-вывод. Хранится в `ai_generation_service.py`, а не в `import_manager.js`.

### 6.2. Содержание structured-промпта

```

</illustrations_rule>

  ],
  "not_recommended": [
    { "task_type": "...", "reason": "..." }

  "illustrations_detected": false,
  "illustrations_note": null,
```

## 7. Порядок реализации (фазы)

### Фаза A: Бэкенд — провайдеры и сервис генерации

1. Создать `services/ai_generation_service.py`:
   - Классы провайдеров: `OpenRouterProvider`, `GeminiProvider`, `GroqProvider`.
   - Класс `AIGenerationService` с логикой цепочки фолбеков (OpenRouter → Gemini → Groq → ручной режим).
   - Функция `parse_analysis_response()`.
   - Structured-промпт для анализа.
   - Промпты для генерации (параметризованные версии существующих).

2. Создать `{USER_DATA_DIR}/ai_config.json` — серверный конфиг с API-ключами (не доступен пользователю).

3. Добавить эндпоинты в `server.py`:
   - `GET /api/editor/ai/status` (с информацией о дневном лимите)
   - `POST /api/editor/ai/analyze`
   - `POST /api/editor/ai/generate`
   - `POST /api/editor/ai/upload` (загрузка и обработка файлов)

4. Написать тесты для:
   - Парсинга ответа анализа (JSON extraction из разных форматов ответа).
   - Фолбек-логики (мок провайдеров).
   - Интеграции с парсерами (ответ LLM → парсер → preview).

### Фаза B: Бэкенд — обработка файлов и лимиты

5. Создать класс `FileProcessor`:
   - Извлечение текста из PDF (`PyMuPDF`), DOCX (`python-docx`), TXT.
   - Определение кодировки (`chardet`).
   - Проверка наличия текстового слоя в PDF.
   - Валидация: размер, формат, объём текста.

6. Система дневных лимитов:
   - Хранение счётчика загрузок (по пользователю/сессии, с обнулением в 00:00).
   - Проверка лимита перед обработкой файла.
   - Возврат информации о лимите в `/api/editor/ai/status`.

7. Тесты для обработки файлов:
   - PDF с текстом, PDF-скан (без текста), DOCX, TXT в разных кодировках.
   - Граничные случаи: пустой файл, огромный файл, файл с изображениями.

### Фаза C: Фронтенд — режим ИИ-генерации

8. Расширить модальное окно импорта (`max-width: 900px`), проверить во всех цветовых схемах.

9. Добавить режим `'ai'` в ImportManager:
   - Новое свойство: `importMode = 'text' | 'archive' | 'ai'`.
   - Новые свойства: `materialText`, `analysisResult`, `generationResult`, `aiProvider`, `dailyLimit`.

10. Step 1: третья кнопка «ИИ-генерация» + поле для материала + загрузка файлов + счётчик лимитов.
    - Валидация файлов на фронтенде (формат, размер, пустота).
    - Drag-and-drop зона.

11. Step 2 (AI): UI анализа — резюме + карточки рекомендаций с чекбоксами и +-количества.
    - Предупреждения при превышении рекомендованного количества заданий.
    - «Умные лимиты» по количеству заданий в зависимости от объёма материала.

12. Step 3 (AI): UI прогресса генерации → **компактный предпросмотр списком** (не как в тренажёре).
    - Группировка по типам со сворачиванием.
    - Чекбоксы для выборочного импорта.
    - Предупреждения (⚠) на проблемных заданиях.

13. Фолбеки и ошибки в UI:
    - Экран ошибки анализа с вежливым сообщением + кнопка «Ручной режим».
    - Частичный фолбек при ошибке генерации одного типа.
    - Сообщения о лимитах и проблемах с файлами (понятные неподготовленному пользователю).

### Фаза D: Полировка и тестирование

14. Проверка доступности при открытии модального окна (`/api/editor/ai/status`).

15. Аудит контрастности и корректности отображения в обеих цветовых схемах.

16. Тестирование полного цикла: файл → валидация → извлечение текста → анализ → генерация → предпросмотр → выборочный импорт.

17. Тестирование граничных случаев:
    - Все провайдеры недоступны → вежливое сообщение + ручной режим.
    - PDF-скан → понятное объяснение.
    - Файл 50 МБ → отказ с объяснением.
    - 4-й файл за сутки → отказ с объяснением.
    - Превышение количества заданий → мягкое ограничение.

## 9. Риски и митигация

| Риск | Вероятность | Митигация |
|---|---|---|
| LLM не возвращает валидный JSON | Средняя | Два слоя парсинга (маркеры → поиск JSON). Retry. Показ сырого текста. |
| LLM генерирует невалидные задания | Средняя | Прогон через существующие парсеры + валидаторы. Некорректные задания помечаются, но не блокируют импорт. |
| Бесплатные лимиты исчерпаны | Средняя | Тройная цепочка фолбеков (OpenRouter → Gemini → Groq). Кэширование анализа в сессии. Дневной лимит 3 файла. |
| API-ключ утёк | Низкая | Ключи хранятся только в серверном `ai_config.json`, не в коде, не передаются на фронтенд. Пользователь не имеет доступа к ключам. |
| Модель галлюцинирует лишние задания | Средняя | Строгая инструкция «ровно N заданий» + постпроверка (если count > запрошенного — обрезать). |
| Материал слишком длинный для контекста | Низкая | Ограничение 15 000 слов на бэкенде. Предложение обрезать при превышении. Gemini Flash: 1M токенов, Groq: 128K. |
| Пользователь загружает огромный файл | Средняя | Лимит 10 МБ на фронтенде (до отправки) + на бэкенде. Понятное сообщение об ошибке. |
| Пользователь загружает неподдерживаемый формат | Высокая | Проверка расширения на фронтенде. Whitelist: PDF, DOCX, TXT. Понятное сообщение. |
| PDF без текстового слоя (скан) | Средняя | Проверка `has_text_layer()` на бэкенде. Объяснение «как для 5-летнего» почему файл нельзя обработать. |
| Ошибка кодировки в TXT/PDF | Низкая | `chardet` + фолбек на Windows-1251 + UTF-8. При неудаче — просьба пересохранить файл. |
| Качество падает при большом кол-ве заданий | Средняя | «Умные лимиты»: макс. +50% от рекомендации. Предупреждение при увеличении количества. |
| Все три провайдера одновременно недоступны | Низкая | Вежливое сообщение пользователю (не технические детали). Автоматическое предложение ручного режима. |

## 10. Что НЕ входит в этот план

- **Стриминг ответов (SSE)**. Все запросы — стандартные request/response. Стриминг можно добавить позже как оптимизацию.
- **Кэширование ответов LLM** между сессиями.
- **Платные API-провайдеры** (OpenAI, Anthropic). Можно добавить как дополнительных провайдеров по тому же интерфейсу.
- **OCR (распознавание текста из изображений/сканов)**. PDF без текстового слоя не обрабатываются — пользователю объясняется, почему, и предлагается найти электронную версию.
- **Пользовательские настройки API**. Вся конфигурация провайдеров — на стороне разработчика/администратора.
- **Редактирование заданий в предпросмотре**. Предпросмотр — только для оценки и выборочного принятия/отклонения. Редактирование — после импорта в существующем редакторе.
